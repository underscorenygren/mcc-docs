Message Mechanics

A walk through the fundamentals of messaging — what messages are, how they move, what can go wrong — and how our system maps against these concepts. Written as a reference for making design decisions, not a spec.

For deeper reading:

  • S2.dev — a streaming platform that nails the "ordered durable log" model
  • Designing Data-Intensive Applications (Kleppmann, Ch. 11) — the best single chapter on stream processing
  • You Cannot Have Exactly-Once Delivery — why "exactly once" is about semantics, not physics
  • The Log (Jay Kreps) — the foundational essay on log-based architectures (O'Reilly excerpt, summary)

What is a message?

A message is a unit of data that moves from one place to another. That's it. Everything else — IDs, ordering, delivery guarantees — is machinery we add on top to deal with the fact that networks are unreliable and time is hard.

A message has:

  • Payload — the content (text, JSON, binary audio frames)
  • Metadata — who sent it, when, where it's going
  • Identity — some way to tell this message apart from every other message

The identity part is where things get interesting.

Message IDs: why they matter

A message without an ID is a message you can't talk about. You can't deduplicate it, you can't acknowledge it, you can't replay it without risking duplicates.

ID generation strategies

Client-generated IDs
The sender creates the ID before sending.
  • Pro: the sender knows the ID immediately, can retry idempotently
  • Con: clients can generate collisions (bad randomness, clock skew)
  • Example: chat_1729043255000_a7x3 — our chat messages use timestamp + random suffix
Server-generated IDs
The receiver assigns the ID on receipt.
  • Pro: guaranteed unique within the server's namespace
  • Con: the sender doesn't know the ID until the server responds — creates a window where the message exists but can't be referenced
  • Example: Kafka offsets — the broker assigns a sequence number on append
Content-derived IDs
Hash the payload to get the ID.
  • Pro: naturally idempotent — same content = same ID
  • Con: intentionally identical messages (retries with different intent) become indistinguishable
  • Example: our chatbus dedup uses hash:<agent>:<from>:<text_first_200> as a fallback when no ID is provided
Sequence numbers
A monotonically increasing counter.
  • Pro: gives you ordering for free — if ID 42 < ID 43, message 42 came first
  • Con: requires a single point of coordination (whoever hands out numbers)
  • Example: S2's model — records are identified by sequence number, ordered and durable before acknowledgment

What we do

We use client-generated IDs with prefixes that encode the message type:

PrefixSourceExample
chat_User typed in web UIchat_1729043255000_a7x3

hist_History replay (fallback)hist_1729043255000

The hist_ prefix is a known problem. When the server replays history, it generates new IDs instead of preserving the original reply_ IDs. The client sees the same message arrive twice with different IDs and can't deduplicate. This was issue #222.

Lesson: if you generate IDs at one layer and replay at another, the IDs must survive the round trip. Otherwise your dedup breaks at exactly the moment it matters most — reconnection.

Ordering

Messages have a natural order — the order they were sent. But networks don't preserve order. A message sent second can arrive first. A message can arrive twice. A message can never arrive at all.

Ordering models

Total order
Every consumer sees every message in the same order. This is what a single Kafka partition gives you, and what S2 gives you per-stream. It requires a single writer (or coordination between writers).
Partial order
Messages within a scope are ordered, but across scopes they're not. Kafka achieves this with partitions — messages in partition 0 are ordered relative to each other, but not relative to partition 1.
No order
Messages arrive whenever. UDP, email, most HTTP-based pub/sub without sequence numbers.

What we do

We have per-agent ordering — messages to/from a single agent are stored sequentially in that agent's JSONL log file. But across agents, there's no ordering guarantee.

Within the chatbus, the in-memory ring buffer preserves insertion order, but the ring drops old entries when full. A client that reconnects after the ring has wrapped may miss messages — the fallback is timestamp-based replay from the JSONL file on disk.

How S2 differs: S2 assigns sequence numbers on append, so consumers can ask for "everything after sequence 47" and get a gapless, ordered response. We use timestamps instead, which means our "everything after T" query can miss messages written at the same millisecond or with clock skew.

Delivery guarantees

This is the taxonomy everyone learns:

At-most-once
Send and forget. The message might not arrive. You don't retry. Fast and simple.
At-least-once
Retry until acknowledged. The message will arrive, but possibly more than once. Requires idempotency or dedup on the receiver side.
Exactly-once
Each message is processed exactly once. This is the holy grail and it doesn't exist at the network level. What systems call "exactly-once" is really "at-least-once delivery + idempotent processing" — the message may arrive multiple times, but the side effect only happens once.

What we do

Our system is at-most-once with client-side dedup as a safety net.

The chatbus has a dedup cache with a 5-minute TTL. If the same message ID (or content hash) arrives within 5 minutes, the duplicate is suppressed. After 5 minutes, the cache entry expires and a true duplicate would be processed again.

The client (ChatStore) maintains a seenIds Set. Every message that arrives — live or replayed — is checked against this set. Duplicates are silently dropped.

Publisher → Chatbus (TTL dedup) → Bridge (broadcast) → Client (seenIds dedup) ↘ JSONL log (replay source)

This is not Kafka. We give you a best-effort fan-out with two layers of dedup. The tradeoff: much simpler, much lower latency, but no guarantee that a message won't be lost if the server crashes between receiving it and writing to disk (no fsync).

For chat messages, this is fine. For financial transactions, it would not be.

Connections and reconnection

A WebSocket connection is a stateful pipe. When it breaks, you lose:

  1. Any in-flight messages (sent but not yet received)
  2. Any messages the server would have sent while you were disconnected
  3. The server's knowledge of where you left off (unless you told it)

Reconnection strategies

Dumb reconnect
Connect fresh, get whatever the server gives you. Simple but you either miss messages or get duplicates.
Cursor-based reconnect
The client tracks a cursor (sequence number, timestamp, offset) and tells the server "I last saw X, send me everything after X."
Session resumption
The server tracks per-client state. On reconnect, the server knows what it already sent and picks up where it left off. More complex server-side but simpler for the client.

What we do

We use cursor-based reconnect with a timestamp cursor:

  1. Client receives a message → stores its timestamp in localStorage as voice-last-msg-ts
  2. Connection drops → client detects WebSocket close
  3. Client reconnects → sends { type: "subscribe", since: "<stored_timestamp>", last: 10 }
  4. Server queries JSONL log for messages after that timestamp
  5. If the timestamp query returns fewer than 10 results → fall back to "last 10 messages"
  6. Client receives replayed messages → dedup via seenIds

The last: 10 fallback handles page reloads where localStorage has a stale timestamp or none at all. Rather than showing nothing, we show the last N messages so the user has context.

Protocols and layers

"Protocol" just means "the rules two sides agree on for talking to each other." Our system has several layers:

Transport — WebSocket

The pipe. Bidirectional, persistent, message-framed (unlike raw TCP which is a byte stream). We use WebSocket because the browser supports it natively, we need server-initiated messages, and HTTP polling wastes bandwidth for real-time chat.

Wire format — JSON messages

Every WebSocket frame contains a JSON object with a type field:

{ "type": "agent_message", "text": "hello", "id": "reply_123", "from": "supervisor" }
{ "type": "history_agent", "text": "hello", "id": "reply_123", "ts": "2026-10-16T00:00:00Z" }
{ "type": "subscribe", "since": "2026-10-15T23:00:00Z", "last": 10 }
{ "type": "ping" }
{ "type": "pong" }

The type field is the discriminator — it tells the receiver how to interpret the rest of the payload. This is a tagged union pattern, common in WebSocket protocols.

Application — message semantics

Above the wire format, there's the semantic layer. history_agent and agent_message contain the same data (text from an agent), but:

  • agent_message = live, just happened, display immediately
  • history_agent = replay, already happened, display but mark as historical

The client must handle both. The server must send the right one. This is where bugs live — the boundary between "this is new" and "you already saw this."

Bus — routing and fan-out

User sends "hello" to agent A → HTTP POST /agent/A/send → Chatbus receives, assigns envelope, persists → Forward to agent A's channel server → Agent A processes, responds → Chatbus receives response, persists → Broadcast to all connected WebSocket clients

The bus is a mediator — no client talks directly to an agent. Publishers (users, agents) don't know about subscribers (connected clients). The bus handles routing.

Two buses: chat and events

We have two separate bus services, and understanding which signals flow where is critical for designing acks, lag detection, and voice integration.

The split

Why two?

The chatbus carries primary content — the actual messages users and agents exchange. These need persistence, dedup, and replay. The sysbus carries secondary signals — operational telemetry that the UI uses for status display. These are ephemeral; losing a tool_use event doesn't break anything.

Mixing them would overload the chat bus. A single agent tool call generates dozens of sysbus events (tool_use, file_change, git_op, etc.). If those flowed through the chatbus, they'd drown out actual messages and bloat the JSONL logs.

Where acks should live

Acks are secondary signals, not primary content. An ack ("I received seq 5") is metadata about a message, not a message itself. It belongs on the sysbus, not the chatbus.

The proposed ack flow:

User sends message → Chatbus assigns seq=5, routes to agent channel → Channel receives message → Channel emits to sysbus: {type: "message_ack", agent: "porter", status: "delivered", seq: 5} → Agent (Claude) picks up message → Agent emits to sysbus: {type: "message_ack", agent: "porter", status: "processing", seq: 5} → Agent responds → Response goes through chatbus (primary content) → Chatbus broadcasts response with ref_seq: 5

Primary content (messages, responses) flows through the chatbus. Secondary signals (acks, status, lag) flow through the sysbus. The UI combines both streams: chatbus for the chat panel, sysbus for the checkmarks and status indicators.

The agent blocking problem

The biggest issue isn't message delivery — it's that agents can't read new messages while they're working. This is an MCP/Claude Code constraint: when Claude is executing a tool call, the MCP transport queues incoming notifications. Claude doesn't see them until the current turn completes.

Message arrives → Channel server receives → MCP notification sent to stdin ↓ Claude is mid-tool-call stdin buffer holds notification ...tool runs for 30s... tool returns Claude reads stdin NOW it sees the message

This is fundamentally different from a chat app where the server can interrupt the client. Our "agent" is a single-threaded reasoning loop. It can't multitask.

Options to reduce blocking

1. Shorter tool calls (preventive)

If tool calls are shorter, the gap between "message delivered" and "message read" shrinks. This means: break large operations into smaller steps, avoid long-running bash commands, use run_in_background for builds. The agent checks its inbox between each step.

Tradeoff: more tool-call overhead, but more responsive to new messages.

2. Polling between tool calls (cooperative)

Instruct the agent (via CLAUDE.md or system prompt) to check for pending messages between tool calls. The channel server exposes GET /pending — the agent calls it as a lightweight tool between heavier operations.

Tradeoff: depends on agent cooperation. Can't enforce it — the agent might not check if it's deep in a reasoning chain.

3. Out-of-band interrupt (SIGINT)

Send SIGINT to the running tool call, forcing it to abort. Claude Code handles SIGINT by cancelling the current tool and returning to the prompt loop, where it will see queued MCP notifications. The channel server (or a monitor process) sends SIGINT when high-priority messages arrive.

Tradeoff: destructive — current work is lost. Only appropriate for urgent interrupts, not routine messages.

4. Sidecar process (architectural)

Run a lightweight sidecar alongside the Claude session that monitors the message queue independently. The sidecar can: emit ack events to sysbus ("message received, agent busy"), summarize queued messages, trigger fast-respond fallbacks, and SIGINT the agent if escalation thresholds are hit.

The sidecar doesn't need Claude — it's a simple Go/Node process watching the channel's message queue and the agent's tool-call state (from sysbus events).

Tradeoff: most robust but adds a component. However, the channel server is already positioned to do this — it knows both the message queue and the MCP state.

5. Parallel context (future)

Run a second, lightweight Claude session (or a different model) that handles incoming messages while the primary agent is busy. It can triage: "this is urgent, interrupting" vs "this can wait, I'll queue it." Effectively a receptionist in front of the worker.

Tradeoff: cost (two sessions), complexity, context synchronization between the receptionist and the worker. But it's the clean solution for agents that do long-running work.

Recommendation: the channel server sidecar (option 4) is the pragmatic path. It already sits between the bus and MCP. Adding ack emission, lag monitoring, and escalation logic there keeps the agent itself unchanged. The agent doesn't need to know about acks — the channel server handles that layer.

For voice specifically, combine with fast-respond (option 5 from the escalation ladder): if the agent is busy and a voice message arrives, the channel server emits "delivered but stalled" to sysbus, the UI shows progress, and a fast-respond fills the silence after 15 seconds.

The message session manager

The channel server already sits between the bus and the agent. Today it's a dumb pipe — message in, forward to MCP, response out. The idea is to promote it into a stateful session manager that takes custody of the message chain and becomes the authoritative connection to the agent.

The concept

Message Session Manager (lives in channel server) ┌─────────────────────────────┐ │ │ Chatbus ─── seq 1 ──→ │ Message Chain State │ Chatbus ─── seq 2 ──→ │ ┌────┬───────────┬──────┐ │ │ │ seq│ status │ acked│ │ │ │ 1 │ responded │ yes │ │ │ │ 2 │ processing│ yes │ │ ──→ Sysbus (ack events) │ │ 3 │ delivered │ no │ │ │ └────┴───────────┴──────┘ │ │ │ │ Agent Cursor: seq 2 │ │ Head: seq 3 │ │ Lag: 1 │ │ │ └──────────┬──────────────────┘ │ MCP (stdin/stdout) │ ┌────┴────┐ │ Agent │ │ (Claude)│ └─────────┘ │ ack, progress, reply (via tool calls or MCP notifications)

The session manager is the single source of truth for where every message is in its lifecycle. It doesn't just forward — it tracks.

How the agent talks back

The agent needs a way to signal "I'm working on seq N" and "I'm done with seq N." Three options, from simplest to most integrated:

A. Implicit ack via reply

The agent's reply() tool call already goes through the channel server. The session manager intercepts it, extracts which message it's responding to (via ref_seq or conversation position), and marks that seq as responded. No agent changes needed.

Covers: responded state. Doesn't cover: processing state (the gap between delivery and first reply).

B. Explicit ack tool

Give the agent an MCP tool: ack(seq: number, status: "processing" | "done"). The agent calls ack(seq=3, status="processing") when it starts working on a message, and the session manager updates state + emits to sysbus.

This requires agent cooperation (calling the tool) but gives the richest signal. The agent's CLAUDE.md would instruct: "always ack messages before starting work."

C. Inferred from tool activity

The session manager watches sysbus for tool_use events from this agent. If the agent starts calling tools after a message was delivered, infer that it's processing that message. No explicit ack needed — tool activity is the signal.

Covers: processing state (probabilistically). Doesn't cover: which specific message the agent is working on if multiple are queued.

Pragmatic approach: start with A (implicit ack from reply) + C (inferred from tool activity). These require zero agent changes. Add B (explicit ack tool) later when we need precise per-message tracking with multiple queued messages.

Why it lives in the channel server

The channel server is the only component that has both sides of the connection:

  • It receives messages from the chatbus (inbound)
  • It delivers them to Claude via MCP (outbound to agent)
  • It receives replies from Claude via MCP tool calls (inbound from agent)
  • It publishes replies back to the chatbus (outbound)

No other component sees the full picture. The chatbus doesn't know if MCP delivered the message. The agent doesn't know its own lag. The sysbus sees events but can't correlate them to specific messages. The channel server is the natural custody point.

Voice signals that should flow through sysbus

Today, voice state (VAD, STT, TTS) lives entirely inside the browser orchestrator. No other component knows when the user is speaking, when transcription is running, or when audio is playing. For the ack model to work end-to-end with voice, these signals need to be visible:

These are all secondary signals — they describe state, not content. They belong on the sysbus. The actual transcribed text goes through the chatbus as a normal message.

What we're not

It's useful to be explicit about what our system is not, to avoid accidentally building toward a model that doesn't fit.

Not Kafka
Kafka is a distributed commit log with partitioned, replicated, exactly-once-semantics streams and consumer groups. Our JSONL files are single-machine, single-writer, no replication. We don't need Kafka's guarantees — we're doing real-time chat, not event sourcing.
Not S2
S2 is a managed streaming API with sequence-numbered records, fencing tokens, and durable replay. We could use S2 as our log backend, but the interesting thing is its API design: append-only, sequence-numbered, readable by offset or timestamp. Worth studying.
Not a message queue
Queues (RabbitMQ, SQS) dequeue on consume — once consumed, the message is gone. Our messages persist and can be replayed. Closer to the log model than the queue model.

What we are: a lightweight pub/sub fan-out with append-only file persistence, client-side dedup, and timestamp-based replay. Simple enough to reason about, good enough for real-time chat, extensible if we need stronger guarantees later.

Acknowledgment and consumer lag

So far we've talked about messages going to a consumer. But there's a second question: does the consumer tell you it got the message? And if so, what can you do with that information?

The ack

An acknowledgment (ack) is a message back from the consumer saying "I received message N" or "I've processed up to sequence N." It's the consumer's cursor position, reported back to the server.

Without acks, the server is flying blind. It sent the message, but has no idea if the consumer received it, is processing it, or dropped it on the floor. The server can't distinguish "working on it" from "never got it" from "crashed mid-processing."

Implicit ack (cursor advance)
The consumer reports its position: "I've seen up to seq 47." The server infers that everything ≤ 47 was received. This is how Kafka consumer offsets work, and how S2 checkpoints work. Simple, low overhead.
Explicit per-message ack
The consumer acks each message individually: "I processed message with ID X." More granular — handles out-of-order processing — but more traffic. AMQP (RabbitMQ) does this.
No ack (fire and forget)
The server publishes and moves on. This is what we do now. Fast, but the server (and the user) has no visibility into whether the consumer is keeping up.

Consumer lag

Once you have acks, you get consumer lag for free. Lag is the distance between the latest message produced and the last message acknowledged by a consumer:

Server: seq 1 seq 2 seq 3 seq 4 seq 5 seq 6 ↑ ↑ consumer acked server head lag = 6 - 4 = 2 messages behind

This is the same concept as Kafka's consumer group lag, and it's how monitoring tools know when a consumer is falling behind. The sequence number makes lag a simple subtraction.

Why this matters for us

When you send a message to an agent and it doesn't respond for a while, the question is: where is the message? Today we can't answer that. With sequence-based acks, we can show exactly where the message is in the pipeline:

StateWhat it meansHow we know
SentMessage accepted by chatbus, assigned seq NChatbus returns seq in response
DeliveredAgent channel received the messageChannel acks seq N back to bus
ProcessingAgent (Claude) has picked up the messageAgent emits "processing seq N" event
RespondedAgent has repliedReply message references seq N

This is exactly the WhatsApp checkmark model — single check (sent), double check (delivered), blue check (read/processing). The sequence number is the anchor that ties these states together.

Key insight: acks are optional per consumer. The protocol supports them but doesn't require them. A chat UI consumer might never ack (it just displays messages). An agent consumer should ack so we can track lag and detect stalls. The bus stores each consumer's last-acked seq, and lag = head_seq - acked_seq.

Layering voice on top of chat

Voice adds latency at every stage. A text chat message is: type → send → deliver → process → respond. Voice wraps each end with additional steps, each with its own delay budget:

The minimum round trip for voice-to-voice is ~1.5s even with instant agent processing (VAD + STT + TTS + playback). The agent processing time (step 5) is additive on top of that.

Where acks help with voice

Without acks, the voice UI can only show two states: "listening" and "waiting." The user speaks, the UI goes to "waiting," and then... silence until the response arrives. That silence could be 2 seconds or 30 seconds, and the user can't tell if the system is working or broken.

With sequence-based acks, the voice UI can show granular progress:

  • Transcribing... — STT is running (local state, before seq is assigned)
  • Sent — seq assigned, message in the pipeline
  • Delivered — agent has the message (channel acked)
  • Thinking... — agent is processing (processing event received)
  • Speaking... — TTS streaming back

Each transition is driven by an event, not a timer. The user sees progress instead of silence.

The MCP reliability problem

There's a practical wrinkle in our system: the agent's connection to Claude runs over MCP (Model Context Protocol), which uses stdio as its transport. MCP has no built-in ack mechanism — you write a JSON-RPC notification to stdin and hope the other side processes it. There's no delivery receipt, no backpressure signal, no way to know if the message was consumed.

We've hit this repeatedly: messages delivered to the channel server, forwarded over MCP, but Claude doesn't respond — it's mid-tool-call, or the notification was queued behind other MCP traffic, or the stdio buffer backed up. From the bus's perspective, the message was delivered (the channel server accepted it). From the user's perspective, the agent is ignoring them.

This is exactly where acks would help. If the channel server acked "received" but the agent never acked "processing," the bus (and the UI) could show that the message is stuck in the channel — delivered but not picked up. Today that gap is invisible.

MCP limitation: MCP notifications are fire-and-forget by design. To get ack semantics, we'd need the agent to explicitly emit a "processing seq N" event via a tool call or sysbus signal — the ack lives at the application layer, not the transport. This is workable but means ack support depends on agent cooperation, not protocol guarantees.

Perturbing a lagging consumer

Once you can see lag, the next question is: what do you do about it? The agent is behind — messages are piling up. You have several options, each with different tradeoffs:

1. Nudge (re-notify)

Send another MCP notification: "you have N unprocessed messages." This is the gentlest option. It doesn't interrupt the agent's current work, just adds a signal to its attention queue. If the agent is mid-tool-call, the nudge waits in line — but at least when the current turn ends, the agent sees both the original message and the nudge.

When to use: lag is 1–3 messages, agent is probably just busy.

2. Summarize and collapse

If the queue has grown (e.g., 5+ unprocessed messages), don't deliver them all — summarize. "You have 5 pending messages. Most recent: [last message]. Summary: [LLM summary of the batch]." This prevents the agent from burning context on stale intermediate messages.

When to use: lag is large, older messages may be superseded by newer ones.

3. Priority interrupt

Inject a high-priority signal that breaks the agent's current turn. In Claude Code, this could be a SIGINT to the current tool call, or a special MCP notification type that the agent is instructed to check between steps. The agent abandons its current work and processes the new message.

When to use: user explicitly wants attention now (barge-in, urgent command). Destructive — current work may be lost.

4. Timeout and escalate

If lag exceeds a threshold (e.g., 60 seconds with no ack), the bus marks the consumer as stalled and takes action: restart the agent session, route to a different agent, or notify the user that the agent is unresponsive. This is the circuit breaker pattern applied to consumers.

When to use: agent is genuinely stuck (crashed, infinite loop, MCP deadlock).

5. Drop and fast-respond

Skip the lagging agent entirely. Route the message to a fast-respond path (lightweight model, cached response, or acknowledgment-only) so the user gets something back immediately. The original message stays in the queue for the agent to process later, but the user isn't left in silence.

When to use: voice context where any silence >2–3 seconds feels broken. The fast-respond is a bridge, not a replacement.

The escalation ladder: these options aren't mutually exclusive — they form an escalation sequence based on lag duration:

  • 0–5s: Normal. Show "thinking..." in UI.
  • 5–15s: Nudge. Re-notify the agent.
  • 15–30s: Fast-respond. Give the user a holding response.
  • 30–60s: Summarize. Collapse the queue if multiple messages pending.
  • >60s: Escalate. Circuit breaker — restart or reroute.

The sequence number makes all of this possible. Without it, you don't know how far behind the agent is, and every option above is a guess.

The barge-in problem

Voice has an additional complication: the user can interrupt mid-response (barge-in). This means the consumer lag model has to handle cancellation — "stop processing seq N, I'm sending a new message." The sequence number makes this clean: "cancel everything after seq N, here's seq N+1."

Open questions

Ring buffer vs. unbounded log?
The ring drops old messages. Should we keep everything on disk and only use the ring for fast lookups? Or is the bounded ring the right tradeoff for our scale?
Stronger delivery guarantee for work dispatch?
Chat is fine at-most-once, but a lost work message means a task silently doesn't happen. Should the bus have a separate "confirmed delivery" path for work items (at-least-once with retry until acked)?
What's the right replay window?
We currently fall back to "last 10 messages." Is 10 right? Time-based (last 5 minutes)? Different per context (mobile vs desktop)? Should the client choose?
Consumer groups / fan-out?
Every connected client gets every message for its agent. If we add notification services, logging services, or other consumers that each need to process once, we need fan-out routing.
S2 as a backend?
Replace JSONL with S2 streams — we'd get sequence numbers, durable replay, and a clean API for free. But it's a dependency and a cost. Is the JSONL approach hitting limits?
