Agent Task Management

A unified system for dispatching, tracking, and observing agent work across distributed hosts.

2026-10-22 · Docs Index

TL;DR

We need a lightweight task dashboard that shows what is running, where it's running, and how it's doing — across the supervisor, teammates (worktree agents), hosted shrooms, and potentially remote boxes. Inspired by Graham's "trove" pattern: simple custom UI, launch agents from the sidebar, see live status. The key insight is that visibility into running work is more valuable than sophisticated scheduling.

The Problem

Right now we have several disconnected systems for tracking agent work:

  • TASKS.md — a flat text file, manually maintained, no live status
  • data/attention.md — transient work state, easily stale
  • Scheduler — manages agent wake/sleep but doesn't expose task-level state
  • Bus-follower — classifies tasks from message history, but runs every 30 minutes and misses ~60% of tasks
  • Sysbus activity feed — shows tool calls and lifecycle events, but not task-level progress
  • GitHub issues/PRs — durable but disconnected from live execution state

When the supervisor dispatches work to teammates via worktrees, or a shroom picks up a bus message, or an agent wakes on another box — there is no unified view of what's happening. The user has to ask "what's the status?" and the supervisor has to manually check worktrees, PRs, and bus messages to assemble an answer.

What Graham's Trove Gets Right

The trove pattern is compelling because it prioritizes visibility over sophistication:

  1. Sidebar shows running agents — you can see at a glance what's active, what's idle, what's stuck
  2. Launch from UI — click to start an agent with a task, no terminal required
  3. Simple custom UI — not a general-purpose project management tool, purpose-built for the agent workflow
  4. Notes alongside agents — context travels with the work, not buried in chat history

The trove is a workbench, not a task board. It answers "what is this system doing right now?" rather than "what should it do next?"

Our Version: The Dispatch Board

A live sidebar panel showing all active work units across all execution contexts.

What's a Work Unit?

A work unit is anything that was dispatched and is expected to complete. Each has a type, a location, and a status:

TypeWhere it runsHow we know it's done
TeammateGit worktree (local)Agent exits, PR created
Background taskLocal subprocessProcess exits
Shroom jobDocker containerBus message: result published
Agent sessionMCP channel (local or remote)Session ends or goes idle
Remote agentAnother boxHeartbeat stops or result published
EAS buildExpo cloudBuild status API / webhook
GitHub ActionGitHubCheck run status API

Data Model

Each work unit is a small record, stored in a single place (not scattered across files):

{
  id:          "work_1792701742",
  type:        "teammate",
  title:       "Fix #243: mute TTS bug",
  branch:      "auto/fix-243-mute-tts",
  host:        "local",              // or "remote-box-1", "expo-cloud"
  agent:       "implementer",        // who's doing it
  dispatched:  "2026-10-22T14:30:00Z",
  status:      "running",            // pending | running | done | failed | stale
  last_signal: "2026-10-22T14:35:12Z",
  result:      null,                 // PR URL, commit hash, error message
  context:     "Fix mute button wiring in voice-react.tsx"
}

Status Lifecycle

pending ──dispatch──▶ running ──complete──▶ done │ │ ├──timeout──▶ stale │ └──error───▶ failed

Stale detection: If last_signal is older than stale_timeout (default: 15 minutes for teammates, 30 for shrooms), the unit is marked stale. This catches hung processes, crashed agents, and forgotten worktrees.

Architecture

How it works now

Supervisor dispatches via bus or worktree. Checks status manually when asked. No live view. Teammate results discovered by polling PRs or reading worktree output.

Proposed

Dispatch board as a sysbus consumer. Work units emit heartbeats/signals to sysbus. Board aggregates into a single view. UI sidebar shows live state. Click to inspect, retry, or kill.

Signal Flow

Supervisor ──dispatch──▶ Sysbus ──event──▶ Board UI ▲ Teammate ──heartbeat──┘ │ Shroom ──result─────┘ │ Remote Box ──heartbeat──┘ │ EAS/GitHub ──poll───────┘ ▼ Sidebar Panel

The dispatch board is a read model built from sysbus events. It doesn't own execution — it observes it. This means:

  • No new infrastructure required for the core feature
  • Sysbus already carries lifecycle signals (dispatch, build, deploy, session events)
  • We just need agents to emit signals, and a UI to consume them

Interactions

  • Click a work unit — expand to show: last heartbeat, branch, commit log, PR link, agent output tail
  • Dispatch button — open a form: select agent type, describe task, pick branch name. Supervisor creates the work unit and dispatches.
  • Kill / Retry — for stale or failed units, offer to kill the process or re-dispatch
  • Auto-collapse done items — after 10 minutes, done items move to a "Recent" section

Distributed: Remote Boxes

When agents run on different machines (e.g., a beefy GPU box for inference, a CI runner for builds), we need cross-host visibility. Two approaches:

Option A: Sysbus Bridge (Recommended)

Each remote box runs a lightweight agent that forwards local sysbus events to the central sysbus. The dispatch board doesn't need to know about networking — it just sees events with different host fields.

# Remote box agent — forward events to central sysbus
while read event; do
  curl -sf -X POST $CENTRAL_SYSBUS/events \
    -H 'Content-Type: application/json' \
    -d "{\"host\":\"$HOSTNAME\", ...}" 2>/dev/null || true
done

Option B: Pull-Based Discovery

Central sysbus polls remote boxes for their work state. Simpler for the remote side (just expose a /status endpoint) but adds latency and requires the central system to know about all boxes.

Recommendation: Option A. Push-based means the board updates in real-time, and adding a new box just means running the bridge agent on it. No central configuration needed.

Teammates

Worktree teammates are the most common work unit today. They need the lightest-weight integration:

  1. On dispatch: Supervisor emits work:dispatched with branch, title, agent type
  2. During execution: The mailman coordinator already monitors worktree output. Add periodic sysbus heartbeat (every 60s) with: current file being edited, test results, progress estimate
  3. On completion: Emit work:done with PR URL or commit hash
  4. On failure: Emit work:failed with error summary

The teammate doesn't need to know about the dispatch board. The supervisor (or mailman coordinator) handles all signaling. The teammate just does its work.

Implementation Plan

Phase 1: Local visibility (no new services)

  1. Define WorkUnit type in shared/core/
  2. Extend sysbus event types: work:dispatched, work:heartbeat, work:done, work:failed
  3. Build dispatch board tile (React, same pattern as mobile-sim-react.tsx)
  4. Wire supervisor dispatch to emit work events
  5. Add stale detection (timer-based, client-side)

Phase 2: Shroom and external integration

  1. Bus-follower relays shroom results to sysbus as work events
  2. Cron-based EAS/GitHub status polling, publish as work:external
  3. Builder shroom emits work signals directly

Phase 3: Distributed

  1. Sysbus bridge agent for remote boxes
  2. Host field in work units, filter/group by host in UI
  3. Remote agent discovery (registry-based or mDNS)

Phase 4: Launch from UI

  1. Dispatch form in sidebar: task description, agent type, branch
  2. POST to admin API, which creates branch + dispatches via bus
  3. Template library: common task types (fix issue, write doc, research)

What We Don't Need

Explicit non-goals, to keep this from becoming a project management tool:

  • No task dependencies or DAGs. If work has dependencies, the supervisor sequences it. The board just shows what's running.
  • No priority queues. The supervisor decides what to dispatch and when. The board is a mirror, not a scheduler.
  • No user assignment. Work is dispatched to agent types, not people. The registry maps types to implementations.
  • No Gantt charts or timelines. We care about "is it running?" and "is it done?", not "when will it finish?"
  • No persistence beyond the session. Done work items are ephemeral in the board. Durable records live in git (commits, PRs) and GitHub issues. The board is a live view, not a database.

Open Questions

  • Heartbeat frequency vs. sysbus load. 60s heartbeats from 4 teammates = 4 events/min. Fine for now. At 20+ agents, consider aggregation.
  • Teammate output tailing. Should the board show live output from worktree agents? Useful but potentially noisy. Maybe on-demand (click to expand).
  • Remote auth. Sysbus bridge from remote boxes needs authentication. Mutual TLS? Shared secret? Depends on network topology.
  • Mobile view. The sidebar works on desktop. On mobile, maybe a floating badge with count of active items, tap to expand.
