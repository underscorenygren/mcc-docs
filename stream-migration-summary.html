Stream Migration Summary

Design decisions, general patterns, and what changed.

2026-11-03 — PRs #254 and #256, plus post-merge cleanup.

1. What happened

We replaced the ad-hoc event plumbing and raw WebSocket management with a layered messaging library. The library became the structural convention for how the app is organized — not just a utility, but the pattern that new code should follow.

Two PRs landed the core change. Post-merge work simplified the UI (stripped to two tabs), fixed mobile voice bugs, and cleaned the repo.

2. Design patterns

These are the general principles that drove the migration. They apply beyond the stream library itself — they are the conventions we want enforced going forward.

2a. Encapsulate, don't inline

Raw protocol details (WebSocket construction, JSON parsing, reconnect timers) should not appear in application code. Wrap them behind an abstraction that hides the mechanism and exposes intent.

Before: every connection class had its own new WebSocket(url), its own onopen/onclose/onmessage wiring, its own reconnect timer. Three files, three slightly different implementations of the same thing.

After: a transport abstraction owns the connection lifecycle. Application code says "open", "send", "on message" without knowing it's a WebSocket underneath. The reconnect logic is composed on top, not duplicated inside.

The same principle applies to the event bus: application code calls emit/on without knowing whether the backing store is an array, a stream, or a ring buffer. The implementation can change without touching consumers.

"We should start using the stream library as our convention for how the app is structured, and then take this opportunity to restructure our changes according to that pattern, reinforce that rule set." — design direction, 2026-11-04

2b. One code path, regardless of source

When the same kind of data arrives from different origins (live vs. historic messages, UI button vs. deep-link trigger, web vs. mobile), it should flow through the same code path. No branching on "where did this come from."

Example — chat messages: historic messages replayed on page load and live messages arriving in real time should both enter the component the same way. The component renders messages; it does not care whether they are new or old.

Example — recording sounds: pressing the record button and triggering recording via the iOS Shortcut should both play the same mic-on/mic-off sounds. The trigger mechanism is different; the behavior must be identical.

"We don't want any special handling with these new messages. We want the same simple code path for loading new messages in this component, regardless if they are new or historic." — on chat history loading, 2026-11-04
"For the trigger button, when the recording stops, you don't play the down-tempo sound. It only seems to work when we hit press record, so that needs to be consistent." — on recording sound inconsistency, 2026-11-04

2c. Simplify aggressively

When rebuilding, don't carry forward everything that existed before. Strip to what's actually used, move the rest out of the active code path. If something worked in the past but isn't part of the current product, it belongs in the attic — visible for reference, but clearly separated so it doesn't confuse.

The supervisor page went from 7+ tabs to 2 (Agent + Memo). 30+ tile components moved to attic/. The mobile screen lost its ambient sound selector. Eight top-level directories moved to attic.

"These are things that have worked in the past that we are no longer using. They need to be a separate part of our codebase, clearly labeled so we don't get confused, so we don't refer to it." — on the attic pattern, 2026-11-04

2d. Cross-platform consistency

Web and mobile should behave identically for the same action. Same sounds, same voice behavior, same connection lifecycle. The shared core (shared/) exists to enforce this — platform-specific code should be a thin shell over shared logic.

When mobile had a barge-in bug (TTS kept playing while the user was speaking), the fix went into the shared voice controller, not into mobile-specific code. The principle: if it's wrong on one platform, it's wrong on both.

"I am talking and I see listening, and the agent is still speaking over me." — reporting the mobile barge-in bug, 2026-11-04
"We want to, if we can, take this opportunity to restructure the mobile app according to the stream library patterns." — on mobile restructuring, 2026-11-04

2e. Background reliability

The mobile app must work reliably across app lifecycle transitions — foreground, background, sleep, resume. Connection loss is expected (iOS kills WebSockets after ~30s in background); what matters is that reconnection is automatic and the user has audible feedback when state changes.

"The most important thing from here is the ability to carry the phone in the background and still have a methodology that we know works, that is able to keep the connection to the agent." — on mobile background behavior, 2026-11-04

3. What changed

Stream library (PR #254)

New layered messaging library at shared/lib/stream/. Transports (WebSocket, HTTP, in-memory), codecs (JSON, binary), envelopes, ring buffers, dedup, replay, and a compatibility adapter that provides the same on/emit API the app already used. 50+ files, 116 tests.

Migration (PR #256)

Swapped the old event bus for the stream-backed bus. Wrapped all WebSocket connections with stream transports. Added monotonic sequence numbers to the Go chatbus for cursor-based replay. 20 files changed.

Post-merge cleanup

  • Chat history fix — fresh page loads were using a stale timestamp, getting 0 messages. Fixed by distinguishing first load (get last N) from reconnect (get since timestamp).
  • Mobile barge-in fix — TTS now cancels immediately when the user starts recording, instead of waiting for VAD detection (unreliable on mobile due to speaker-to-mic bleed).
  • Trigger sound consistency — deep-link toggle actions now play the same mic-on/mic-off sounds as the UI buttons.
  • UI simplification — supervisor stripped to Agent + Memo tabs. 30+ retired tiles moved to attic/.
  • Repo cleanup — 8 obsolete directories moved to attic. README written with full entrypoint map.
  • EAS optimization — .easignore updated to exclude worktrees and attic (873 MB → ~100 MB).

5. Rules to enforce

General rules derived from the patterns above, suitable for automated review or skill-based enforcement.

Encapsulate protocol details

Flag raw WebSocket construction, manual reconnect timers, or inline JSON.parse/stringify in application code. These should go through an abstraction layer.

Uniform code paths

Flag branching on message origin (historic vs live, trigger vs button, web vs mobile). If the same kind of data takes different paths depending on how it arrived, that's a design smell.

Shared core for cross-platform behavior

Flag platform-specific logic that duplicates shared core behavior. Voice, chat, and connection logic should live in shared/. Platform code should be a thin adapter.

Consistent audible feedback

Every recording start/stop path must play the corresponding sound. Every connection state change on mobile must be audible. No silent transitions.

Aggressive cleanup

When code is replaced, move the old version to attic/ in the same PR. Don't leave dead code in the active tree "for reference." The attic is the reference.
