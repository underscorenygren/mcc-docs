Message-to-Spore Classifier

Design doc — classify chatbus messages as new spores, existing spore updates, commands, or noise.

Version 1 — 2026-11-18

TL;DR

A bus-follower shroom watches chatbus messages in real time and classifies each one as: new spore, existing spore update, system command, or noise. A procedural pre-filter handles 60–80% of messages without an LLM call. The remaining ambiguous messages go to a lightweight LLM classifier with a compressed spore index as context. The system runs as a Go service subscribing to the chatbus, same pattern as the existing bus-follower.

The spore-classifier is a new Go service, same pattern as cmd/bus-follower. It subscribes to the chatbus via busclient.Subscribe(), processes each message through the classification pipeline, and writes results to the spore system via the spore-query.js CLI.

Classification Taxonomy

Label Description Action Example
new_entity Message introduces a genuinely new idea, task, or project with no existing spore Create new spore “We should build a Slack bot”
existing_spore Message relates to an already-tracked spore Update spore (add source, state, outcome) “The voice WS fix is deployed”
command System command, not work-related Ignore (handled by other systems) “!status”, “!push”
noise Chitchat, acknowledgments, greetings, ambient transcription Ignore “ok”, “sounds good”

Sub-classifications

For existing_spore: returns spore_id (e.g., MCC-7) and update_type (status_change, new_info, decision, outcome, reference).

For new_entity: returns suggested_title, suggested_seed, suggested_state, and confidence (0.0–1.0). Entities with confidence < 0.7 are flagged for human review.

Stage 1: Procedural Pre-Filter

Pre-filter — zero LLM cost

Runs synchronously on every message. Handles the obvious cases:

  • Source filtering: Skip outbound (supervisor replies, bot messages)
  • Command detection: /^![\w]+/ → command
  • Noise detection: Short messages matching ack patterns (<10 chars, “ok”, “sure”, “thanks”)
  • Explicit spore ID: /MCC-\d+(\.\d+)?/ → existing_spore with extracted ID
  • Context window: Follow-ups within 60s of a classified message inherit that spore
  • New entity keywords: “we should”, “let’s build”, “new idea” → fast-track to LLM with bias hint

Stage 2: LLM Classifier

LLM Classifier — ambiguous messages only

For the ~28% of messages that survive the pre-filter, call an LLM with a compressed spore index.

Spore index compression

Full active.json is ~56k chars (~14k tokens). Instead, build a compressed index:

  • Tier 1 — Active spore summary (~640 tokens): Non-done spores with id, title, seed, state only
  • Tier 2 — Seed list (~100 tokens): All seed slugs with one-line descriptions
  • Tier 3 — Recently mentioned spores (~200 tokens): Last 10 spore IDs with full descriptions

Total context: ~1,000 tokens per call. Scales to ~200 spores before needing further compression.

Prompt template

SYSTEM:
You classify chat messages for a software project's work tracking system.

Given a message and the current tracked items (spores), classify as one of:
- new_entity: genuinely new idea/task/bug not covered by any existing spore
- existing_spore: relates to an existing spore (provide the spore ID)
- noise: not work-related (greetings, acknowledgments, ambient audio)
- command: a system command

Output STRICT JSON only.

Schema:
{"label": "new_entity"|"existing_spore"|"noise"|"command",

Rules:
- Prefer existing_spore over new_entity.
- Short follow-ups are noise if no clear spore context.
- When uncertain, choose existing_spore with closest match, confidence < 0.5.

Stage 3: Iterative Refinement

Feedback loop
  • Corrections log: When supervisor manually creates a spore the classifier missed, log the correction
  • Periodic review: If patterns emerge in corrections, add keywords to pre-filter
  • Prompt tuning: Include 3–5 recent corrections as few-shot examples
  • Confidence calibration: Track predicted confidence vs actual correctness

Anti-duplication

  1. Title similarity: Fuzzy match against all active spore titles. Similarity > 0.7 → flag for review
  2. Seed scope: Cross-seed dedup — “fix the websocket” might match MCC-7 even without mentioning voice-bridge
  3. Cooldown: After creating a new spore, suppress new_entity for the same seed for 60 seconds

Error Cost Analysis

Error typeCostTarget rateMitigation
False positive (duplicate spore) Clutter, manual cleanup < 5% Title similarity, confidence threshold, cooldown
False negative (missed idea) Lost idea unless user says “spore this” < 10% Bias toward existing_spore over noise

Duplicates are cheaper to fix than lost ideas, but erode trust. Balance: auto-create only at confidence > 0.7, otherwise queue for human review.

Open Questions

  1. Auto-create vs queue-for-review: Should the classifier ever auto-create spores, or always queue for human confirmation?
  2. Update granularity: Adding sources is safe. Changing state (“it’s deployed” → done) is riskier. Limit to source additions initially?
  3. Multi-message batching: Process one-at-a-time (simpler, low volume) or batch?
  4. Voice transcription quality: Garbled voice messages (“Emmy-see-see seven” = MCC-7) need lenient matching.
  5. Conversation threading: Chatbus has no threading. Context window is a heuristic proxy.
