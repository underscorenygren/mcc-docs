Message Mechanics: Reactions & Decisions

Companion to Message Mechanics. My takes on what we keep, what we change, and what needs more thought.

Last updated: 2026-10-17

Message IDs

Keep
Client-generated IDs with type prefixes

The chat_ / reply_ / msg_ prefix convention works. It's simple, debuggable (you can tell what generated a message by looking at the ID), and the timestamp component gives rough ordering without coordination.

Change
Eliminate hist_ IDs entirely — subsumed by sequence numbers

The hist_ fallback IDs were a symptom of not having a proper replay cursor. With server sequence numbers, replay returns original messages with original IDs. No generated fallback IDs, no dedup mismatch. Issue #222 goes away as a side effect.

Change
Add server-assigned sequence numbers — dual ID model

Decision (2026-10-16): Move to the industry-standard dual ID model:

  • Client ID (chat_xxx) — owned by the sender, used for retry idempotency. Chatbus dedup cache uses this to suppress duplicate sends.
  • Server sequence number — assigned by chatbus on receipt, per-agent monotonic counter. This becomes the canonical ordering and replay cursor.

This is how WhatsApp, Discord, and S2 work. Replay becomes "give me everything after sequence 47" (gapless) instead of "after this timestamp" (lossy). Eliminates the hist_ problem entirely — original IDs survive because there's no reason to generate new ones.

Implementation: atomic counter per agent in chatbus, persisted alongside JSONL log. Each log entry gets a seq field. Client subscribe sends { since_seq: N } instead of timestamp.

Ordering

Keep
Per-agent ordering (not global)

We don't need total ordering across agents. Each agent conversation is independent. Per-agent JSONL log gives us what we need.

Change
Unbounded log with archival — no hard ring buffer cap

Decision (2026-10-17): Don't hard-cap the message log. Let it grow unbounded, with a cron task monitoring disk usage to warn before we run out. Messages older than ~2 weeks are low value — archive them to a cheap storage layer (compressed files, cold storage) rather than dropping them.

Partial bound: recent messages stay hot and fast, old messages move to cold archive. This gives us the safety of a cap without data loss.

Delivery guarantees

Keep
At-most-once for chat

Chat messages don't need exactly-once. The two-layer dedup (server TTL + client seenIds) is good enough. Adding ack/retry machinery would complicate everything for minimal gain.

Change
Akka-style work dispatch — sender-side reliability, not message-layer

Decision (2026-10-17): Don't solve work dispatch reliability in the message layer. Keep delivery guarantees weak (at-most-once is fine for the transport). Instead, build reliability at the supervisor/worker level:

  • Workers ACK receipt via heartbeat/sysbus-style signals
  • Supervisor monitors ACKs — if a worker stalls or crashes, it re-issues the work
  • Inspired by Akka's "let it crash" model: supervisors own retry logic, not the message bus

This keeps the stream library simple (no exactly-once, no persistent queues at the transport level) and puts recovery logic where it has the most context — the sender.

Connections & reconnection

Keep
Cursor-based reconnect with timestamp

The since + last: N fallback pattern is solid. Handles both reconnect (delta) and page reload (last N) cleanly.

Keep
Current replay window (last 50) is fine for now

With unbounded storage and archival, the replay window is just about what to show on reconnect. Last 50 messages covers a session. Sequence-based replay (#222) makes this precise. No need to over-engineer yet.

Add
Interruption context: deliver last two messages on agent interrupt

When a user interrupts an agent mid-work, the agent's new context should include the last two messages: the one that was interrupted plus the new interrupting message. This gives the agent enough context to understand what was happening and what the user now wants, without replaying the entire conversation.

Without this, an interrupted agent only sees the new message and loses the thread of what it was doing. The interrupted message may contain partial results or in-progress status that informs the next action.

Architecture

Change
Unify sockets, buses, chat into one layered stream library

Decision (2026-10-16): Instead of separate ChatTransport, BusTransport, etc., build a single typed stream library with layers. One core abstraction that handles chat, voice, multi-agent, and events — with typed messages at each layer.

Today we have: WebSocket (bridge), HTTP pub/sub (chatbus), WebSocket (sysbus), and MCP (agent channels) — four different connection types with overlapping concerns. The goal is one stream primitive with layers for transport, framing, typing, and semantics.

Informed by S2's model (append-only, sequence-numbered, typed records) but implemented as our own library, not a dependency.

Change
Message session manager in channel server

Decision (2026-10-16): Promote the channel server from dumb pipe to stateful session manager. It takes custody of the message chain per agent, tracks per-message state (sent/delivered/processing/responded), maintains the agent cursor, computes lag, emits acks to sysbus, and runs escalation logic.

Exposes /agent/{name}/chain HTTP endpoint for state reflection. Start with implicit acks (from reply) + inferred acks (from tool activity). Add explicit ack() tool later.

Change
Not S2 — self-hosted Redis Streams as the message backbone

Decision (2026-10-17): Instead of S2 (external dependency, cost) or building our own pub/sub from scratch, self-host Redis and use Redis Streams. We have very low volume — a single Redis instance is more than enough.

Redis Streams gives us: consumer groups for fan-out, built-in ordering, persistence, ACK/NACK, and mature TS client libraries (ioredis). This replaces the chatbus HTTP pub/sub entirely, letting us focus on L3-L5 (protocol, routing, business logic) instead of reinventing the transport.

Research pass (#238) will evaluate Redis Streams alongside pure-TS libraries to confirm this is the right call.

Change
Consumer groups via Redis Streams — fan-out solved

Decision (2026-10-17): Redis Streams consumer groups handle this natively. Each consumer (notification service, logger, UI client) gets its own consumer group with independent read cursors and ACKs. No custom fan-out code needed.

Implementation stack

Change
Consider moving to TypeScript-only — drop Go

Decision (2026-10-17): Evaluate moving away from Go entirely. If we're building the stream library in TS and reimplementing both sides of the pipe, Go doesn't provide unique value. TS everywhere (web, mobile, server) simplifies the stack, shares types, and reduces cognitive overhead.

This is a decision to evaluate, not a done deal. #239 tracks the tradeoffs. Must be resolved before starting stream library implementation.

Change
Replace chatbus HTTP pub/sub

Decision (2026-10-17): The current chatbus uses HTTP POST for publish and HTTP fetch for subscribe. This is legacy from early prototyping — there's no strong reason for HTTP over WebSocket or a proper message broker.

HTTP pub/sub adds latency, requires polling, and can't push. Redis Streams (or whatever the research picks) should replace this entirely. The constraint to check: if there was a reason for HTTP (firewall traversal, proxy compatibility), note it so we don't lose it in the rewrite.
