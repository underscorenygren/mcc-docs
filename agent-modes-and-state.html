Agent Architecture: Dispatch Board Task Orchestration Modes & State

Agent Behavioral Modes & State Machines

Formalizing agent behavior: three rule mechanisms, two kinds of state machine, and a hybrid model where software enforces transitions while the agent handles judgment.

November 2026 — Agent Architecture series

TL;DR

Three mechanisms encode agent rules: CLAUDE.md instructions (cheap, skippable), hooks (mechanical, limited to tool events), and skills with preconditions (composable, testable). "Agent state machines" with fuzzy transitions are just prompting with extra words. The useful architecture is a hybrid: a software state machine enforces deterministic transitions between modes, while the agent exercises judgment within each mode. The enforcement mechanism is tool restriction — each mode exposes a different tool set, preventing the agent from taking actions outside its current role.

1. The Problem

Agents drift. Without formalization, an agent tasked with "review this PR" may start editing files, deploy changes, or wander into unrelated codebases. The behavior is probabilistic — sometimes the agent follows instructions precisely, sometimes it interprets them creatively under context pressure.

Specific failure modes observed in production:

  • Validation skipped. Agent completes a task, marks it done, never checks if the deployment actually works.
  • Mode blur. Agent brainstorming an approach starts writing code mid-discussion, before the plan is agreed.
  • Stale task drift. Agent picks up a stale task from context and re-executes it, even though it was completed hours ago.
  • Self-managed transitions. Agent decides on its own when to move from planning to execution, sometimes prematurely.

The common thread: the agent manages its own state transitions. It decides when to shift from one behavioral mode to another. This is the root cause. An agent that controls its own mode switches will eventually switch at the wrong time.

2. Three Rule Mechanisms

There are three ways to encode behavioral rules for a Claude Code agent. Each has a different enforcement strength and a different cost to iterate.

Mechanism Enforcement Scope Iteration Cost Failure Mode
CLAUDE.md rules Advisory (LLM follows or ignores) All behavior Edit a text file Ignored under context pressure
Hooks Mechanical (shell command fires) Tool-call events only Write a shell script Can only react to tool calls, not semantic events
Skills with preconditions Structural (skill chains enforce order) Composable operations Define skill + precondition graph Agent can bypass by not invoking the skill

CLAUDE.md Rules

Plain text instructions injected into the system prompt. The agent reads them at session start and (ideally) follows them throughout. 

# Example: validation rule in CLAUDE.md
## Post-deploy validation
After every deploy, run these checks before reporting success:
1. curl the health endpoint
2. Check nginx logs for 404s
3. Verify the page loads

Strengths

  • Zero infrastructure — edit a file, restart the session
  • Covers any behavioral aspect: tone, workflow, priorities, restrictions
  • Human-readable — serves as documentation and instruction simultaneously

Weaknesses

  • No enforcement — the agent can skip rules when the context window is full or the task is urgent
  • Degradation over distance — rules near the top of context are followed more reliably than rules buried deep
  • No feedback loop — you only discover a rule was skipped after the damage is done

Hooks

Shell commands that fire automatically on specific events: before a commit, after a tool call, on session start. Claude Code supports hooks via .claude/hooks/. 

# Example: pre-commit hook that blocks deploy from non-main branches
#!/bin/bash
BRANCH=$(git rev-parse --abbrev-ref HEAD)
if [[ "$BRANCH" != "main" ]] && git diff --cached --name-only | grep -q "deploy/"; then
  echo "ERROR: deploy/ changes only allowed on main"
  exit 1
fi

Strengths

  • Mechanical enforcement — the hook runs regardless of what the agent thinks
  • Deterministic — same event always triggers same check
  • Can block actions (non-zero exit code prevents the tool call from completing)

Weaknesses

  • Limited trigger surface — hooks fire on tool-call events (bash, write, commit), not on semantic events ("agent started planning" or "user approved the task")
  • No LLM judgment — hooks are binary pass/fail, cannot make nuanced decisions
  • Workaround risk — the agent may find alternative tool calls that avoid the hook

Skills with Preconditions

A skill is a composable, documented operation the agent can invoke. Skills can declare preconditions — other skills that must run first. This creates enforceable chains. 

# Example: deploy skill requires validate skill
skill: deploy
preconditions:
  - validate   # must pass before deploy can proceed
steps:
  - docker compose build ${service}
  - docker compose up -d --force-recreate ${service}
  - curl health endpoint

skill: validate
steps:
  - run test suite
  - check for uncommitted changes
  - verify branch is main

Strengths

  • Composable — skills chain into workflows without hardcoding sequences
  • Testable — each skill is a unit that can be verified independently
  • Self-documenting — the skill definition describes what it does and what it requires

Weaknesses

  • Agent must invoke the skill — nothing prevents the agent from running the deploy steps directly without calling the skill
  • Requires infrastructure to define, register, and enforce preconditions
  • Precondition evaluation is still LLM-mediated unless backed by a software check

Mechanism Comparison

Enforcement strength: CLAUDE.md rules ░░░░░░░░░░░░░░░░░░░░ Advisory Skills + preconditions ████████░░░░░░░░░░░░ Structural Hooks ████████████████░░░░ Mechanical Coverage breadth: CLAUDE.md rules ████████████████████ Everything Skills + preconditions ████████████░░░░░░░░ Defined operations Hooks ████░░░░░░░░░░░░░░░░ Tool-call events only

No single mechanism is sufficient. The strongest enforcement (hooks) has the narrowest scope. The broadest scope (CLAUDE.md) has the weakest enforcement. A robust system layers all three.

3. Software vs Agent State Machines

"State machine" gets applied to two fundamentally different things in agent systems. Conflating them leads to architectural confusion.

Software State Machines

Deterministic. Runs in code. Transitions are triggered by observable events: bus messages, tool-call completions, API responses, timers. The state machine does not decide whether to transition — it transitions when the event fires.

States: idle ──▶ building ──▶ testing ──▶ deploying ──▶ validating ──▶ done │ │ │ │ ▼ ▼ ▼ ▼ build_failed test_failed deploy_failed validation_failed │ │ │ │ └────────────┴──────────────┴───────────────┘ │ retry (max 3) ──▶ escalate Trigger: bus message "build/done" fires transition building → testing No judgment involved. Event arrives, state changes.

Properties: fast (microseconds), cheap (no LLM), predictable (same input always produces same transition), auditable (state transitions are logged).

Agent State Machines

Often proposed in agent framework docs: "the agent is in the planning state, then transitions to execution." But how does the transition happen? The LLM decides it has finished planning. The transition is probabilistic, not deterministic.

Proposed: planning ──"I'm done planning"──▶ execution Reality: planning ──(LLM thinks it's done)──▶ execution │ (but is it really done?) │ (depends on context window, prompt position, temperature, how many tokens remain...)

If transitions are fuzzy, it is not a state machine. It is prompting with extra vocabulary. Calling it a "state machine" imports expectations of determinism that do not hold. The agent may skip states, revisit states, or invent states that were not in the design.

When Each Applies

Dimension Software SM Agent SM
Transitions Deterministic, event-triggered Probabilistic, LLM-decided
Speed Microseconds Seconds (LLM inference)
Cost Zero (runs in code) API call per transition decision
Predictability 100% given same event Varies with context, prompt, model version
Best for Lifecycle management, retry logic, build pipelines, mode switching Within-state reasoning, tool selection, response generation
Failure mode Bug in transition logic (fixable) Drift, skipped states, invented states (hard to detect)

4. The Hybrid Model

The resolution: software enforces transitions, agent handles judgment within states.

Don't trust the agent to manage its own state transitions. Don't trust the software to make nuanced decisions within a state. Each does what it is good at.

┌──────────────────────────────────────────────────────────────┐ │ Software State Machine │ │ │ │ brainstorm ──event──▶ execution ──event──▶ validation ──event──▶ done │ │ │ │ │ │ │ ▼ ▼ ▼ │ │ ┌────────┐ ┌────────┐ ┌────────┐ │ │ │ Agent │ │ Agent │ │ Agent │ │ │ │ reads, │ │ edits, │ │ checks │ │ │ │ thinks,│ │ builds,│ │ tests, │ │ │ │ chats │ │ deploys│ │ verifies│ │ │ └────────┘ └────────┘ └────────┘ │ │ │ │ Transitions: bus messages, tool completions, chat commands │ │ Within-state: agent judgment, LLM reasoning, tool selection │ └──────────────────────────────────────────────────────────────┘

This maps directly to the reactive tailer (software SM) + planner (agent judgment) architecture from the Task Orchestration research. The tailer detects events and drives transitions. The agent operates within the boundaries the current state allows.

Key Principle: Observable Events as Transition Triggers

Transitions must be triggered by events the software can observe mechanically:

  • Bus messages: build/done, deploy/done, dispatch/confirmed
  • Tool-call completions: agent called git commit, agent called docker compose up
  • Chat commands: user says !approve, !validate, !brainstorm
  • Timers: 30 seconds without activity, build timeout reached
  • External API state: GitHub PR merged, CI check passed

The agent does not choose when to leave a state. The software detects the condition and switches the mode. The agent operates within the new mode's constraints.

5. Mode Controller Design

The enforcement mechanism for the hybrid model is tool restriction. Each behavioral mode exposes a different set of tools. The agent physically cannot take actions outside its current mode because the tools are not available.

Example Modes

Brainstorm Mode

Purpose: Explore ideas, read code, discuss approaches. No changes to the codebase.

Allowed tools: read, grep, glob, chat-bridge, write (restricted to assets/plans/ only)

Blocked tools: edit, bash (except read-only commands), git commit, docker

Exit trigger: User approves a plan via chat command (!approve) or voice confirmation.

Execution Mode

Purpose: Implement the agreed plan. Full tool access.

Allowed tools: All — read, edit, write, bash, git, docker, chat-bridge

Blocked tools: None (current default behavior)

Exit trigger: Agent calls a "done" tool, or dispatches to a worker. Software SM transitions to validation.

Validation Mode

Purpose: Verify the work is correct. Can read and check, cannot change.

Allowed tools: read, grep, glob, bash (read-only: curl, docker logs, git status), chat-bridge, GitHub API (read), Linear API (read)

Blocked tools: edit, write, git commit, docker compose up

Exit trigger: All validation checks pass (software SM verifies), or agent escalates a failure to the user.

6. Implementation Options

Claude Code does not natively support dynamic tool sets. Three approaches can approximate it.

A. MCP Proxy
A proxy process sits between Claude Code and the actual MCP tool servers. The proxy holds the current mode and filters tool calls — allowed tools pass through, blocked tools return an error message explaining the restriction. Mode changes arrive via bus message or HTTP endpoint.
MCP Proxy
Pro True enforcement — blocked tools are invisible or return errors
Pro Single agent session, preserves context across mode changes
Pro Mode switch is a bus message, not a session restart
Con Requires building an MCP proxy (new infrastructure)
Con Built-in tools (read, edit, bash) may not be interceptable via MCP
B. Separate Sessions (Switchboard)
Different Claude Code sessions for different modes, each with a different .mcp.json that only lists the tools for that mode. A software controller decides which session is active and routes messages to it. Context is passed between sessions via files or a shared state store.
Separate Sessions
Pro Works today with vanilla Claude Code — no custom proxy needed
Pro Complete isolation between modes — brainstorm session literally cannot edit
Con Context loss on switch — each session starts fresh or needs explicit handoff
Con Expensive — multiple concurrent Claude sessions
Con Latency on mode switch (session startup is seconds, not milliseconds)
C. Hook-Based Soft Enforcement
Use Claude Code hooks to intercept tool calls and reject those not allowed in the current mode. A mode state file (/tmp/agent-mode) is read by every hook. CLAUDE.md instructions tell the agent what mode it is in and what tools to use. Hooks catch violations.
Hook-Based
Pro No new infrastructure — uses existing hook system
Pro Single session, context preserved
Pro Incremental — add one hook at a time for specific violations
Con Hooks only fire on tool calls, not on all agent actions
Con Agent still sees all tools and may attempt blocked ones repeatedly
Con Soft enforcement — the agent knows the tools exist and may try workarounds

Recommendation

Start with C (hooks) for immediate value. It requires no new infrastructure and catches the most common violations (editing during brainstorm, deploying without validation). Move to A (MCP proxy) when the mode system proves useful and hook coverage is insufficient. Defer B (separate sessions) unless context isolation becomes a hard requirement.

7. Validation Case Study

Walk through the "check your work" flow using the hybrid architecture.

Scenario

The supervisor dispatches a task to a teammate: "Fix the broken CSS on the dashboard." The teammate completes the work and pushes a PR. The system must verify the fix before reporting success.

Step-by-Step

1. Dispatch supervisor ──dispatch──▶ teammate mode controller: execution → waiting (supervisor's tools restricted while waiting — no new dispatches) 2. Completion event sysbus ──"dispatch/confirmed"──▶ mode controller teammate pushes PR, bus message: "pr/opened #250" mode controller: waiting → validation (tools restricted to read-only + check commands) 3. Agent runs validation (within validation mode) agent judgment decides WHAT to check: ├── curl the dashboard page ├── check nginx logs for 404s ├── verify PR #250 targets main ├── check Linear issue status └── run vitest for CSS-related tests agent CANNOT: ├── edit files (tool blocked) ├── deploy (tool blocked) └── merge the PR (tool blocked) 4a. All checks pass agent reports: "all checks pass" software SM detects pass condition → done mode controller: validation → idle chat-bridge: "Dashboard CSS fix verified. PR #250 ready to merge." 4b. Check fails agent reports: "404 on dashboard.css" software SM detects failure → execution (fix cycle) mode controller: validation → execution chat-bridge: "Validation failed — CSS file missing. Re-entering execution."

What the Hybrid Prevents

  • Without hybrid: Agent completes task, skips validation, says "done." User discovers the dashboard is broken an hour later.
  • With hybrid: Software SM forces the agent into validation mode after task completion. The agent cannot report "done" until the software SM transitions out of validation. The agent cannot fix things in validation mode — it can only check. If something is wrong, it must go back to execution mode (triggered by the software SM detecting a failure report).

Cross-Checking Sources

Validation mode is where multi-source cross-checking happens. The agent, restricted to read-only tools, checks:

Source What to Check Failure Condition
GitHub PR PR exists, targets main, CI passing PR missing, CI red, wrong base branch
Deployment Health endpoint, nginx logs, page loads 404s, 502s, health check failure
Linear Issue status matches work state Issue still "in progress" after PR merged
Test suite Relevant tests pass New failures in affected test files
Git state No uncommitted changes, branch is clean Leftover debug code, untracked files

The software SM does not know what "validation" means for a given task. That is agent judgment. The software SM only knows: "you are in validation mode, you can only read, and you cannot leave until you report pass or fail."

8. Open Questions

  • Granularity of bash restriction. In validation mode, bash should allow curl and docker logs but block docker compose up. Filtering bash commands by content requires parsing the command string — fragile, but achievable with an allowlist of prefixes.
  • Mode persistence across sessions. If the agent session restarts mid-validation, does it resume in validation mode? Requires persisting mode state to disk and reading it on startup.
  • Agent awareness of mode. Should the agent know what mode it is in? Probably yes — the CLAUDE.md should state the current mode and its constraints. This helps the agent work within the mode rather than fighting the restrictions.
  • Multi-agent mode coordination. If the supervisor is in validation mode and a teammate reports a new issue, does the supervisor need to exit validation to handle it? Mode preemption rules need definition.
  • Mode for the user. Can the user override the mode controller? Probably yes — a !force-execute command should bypass validation if the user knows what they are doing. The mode controller serves the user, not the other way around.
