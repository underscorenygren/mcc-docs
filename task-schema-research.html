MCC Docs

Task Schema Research

A canonical task format for solo-developer + AI agent workflows.

November 2026

TL;DR

Each task is a markdown heading with a YAML-style front matter block. Seven fields: id (short slug), status (open/active/blocked/done/dropped), priority (p1/p2/p3), owner (human/agent/unassigned), repo, ref (issue/PR/commit), and depends (list of IDs). Agent dispatch adds branch, accept, and test as optional fields. The markdown file is the source of truth. A parser extracts JSON for reports and agent consumption. GitHub issues are the backlog; tasks.md is the active sprint.

1. Survey of Existing Schemas

GitHub Issues / Projects Partial

GitHub Issues provide: title, body (markdown), labels, assignees, milestone, and a state machine (open/closed). GitHub Projects (v2) adds custom fields (single-select, date, number, iteration) and board/table views.

What works: Labels for categorization. Milestone for grouping. The body is freeform markdown that agents can read. The API is stable and well-documented. Projects v2 custom fields can model priority and status.

What doesn't: No native priority field (labels are stringly-typed). No blocking/dependency model. Projects v2 requires GraphQL for writes, which is verbose for automation. Cross-repo references are manual. The issue body has no structured schema — you get markdown, not typed fields.

Verdict: Good as a backlog store and public interface. Not sufficient as the sole canonical format because it lacks machine-parseable structure in the body and has no dependency model.

Linear Partial

Linear's data model: Issue (title, description, state, priority 0-4, estimate, assignee, team, project, cycle, label[]). States are team-configurable but default to: Backlog, Todo, In Progress, Done, Cancelled. Sub-issues supported. Relations: blocks, is-blocked-by, relates-to, duplicate.

What works: Priority as a number (0=urgent, 4=none). Named states with transitions. Relations. Cycles (time-boxed sprints). The API is clean — everything is a flat object with typed fields.

What doesn't: Designed for teams of 5-50. Cycles, teams, projects, views — all overhead for a solo developer. The UI is the product; the data model alone is overkill when your "UI" is a markdown file.

Verdict: The field set is a good reference. Priority-as-number and explicit state machine are worth adopting. Drop cycles, teams, estimates, and the SaaS dependency.

Todoist / Things / OmniFocus Avoid

Personal task managers. Todoist: task, project, section, priority (1-4), due date, labels, parent task. Things: area, project, heading, task, checklist, tags, deadline, when (schedule). OmniFocus: perspectives, contexts, forecast, review cycles.

What works: Simplicity of Todoist's model. The concept of "when" (scheduled start) vs "deadline" in Things.

What doesn't: No concept of code artifacts (branches, PRs, commits). No agent dispatch. No cross-repo. No blocking relationships. These are consumption-tracking tools, not production-tracking tools.

Verdict: Wrong domain. These track personal errands, not software development with AI agents.

TaskWarrior Partial

CLI task manager. Fields: description, project, priority (H/M/L), tags[], due, depends (list of UUIDs), status (pending/completed/deleted/waiting/recurring), urgency (computed score). Stores as line-delimited JSON.

What works: depends as a first-class field. Computed urgency score. CLI-first (agents can shell out). Tags as freeform annotations. The JSON storage is trivially parseable. UDA (user-defined attributes) for extension.

What doesn't: UUIDs are not human-readable. No concept of repos, branches, or PRs. The urgency formula is clever but opaque — hard to debug why something is ranked where it is.

Verdict: The depends model and JSON-line storage are directly applicable. Short slugs instead of UUIDs. Skip the urgency formula — with <50 tasks, manual priority is fine.

todo.txt Partial

One line per task: (A) 2026-11-14 Call plumber +home @phone. Priority is (A)-(Z). Projects are +project. Contexts are @context. Completion: prepend x 2026-11-14. Metadata via key:value pairs.

What works: Radically simple. Human-readable. Parseable with a regex. The key:value extension mechanism is exactly what we need for custom fields.

What doesn't: One-line-per-task breaks down when tasks need context, acceptance criteria, or multi-line descriptions. No hierarchy. No blocking. Designed for personal productivity, not software.

Verdict: The key:value inline metadata pattern is worth stealing. The one-line constraint is too tight for development tasks.

Org-mode Partial

Emacs Org-mode: headings are tasks. States: TODO, DONE, plus custom (IN-PROGRESS, WAITING, CANCELLED). Properties drawer for typed metadata. Tags on headings. Priority [#A]/[#B]/[#C]. Agenda views. Clock-in/clock-out for time tracking. Links to files, URLs, other headings.

What works: Headings-as-tasks maps directly to markdown sections. The properties drawer (key-value pairs under a heading) is the exact pattern: human-readable, machine-parseable, extensible. Custom state sequences. Priority letters.

What doesn't: Org-mode is an Emacs ecosystem. The syntax (:PROPERTIES: drawers, #+ directives) is idiosyncratic. We're in markdown, not org.

Verdict: The properties-drawer pattern — structured metadata under a heading — is the core design we should adopt, translated to markdown-compatible syntax (YAML-style - **Key:** value).

JIRA Avoid

Issue types (Epic, Story, Task, Sub-task, Bug), 50+ built-in fields, custom fields, workflows with conditions and validators, components, versions, sprints, boards, filters, dashboards, permissions, schemes.

What works: Nothing, for a solo developer. The lesson from JIRA is that schema complexity grows monotonically and never shrinks. Every optional field becomes mandatory in someone's workflow. Every custom field becomes load-bearing. Every workflow transition needs a validator.

Verdict: Cautionary tale. Keep the field count under 10. Make extension possible but not encouraged.

Agent Task Formats (SWE-bench, Devin, AutoGPT) Partial

SWE-bench: Structured JSON — repo, base_commit, problem_statement (natural language), hints (optional), test_patch (diff that validates the fix). The test_patch is the acceptance criterion.

Devin: Natural language task description + repo URL + branch. No formal schema beyond that. The agent infers structure from the description.

AutoGPT/OpenDevin: Task as a goal string + constraints list. Minimal structure — the agent is expected to decompose the task itself.

What works from SWE-bench: The concept of a test command as acceptance criteria. test_patch or test_cmd — something the agent can run to verify its own work. Also: pinning to a specific commit/branch so the agent starts from a known state.

What works from practice: In the MCC dispatch workflow, the supervisor already compresses a plan into: what to change, which files, acceptance criteria, branch name, test command. This is the agent dispatch metadata that belongs in the schema.

Verdict: Add optional agent dispatch fields: branch, accept (criteria text), test (shell command). These only appear on tasks actively dispatched to agents.

2. Design Principles

Constraints derived from how MCC actually works:

  • Markdown is the source of truth. The developer reads tasks.md in a terminal or browser. If the schema isn't readable as plain markdown, it fails.
  • Machine-parseable without a build step. A simple parser (regex or line-by-line) should extract structured data. No AST required.
  • Under 10 fields. Every field must earn its place. If a field is empty on >50% of tasks, it should be optional or removed.
  • GitHub issues are the backlog, tasks.md is the sprint. Not everything in GitHub issues appears in tasks.md. When something moves to active work, it gets a tasks.md entry. The ref field links back to the issue.
  • One canonical ID per task. Short slugs (e.g., slack-setup, ws-reconnect). Not UUIDs, not auto-incrementing numbers. Human-typeable, greppable.
  • Status drives the view. The PM report, the tasks.md sections, and agent queries all filter by status. Status must be a closed enum, not freeform text.

3. The Proposed Schema

Field Definitions

FieldTypeRequiredDescription
id string Yes Short slug. Lowercase, hyphens. Unique across active tasks. E.g., slack-setup, ws-reconnect.
status enum Yes One of: open, active, blocked, done, dropped.
priority enum Yes p1 (do now), p2 (do soon), p3 (backlog).
owner string No human, agent name (e.g., octocat), or omitted (unassigned).
repo string No Repository short name. Defaults to claude-by-voice. E.g., mcc-notes, mcc-realtime.
ref string No GitHub issue, PR, or commit. E.g., #283, PR #286, 8a0d79b.
depends string[] No List of task IDs this is blocked by. E.g., slack-setup.
added date No When the task was created. ISO date: 2026-11-14.

Agent Dispatch Fields (optional, only when dispatching)

FieldTypeDescription
branch string Git branch name. E.g., auto/slack-setup.
accept string Acceptance criteria in plain English. What "done" looks like.
test string Shell command to verify. E.g., cd web && npx vitest run.

Status Lifecycle

open --> active --> done | | | +-> blocked --> active | +-> dropped open task exists, not started active someone (human or agent) is working on it blocked waiting on an external dependency or another task done completed, ref points to the commit/PR dropped abandoned, kept for history (not deleted)

Rules: blocked can only transition to active (unblocked) or dropped. done and dropped are terminal. A task can move from active back to open if deprioritized. There is no "in review" state — reviews happen within active.

Priority Model

Three levels. No more.

PriorityMeaningAction
p1Do nowCurrent session work. At most 3 p1 tasks at a time.
p2Do soonNext session or when a p1 clears. The default for new work.
p3BacklogWorth tracking, not worth scheduling. Lives in tasks.md or GitHub issues.

If everything is p1, nothing is p1. The constraint of "at most 3 p1s" forces prioritization. Agents should only pick up p1 or p2 tasks unless explicitly told otherwise.

Dependencies

The depends field lists task IDs. A task with depends: [slack-setup] cannot move to active until slack-setup is done. This is enforced by convention (the parser can warn) not by hard locks.

Keep dependency chains short. If A depends on B depends on C depends on D, something is wrong — decompose differently. In practice, most tasks in a solo project have zero or one dependency.

4. Markdown Format (Human View)

The format extends the current tasks.md pattern. Each task is an h3 heading followed by metadata lines. The metadata uses the existing - **Key:** value pattern for backward compatibility.

Example: tasks.md
## Active

### Slack integration
- **ID:** slack-setup
- **Status:** blocked
- **Priority:** p1
- **Owner:** human
- **Ref:** PR #286
- **Depends:** —
- **Context:** Code complete. Waiting on human to create Slack workspace,
  add tokens to .env, invite Lisa.

### JSONL WebSocket reconnect
- **ID:** ws-reconnect
- **Status:** active
- **Priority:** p2
- **Owner:** octocat
- **Repo:** claude-by-voice
- **Ref:** #280
- **Branch:** auto/ws-reconnect
- **Accept:** JSONL WS reconnects within 5s after disconnect, no message loss
- **Test:** cd web && npx vitest run
- **Context:** Voice WS reconnect done. JSONL WS still drops on disconnect.

### mcc-realtime skeleton
- **ID:** realtime-skeleton
- **Status:** open
- **Priority:** p3
- **Repo:** mcc-realtime
- **Context:** Whisper realtime STT first, ElevenLabs fast follow.

## Done

### Completed 2026-11-13
- **slack-connector** — Slack connector service (PR #286, 43c2c36)
- **tts-reconnect** — TTS reconnect fix (PR #285, 8a0d79b)

The ## Active / ## Done sections remain. Within Active, tasks are ordered by priority (p1 first, then p2, then p3). Done entries are compressed to one line with ID, description, and ref.

5. JSON Format (Machine View)

A parser reads tasks.md and emits a JSON array. Each task becomes an object. This powers the PM report, agent task queries, and any future automation.

Example: tasks.json (generated)
[
  {
    "id": "slack-setup",
    "title": "Slack integration",
    "status": "blocked",
    "priority": "p1",
    "owner": "human",
    "repo": "claude-by-voice",
    "ref": "PR #286",
    "depends": [],
    "added": "2026-11-13",
    "context": "Code complete. Waiting on human to create Slack workspace."
  },
  {
    "id": "ws-reconnect",
    "title": "JSONL WebSocket reconnect",
    "status": "active",
    "priority": "p2",
    "owner": "octocat",
    "repo": "claude-by-voice",
    "ref": "#280",
    "added": "2026-11-12",
    "dispatch": {
      "branch": "auto/ws-reconnect",
      "accept": "JSONL WS reconnects within 5s after disconnect, no message loss",
      "test": "cd web && npx vitest run"
    },
    "context": "Voice WS reconnect done. JSONL WS still drops on disconnect."
  }
]

The parser is trivial: split on ### headings, extract - **Key:** value lines with a regex, map keys to the schema. Unknown keys go into an extra object. Context is everything after the structured fields that isn't a recognized key.

6. How It Integrates

tasks.md (canonical)

Human-edited. The source of truth for active work. Agents can read and propose edits via PR. The supervisor updates it after each work session.

GitHub Issues (backlog)

Issues that aren't in active work stay in GitHub only. When an issue is promoted to active work, the supervisor creates a tasks.md entry with ref: #NNN. When the task is done, the issue is closed. One-directional flow: GitHub issue → tasks.md entry → done.

No bidirectional sync. That way lies madness and stale data. The tasks.md entry is always more current than the GitHub issue body.

PM Report (generated)

The PM report (pm.html) reads the JSON output of the parser. It groups by status, sorts by priority, and renders a dashboard. No hand-editing of pm.html. Change tasks.md, run the build, pm.html updates.

Agent Dispatch

When the supervisor dispatches work to an agent:

  1. Add/update the task in tasks.md with status: active, owner: <agent>, and the dispatch fields (branch, accept, test).
  2. The agent receives the compressed plan (from the Context field or a separate prompt).
  3. When the agent finishes, the supervisor updates: status: done, ref: PR #NNN.

history.tsv (append-only log)

Each status transition appends a row. The TSV format gets one new column: id. 

date	action	id	task	ref
2026-11-14	active	ws-reconnect	JSONL WebSocket reconnect	auto/ws-reconnect
2026-11-14	done	slack-connector	Slack connector service	43c2c36

7. Migration

The current tasks.md is close to the proposed format. Migration is incremental, not a rewrite.

Current

### Task name
- **Status:** in progress
- **Added:** 2026-11-13
- **Ref:** PR #286
- **Context:** description

Proposed

### Task name
- **ID:** slug (new)
- **Status:** active (enum)
- **Priority:** p2 (new)
- **Owner:** human (new)
- **Added:** 2026-11-13
- **Ref:** PR #286
- **Context:** description

Steps:

  1. Add IDs. Go through each active task, assign a short slug. 5 minutes of work.
  2. Normalize status values. Replace "in progress" with active, "pending" with open, "waiting on human setup" with blocked. Use the five-value enum.
  3. Add priority. Tag each active task as p1/p2/p3. Default everything to p2.
  4. Add owner where known. Most tasks are human or unassigned. Agent-dispatched tasks get the agent name.
  5. Write the parser. A ~50 line script (bash, python, or node) that reads tasks.md and emits JSON. Wire it into build.sh so pm.html is generated from JSON, not hand-authored.
  6. Update history.tsv. Add the id column. Old rows get a blank id (backward compatible).

Total effort: under an hour. No data loss, no format break. The existing tasks.md is already 80% of the way there.

8. Sub-tasks and Recursion

The PM report's "Today's Work" section shows items like "PR #282 merged: JSONL tailer + status tile event log" and "Email router fix: Bun Buffer.from crash". These are sub-events of larger tasks. The schema should support this without requiring a separate model.

Design: tasks are recursive

A task can have children. Children are indented under the parent in tasks.md. In JSON, they nest in a children array. Children inherit the parent's repo and priority unless overridden. A parent task is done when all its children are done or dropped.

Example: parent with sub-tasks
### Slack integration
- **ID:** slack
- **Status:** active
- **Priority:** p1

#### Slack connector service
- **ID:** slack/connector
- **Status:** done
- **Ref:** PR #286, 43c2c36

#### Slack app setup
- **ID:** slack/app-setup
- **Status:** blocked
- **Owner:** human
- **Context:** Create workspace, add tokens to .env

#### Lisa invitation
- **ID:** slack/lisa
- **Status:** open
- **Depends:** slack/app-setup

Sub-task IDs use slash notation: slack/connector, slack/app-setup. This is greppable, hierarchical, and avoids the ambiguity of flat IDs. Depth is limited to two levels — if you need three, decompose the parent.

Collapsing completed sub-tasks

When a parent task moves to done, its children collapse into a summary line in the Done section:

Collapsed in Done section
- **slack** — Slack integration (3 sub-tasks: connector PR #286, app setup, Lisa invite)

The full history lives in history.tsv. The Done section stays compact. The sub-tasks only appear expanded while the parent is active.

9. Unified Data Model

The same schema powers every view. One data model, multiple renderers:

ConsumerReadsWritesNotes
In-session tasks (TaskCreate/Update) tasks.json tasks.md (via supervisor) Session tasks map 1:1 to schema tasks. Sync on session end.
tasks.md — Supervisor edits directly Source of truth. Human-readable markdown.
PM report (pm.html) tasks.json — Generated by build.sh. No hand-editing.
Seed / project pages tasks.json — Filter by repo or tag to build per-project views.
Agent dispatch tasks.json (filtered) tasks.md (via supervisor) Dispatch fields populate the agent prompt.
history.tsv — Append on status change Timeline visualization, delta source.

The parser runs in build.sh: tasks.md → tasks.json → pm.html, seed pages. This means changing tasks.md and running the build updates everything downstream. No separate data entry for PM reports or project pages.

10. Delta Generation

A delta is the diff between two snapshots of tasks.json. This powers:

  • Session summaries: "3 tasks completed, 1 new task added, 2 priority changes"
  • PM report diffs: "Since last report: slack-connector done, ws-reconnect moved to p1"
  • history.tsv entries: Each delta row is a state transition

Implementation

On each sync, the build script:

  1. Reads previous tasks.json (git show HEAD:tasks.json)
  2. Parses current tasks.md into new tasks.json
  3. Diffs by ID: new tasks, removed tasks, field changes
  4. Appends changed rows to history.tsv
  5. Optionally generates a delta.json for the PM report's "Changes since last sync" section
Example: delta.json
{
  "since": "2026-11-13T21:35:00Z",
  "added": ["slack/lisa"],
  "completed": ["slack/connector", "tts-reconnect"],
  "changed": [
    {"id": "ws-reconnect", "field": "status", "from": "open", "to": "active"},
    {"id": "slack", "field": "priority", "from": "p2", "to": "p1"}
  ]
}

This delta is cheap to compute (JSON diff by ID) and gives the PM report a "what changed" section without manually tracking changes. The history.tsv becomes a flattened append-only version of all deltas.

11. Open Questions

  • Should the parser live in mcc-tasks or be a shared tool? If other repos need to read/write task format, it should be a standalone script or package. For now, living in mcc-tasks alongside build.sh is simplest.
  • How to handle multi-repo tasks? A task like "deploy Convex frontend" spans mcc-ablog-convex and claude-by-voice. The proposed repo field is singular. Options: comma-separated repos, or decompose into two linked tasks. Recommendation: decompose. Multi-repo tasks are usually two tasks pretending to be one.
  • Should the Done section use the full schema or stay compressed? Current Done entries are one-liners. The proposed format could expand them, but that would make tasks.md grow fast. Recommendation: keep Done compressed (one line with ID + description + ref), let the history.tsv carry the full transition log.
  • Time estimates? Linear and JIRA have story points or time estimates. For a solo dev + agents, estimates are usually wrong and create guilt. Recommendation: skip them. If needed later, add an optional effort field (small/medium/large) — but don't start with it.
  • Should agents edit tasks.md directly? Currently only the supervisor edits tasks.md. Agents could propose changes via PR. Risk: merge conflicts if multiple agents edit simultaneously. Recommendation: supervisor remains the sole writer. Agents report status via chat-bridge; the supervisor updates tasks.md.
  • Due dates? Not in the initial schema. Most solo-dev tasks don't have hard deadlines. If collaboration repos need deadlines (e.g., "demo for Dimitri by Friday"), add an optional due field later. The priority field handles urgency without calendar coupling.
