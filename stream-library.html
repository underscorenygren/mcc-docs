Stream Library

A unified, layered abstraction for all message passing in the system — chat, voice, events, work dispatch, agent communication. One library, typed messages, multiple transports.

PR/FAQ format — describing how it works before building it.
Companion to Message Mechanics and Decisions.

The press release

Today, messages in our system travel through four different mechanisms: WebSocket (bridge), HTTP pub/sub (chatbus), WebSocket (sysbus), and MCP stdio (agent channels). Each has its own framing, its own ID scheme, its own replay logic (or none). A chat message and a tool_use event are fundamentally the same thing — a typed record moving from producer to consumer — but they're implemented as if they're different species.

The stream library replaces these with one abstraction: a typed, ordered, replayable stream of records. Every message in the system — chat text, voice events, agent acks, build status, work dispatch — is a record in a stream. Streams are per-agent, per-channel, or per-topic. Records have sequence numbers, typed payloads, and optional client IDs for dedup.

The library is layered. You choose how deep you go:

  • Need a raw WebSocket? Layer 0.
  • Need typed JSON messages? Add Layer 1–3.
  • Need replay and dedup? Add Layer 4.
  • Need per-message ack tracking and lag? Add Layer 5.

Each layer is independent. Voice uses layers 0–3 (transport + framing + typing, no replay needed for audio frames). Chat uses layers 0–5 (full stack). Events use layers 0–3 (ephemeral, no replay). The session manager uses layer 5 on top of a chat stream.

The layers

Layer 0
Transport

The pipe. How bytes move between two endpoints.

Implementations: WebSocketTransport, HttpPollTransport, StdioTransport (MCP), SSETransport.

Interface: connect(), send(bytes), onReceive(bytes), disconnect(). That's it. No opinions about what the bytes contain.

Layer 1
Framing

Message boundaries and serialization. Turns a byte stream into discrete messages.

For WebSocket: each WS frame = one message (framing is built into the transport). For stdio: newline-delimited JSON. For HTTP: each request/response body = one message.

Interface: encode(message) → bytes, decode(bytes) → message. Default: JSON. Could be protobuf, msgpack, or raw binary (audio frames).

Layer 2
Identity

Every message gets a sequence number and optional client ID. This is the envelope.

{
  seq: 42,                    // server-assigned, monotonic
  client_id: "chat_17290...", // sender-assigned, for dedup
  stream: "porter",           // which stream this belongs to
  timestamp: "2026-10-16T...",
  payload: { ... }            // typed content (Layer 3)
}

The sequence number is assigned by the stream server on append. The client ID is assigned by the producer before sending. Together they give you: ordering (seq), dedup (client_id), and replay cursor (seq).

Layer 3
Typing

The payload is a tagged union — a type field discriminates the shape.

// Chat
{ type: "chat.message", from: "user", text: "Write me a poem" }
{ type: "chat.message", from: "agent", text: "Roses are red...", ref_seq: 1 }

// Voice
{ type: "voice.speech_start" }
{ type: "voice.stt_complete", text: "Write me a poem", duration_ms: 1200 }
{ type: "voice.tts_chunk", audio: <base64>, seq_in_utterance: 3 }

// Events
{ type: "event.tool_use", tool: "Bash", agent: "porter" }
{ type: "event.build", status: "done", service: "bridge" }

// Acks
{ type: "ack.delivered", ref_seq: 5 }
{ type: "ack.processing", ref_seq: 5 }

// Control
{ type: "control.subscribe", since_seq: 42, limit: 10 }
{ type: "control.ping" }
{ type: "control.pong" }

Types are namespaced: chat.*, voice.*, event.*, ack.*, control.*. A consumer subscribes to a stream and filters by type namespace. A chat UI ignores event.* records. A status tile ignores chat.* records. But they're all records in the same stream infrastructure.

In TypeScript, this is a discriminated union: 

type StreamRecord =
  | { type: "chat.message"; from: string; text: string; ref_seq?: number }
  | { type: "chat.thinking"; agent: string }
  | { type: "voice.speech_start" }
  | { type: "voice.stt_complete"; text: string; duration_ms: number }
  | { type: "voice.tts_chunk"; audio: string; seq_in_utterance: number }
  | { type: "event.tool_use"; tool: string; agent: string }
  | { type: "ack.delivered"; ref_seq: number }
  | { type: "ack.processing"; ref_seq: number }
  | { type: "control.subscribe"; since_seq?: number; limit?: number }
  // ...etc
Layer 4
Delivery

Replay, dedup, and cursor management. This is where "stream" becomes more than a pipe.

Server side:

  • Append-only log (JSONL on disk, ring buffer in memory)
  • Assign sequence number on append
  • Dedup by client_id (TTL cache)
  • Query by seq range: GET /stream/{name}?after_seq=42&limit=20

Client side:

  • Store last-seen seq in localStorage
  • On connect: send control.subscribe with since_seq
  • Receive replay records, dedup via seenIds set
  • Transition to live records seamlessly

Not every stream needs Layer 4. Voice audio frames are ephemeral — no replay, no persistence. Events are ephemeral — ring buffer only, no disk. Chat is persistent — full Layer 4. The layer is opt-in per stream.

Layer 5
Session

Per-consumer state tracking. This is the message session manager — it lives on top of a Layer 4 stream and adds:

  • Consumer cursor: the last seq this consumer acknowledged
  • Lag: head_seq − consumer_cursor
  • Per-message state: sent → delivered → processing → responded
  • Escalation: timers that trigger nudge, fast-respond, circuit breaker
  • State reflection: HTTP endpoint exposing the full chain state

Layer 5 is specific to agent consumers. A browser chat client doesn't need it — it just reads the stream. The channel server uses Layer 5 to track the agent's progress through the message chain.

What's duplicated

  • Envelope wrapping — chatbus and sysbus both use pkg/provider/bus/envelope.go but bridge WebSocket has its own ad-hoc framing
  • Dedup — chatbus has server-side TTL cache, ChatStore has client-side seenIds, both doing the same job at different layers
  • Connection management — bridge WS, sysbus WS, and agent chat WS all have separate ping/pong, reconnect, and timeout logic
  • Replay — bridge replays from JSONL, chatbus replays from ring buffer, sysbus sends snapshot on connect — three implementations of "give me what I missed"

What's missing

  • Sequence numbers — no component has them yet
  • Cross-stream typing — each bus defines its own message shapes, no shared type system
  • Ack protocol — nothing tracks consumer progress
  • Voice as a stream participant — voice events are invisible outside the browser

How you use it

Producer: sending a chat message

// Browser client
const stream = createStream("porter", {
  transport: "websocket",
  url: "/ws/stream/porter",
  layers: [framing.json, identity.clientId, delivery.replay]
});

await stream.connect();

// Send a message — client_id generated automatically
const { seq } = await stream.append({
  type: "chat.message",
  from: "user",
  text: "Write me a poem"
});
// seq = 5 (assigned by server)

// Listen for responses
stream.on("chat.message", (record) => {
  if (record.payload.from === "agent") {
    displayMessage(record.payload.text);
  }
});

// Listen for acks (from sysbus, merged into the stream view)
stream.on("ack.*", (record) => {
  updateCheckmark(record.payload.ref_seq, record.payload.type);
});

Consumer: agent channel server

// Channel server (Node.js)
const agentStream = createStream("porter", {
  transport: "http",
  url: "http://chatbus:9095",
  layers: [framing.json, identity.envelope, delivery.replay, session.manager]
});

await agentStream.connect();

// Session manager tracks the chain
agentStream.onMessage((record) => {
  // Deliver to Claude via MCP
  mcpTransport.sendNotification("message", record.payload);

  // Emit delivery ack to sysbus
  sysbus.emit({ type: "ack.delivered", ref_seq: record.seq, agent: "porter" });
});

// When agent replies via tool call
function onAgentReply(text, refSeq) {
  agentStream.append({
    type: "chat.message",
    from: "agent",
    text: text,
    ref_seq: refSeq
  });
  // Session manager automatically marks refSeq as "responded"
}

// Query chain state
// GET /agent/porter/chain → { head_seq: 8, cursor: 6, lag: 2, messages: [...] }

Voice: audio + events on the same stream

// Voice uses a lightweight stream — no replay, no persistence
const voiceStream = createStream("voice-session-abc", {
  transport: "websocket",
  url: "/ws/stream/voice",
  layers: [framing.binary]  // raw audio frames, no identity layer
});

// But voice *events* go on the agent's main stream
const agentStream = getStream("porter");
agentStream.append({ type: "voice.speech_start" });
// ... STT runs ...
agentStream.append({ type: "voice.stt_complete", text: "Write me a poem", duration_ms: 1200 });
// This becomes a regular chat message in the stream, with a seq number
agentStream.append({ type: "chat.message", from: "user", text: "Write me a poem" });

Events: ephemeral stream

// Sysbus becomes just another stream with fewer layers
const eventStream = createStream("system-events", {
  transport: "websocket",
  url: "/ws/stream/events",
  layers: [framing.json, identity.envelope]  // no delivery layer — ephemeral
});

eventStream.on("event.*", (record) => {
  updateActivityTimeline(record);
});

// Snapshot on connect replaces the current sysbus snapshot mechanism
// It's just "replay the ring buffer" — same as chat replay but smaller window

Migration path

We don't rewrite everything at once. The library wraps existing infrastructure first, then replaces it layer by layer.

PhaseWhat changesWhat stays
1. Types Define the StreamRecord discriminated union. Shared between Go and TypeScript. All existing transport, routing, persistence unchanged.
2. Identity Add sequence numbers to chatbus. Envelope gets seq field. Client sends since_seq. Transport unchanged. Replay still works (timestamp fallback for old logs).
3. Client library TypeScript createStream() that wraps existing WebSocket/HTTP connections with the layer model. Server unchanged. Client library adapts to existing protocols.
4. Session manager Channel server gets Layer 5. Ack emission to sysbus. /chain endpoint. Chatbus, sysbus unchanged. Session manager is additive.
5. Unify transports Replace bridge WS, chatbus HTTP, sysbus WS with stream endpoints. One connection per agent. This is the big consolidation — but by now every layer is proven independently.

FAQ

Why not just use Kafka / NATS / Redis Streams?

Scale. We have one server, a handful of agents, and hundreds of messages per hour. Kafka is a distributed system for millions of messages per second. The operational complexity of running Kafka (or NATS, or Redis Streams) far exceeds the complexity of the problem we're solving. Our JSONL files + ring buffer are the right weight.

The library borrows concepts from these systems (append-only logs, sequence numbers, consumer cursors) without importing their infrastructure.

Why not use S2.dev as the backend?

S2 is interesting and worth watching. It solves exactly the problem we have (ordered, durable, replayable streams) with a clean API. But it's a hosted service with a cost, and it would make our system dependent on external infrastructure. Our current approach (local JSONL + ring buffer) is zero-dependency and good enough. If we outgrow it, S2 is a natural migration target — the library's Layer 4 could swap backends.

Does this replace MCP?

No. MCP is the protocol between the channel server and Claude. It's Layer 0 (stdio transport) with its own framing (JSON-RPC). The stream library doesn't replace MCP — the channel server bridges between the stream world and the MCP world. Messages come in on a stream, get delivered to Claude via MCP, and responses come back via MCP and get appended to the stream.

Does every message type need every layer?

No. That's the point of layers being opt-in:

  • Audio frames: L0 + L1 only (transport + binary framing). No identity, no replay.
  • Events: L0 + L1 + L2 + L3 (transport + framing + identity + typing). No persistence.
  • Chat: L0 through L4 (full delivery with replay and dedup).
  • Agent messages: L0 through L5 (full stack with session tracking).
How does voice fit in?

Audio frames stay on their own lightweight stream (L0 + L1). But voice events (speech_start, stt_complete, tts_start, barge_in) are records on the agent's main stream with full typing and sequence numbers. This makes voice state visible to every component that reads the stream — the session manager can see that STT just completed, the UI can show "transcribing..." without polling, and the agent can be notified of barge-in.

What happens to chatbus and sysbus?

They converge. In Phase 5, both become stream servers — same code, different configuration. Chatbus is a persistent stream server (JSONL + ring, seq numbers, dedup). Sysbus is an ephemeral stream server (ring only, no dedup). The client library connects to both the same way. Eventually they could be one server with per-stream configuration.

What about multi-agent? User talks to porter, then switches to runa.

Each agent has its own stream. Switching agents means subscribing to a different stream. The client library manages multiple stream connections. A "meta" stream could carry routing decisions ("user switched to runa") so other components can react.

What about multi-party? Human + two agents in the same conversation.

A shared stream. All parties append to the same stream. The from field distinguishes who said what. Each agent's session manager (Layer 5) tracks its own cursor independently. Human sees all messages. Each agent sees all messages but acks at its own pace.

Is this a lot of work?

The migration path is designed so each phase is useful on its own. Phase 1 (types) is a TypeScript/Go type definition. Phase 2 (seq numbers) is a chatbus change. Phase 3 (client library) is a wrapper around existing connections. You get value at every step, and you can stop at any phase.
