Taskmaster Sidecar — Design Research

Patterns for a PM sidecar that observes work, synthesizes status, and suggests next actions from an intake queue.

A comprehensive survey of patterns for a "taskmaster" sidecar process that acts as a project manager alongside an interactive coding agent. Covers prior art, communication patterns, activity detection, work suggestion algorithms, and a recommended architecture.

Design brief: assets/plans/taskmaster-sidecar.md. Spore intake queue: mcc-tasks/spores/active.json. Triage logic: mcc-tasks/spore-triage.md.

1. Prior Art Survey

1.1 Devin Bots (Cognition, Nov 2026)

Cognition's Devin Bots are the closest analog to the taskmaster concept. A Devin Bot is a persistent manager agent that supervises teams of worker Devin instances over multi-week projects.

Architecture

  • Brain / Devbox split. The reasoning engine (brain) is stateless and cloud-hosted. The execution environment (devbox) is a containerized workspace with full shell, browser, and editor access. The manager outlives any individual worker session.
  • Persistent memory. Bots retain context across sessions and weeks. Memory is not reset between task delegations — the Bot remembers the full project arc.
  • Model routing (Devin Fusion). The manager selects different models per stage: a frontier model for planning and review, faster/cheaper models for routine code generation.
  • Worker delegation. The Bot decomposes work into discrete tickets, spawns individual Devin sessions for each, monitors CI results, and merges PRs that pass. The Android Bot example: 1,134 PRs merged with only 183 human messages (1 human message per ~6 PRs).
  • Authority model. Engineers define guardrails up front — which systems can be accessed, what can change, when approval is needed. Decisions requiring human judgment land in a "Needs You" inbox.
  • Communication. Bots join Slack as team members and reach out when blocked or needing decisions.
Takeaway: Devin Bots validate the "persistent PM agent alongside workers" model. Their authority system (human-defined guardrails + escalation inbox) maps directly to the suggest-only vs. auto-dispatch question. Start with suggest-only, graduate to auto-dispatch for low-risk items as trust builds.

1.2 Cursor Background Agents (Cloud Agents)

Cursor's Cloud Agents run in isolated cloud VMs, each getting a full development environment.

  • Isolated VMs. Each agent gets its own Ubuntu VM with browser, shell, editor. No shared state between agents.
  • Branch-based handoff. Agents work on a separate branch, push results, open a PR.
  • Observation. Users can follow the conversation live, take control of the remote desktop, or watch via live view.
  • Parallelism. Up to 8 agents simultaneously. No coordination between agents.
  • Multi-entrypoint dispatch. Tasks from desktop app, web UI, iOS, Slack, Linear, GitHub, Bitbucket, or API.
Takeaway: Cursor validates "dispatch and forget" but has no PM layer. Each agent is independent. No process observes overall project state and suggests what to work on next. That gap is exactly what the taskmaster fills.

1.3 AutoGPT / BabyAGI Task Decomposition

Three ideas from the 2023 agent craze that survived to 2026:

  1. The Tool Loop with Hard Stops. LLMs use tools in a loop with environmental feedback. Modern implementations added max iteration limits, spending caps, and real environmental feedback (test runners, compilers) replacing self-assessment.
  2. External Memory as Plain Files. Vector databases proved unnecessary overhead. Successful agents use structured markdown files persisted outside the context window. Task lists became descriptive aids rather than execution drivers.
  3. Human Checkpoints. Auto-GPT's optional approval prompts evolved into graduated permission systems: auto mode, manual mode, plan mode.

BabyAGI's three-agent loop is the most relevant pattern:

  • Task Creation Agent: generates new sub-tasks from objective + completed results
  • Prioritization Agent: reorders the queue by importance and logical sequencing
  • Execution Agent: runs the top-priority task

BabyAGI-2o (2026) replaced the flat priority queue with a hierarchical task graph with explicit dependency tracking — matching the spore system's blocked_by mechanism.

Takeaway: The taskmaster maps to BabyAGI's creation + prioritization agents combined. It should NOT be the execution agent. Keep those roles separate. The supervisor executes; the taskmaster triages and suggests.

1.4 CrewAI Process Types

CrewAI offers two orchestration models:

  • Sequential Process: Tasks run in fixed order. Simple but inflexible.
  • Hierarchical Process: A Manager Agent receives the overall goal, delegates to specialized workers, validates outputs, and can reassign failed tasks.

Delegation control. CrewAI learned the hard way that delegation must be tightly controlled. Delegation is now disabled by default. Individual contributors with delegation enabled tend to loop endlessly. Only manager agents should delegate.

Takeaway: The taskmaster should be the only process that suggests/delegates work. Delegation should flow: human triages intake → taskmaster suggests → supervisor executes.

1.5 Linear Triage Intelligence

Linear's AI triage (Business plan) performs automated assessment when issues enter triage:

  • Cross-references against historical workspace data
  • Suggests team ownership, assignee, labels
  • Checks for duplicate existing issues
  • Learns prioritization patterns from team behavior
  • Sets initial priority level based on description analysis
Takeaway: Linear's triage is a good model for the taskmaster's intake processing. It reads context and suggests metadata without executing. The spore-triage.md algorithm already does this manually — the taskmaster automates it.

1.6 GitHub Copilot Workspace

Copilot Workspace converts natural-language task descriptions into multi-file plans and code changes:

  • Produces editable specs (current state vs. desired state)
  • File-level plans (actions per file)
  • Concrete diffs for human inspection
  • Hybrid model routing (Claude, Gemini, GPT-4o)
  • 55% issue resolution rate in benchmarks
Takeaway: The taskmaster's suggestions should follow a similar spec/plan/implementation pipeline — present the spore, the proposed approach, the files involved, and the acceptance criteria before dispatch.

2. Sidecar Communication Patterns

The taskmaster and supervisor are two long-running processes on the same host that need to exchange state. Viable patterns, ranked by fit:

2.1 Shared State File (JSON)

┌───────────┐    data/taskmaster-state.json    ┌───────────┐
│ Supervisor │◄──────── read/write ──────────►│ Taskmaster │
└───────────┘                                  └───────────┘

Pros: Dead simple. No infrastructure. Survives restarts. Human-inspectable. Both Claude Code sessions can read/write natively.

Cons: No atomicity on concurrent writes. Polling required. No ordering guarantees.

Locking strategy: Atomic writes (write to temp file, then rename). Effectively atomic on Linux for small JSON.

2.2 Append-Only Event Log (JSONL)

┌───────────┐    data/taskmaster-events.jsonl    ┌───────────┐
│ Supervisor │──── append ──────────────────────►│            │
│            │◄── append ────────────────────────│ Taskmaster │
└───────────┘                                    └───────────┘

Pros: Append-only = no corruption risk (atomic for lines < PIPE_BUF, 4096 bytes on Linux). Full audit trail. Aligns with "log is the agent" pattern from event-sourced reactive graphs. Both processes can tail for new events.

Cons: State must be reconstructed by replaying the log. Log grows unbounded without compaction.

2.3 Chatbus Channel

┌───────────┐    chatbus (agent=taskmaster)     ┌───────────┐
│ Supervisor │◄──────── pub/sub ──────────────►│ Taskmaster │
└───────────┘                                   └───────────┘

Pros: Already built. Real-time delivery. Messages persist in bus-messages.jsonl. UI can display taskmaster messages in the activity feed.

Cons: Requires chatbus running. Supervisor misses messages if it restarts.

2.4 Comparison Matrix

2.5 Recommendation: Hybrid — JSONL log + chatbus notifications

┌───────────┐                                    ┌───────────┐
│            │── append event ►[events.jsonl]◄── append ──│            │
│ Supervisor │                                    │ Taskmaster │
│            │◄── chatbus notify ─────────────────│            │
└───────────┘                                    └───────────┘
  • JSONL log (data/taskmaster-events.jsonl): source of truth. Both processes append. Survives restarts.
  • Chatbus: real-time notification channel. Taskmaster posts suggestions to agent=taskmaster.
  • Fallback: if chatbus is down, supervisor polls the JSONL file on a 30-second interval.

Atomicity Guarantees

ConcernGuaranteeRationale
Single-writer appendAtomicLinux O_APPEND writes under ~4KB are atomic at the kernel level. Our event lines are small JSON — well under threshold.
Multi-writer appendNot guaranteedUnnecessary — each agent session is a single writer to its own log. Taskmaster writes to a separate events file.
Crash recoveryLast line may be partialReader skips malformed trailing line. All prior lines intact.
Durability (fsync)Buffered, not syncedAcceptable for activity tracking — not a database. Power loss may lose last few buffered writes.
Cross-agent coordinationVia chatbusJSONL handles per-agent ordered logs; chatbus handles real-time fan-out and coordination.

Key constraint: each process owns its own append stream. No two writers append to the same JSONL file concurrently, so the POSIX O_APPEND guarantee (atomic for writes ≤ PIPE_BUF, typically 4096 bytes) is sufficient.

3. Activity Detection

The taskmaster must know whether the supervisor is busy (don't interrupt) or idle (suggest work).

3.1 Available Signals

Signal 1: JSONL transcript modification rate. Claude Code writes tool calls to a JSONL transcript. Active: file growing (new lines in last 60 seconds). Idle: no new lines for >5 minutes.

Production data from GitHub Copilot at scale: median agent session has 15 LLM calls and 13 tool invocations. Container idle between turns averages 243 seconds (4 min). User idle between turns averages 1,512 seconds (25 min).

Signal 2: Chatbus message recency. Recent message (<2 min): engaged. No message (>10 min): may be idle.

Signal 3: Active teammate count. Teammates running: orchestrating. No teammates: idle or interactive.

Signal 4: Time since last user message. Recent (<5 min): actively directing. Stale (>30 min): may have stepped away.

Signal 5: Time of day. Outside working hours, more aggressive about suggesting autonomous work.

3.2 Activity Scoring Function

activity_score(signals) -> float [0.0 = idle, 1.0 = busy]

  jsonl_rate    = clamp(lines_per_minute / 5.0, 0, 1)      # 5+ lines/min = busy
  chat_recency  = clamp(1 - (seconds_since_chat / 600), 0, 1) # decays over 10 min
  user_recency  = clamp(1 - (seconds_since_user / 1800), 0, 1) # decays over 30 min
  teammate_load = clamp(active_teammates / 3.0, 0, 1)       # 3+ teammates = busy

  score = max(
    jsonl_rate * 0.5,           # tool activity is strongest signal
    chat_recency * 0.3,         # recent chat means engaged
    user_recency * 0.2,         # recent user message means directed
    teammate_load * 0.15        # teammates running = orchestrating
  )

  return score

Thresholds:

  • score > 0.4: Busy. Do not suggest. Only post status updates.
  • score 0.15 - 0.4: Light activity. Queue suggestion, deliver on next idle window.
  • score < 0.15: Idle. Suggest next work item.

3.3 Detection Implementation

Every 30 seconds:
  1. stat() the JSONL transcript → line count delta
  2. Read last chatbus message timestamp
  3. Count running teammate processes
  4. Read last user message timestamp from chatbus
  5. Compute activity_score()
  6. If score < threshold AND suggestion queued:
     → deliver suggestion via chatbus
  7. Write score + signals to state file for debugging

4. Work Suggestion Algorithm

4.1 Input: The Spore Intake Queue

Supervisor intake = spores where:
  state = "todo"
  assignee = "supervisor"
  NOT blocked (all blocked_by entries are done or absent)

4.2 Priority Ordering

score(spore) =
  priority_weight(spore.priority) * 100     # P0=500, P1=400, P2=300, P3=200
  + age_bonus(spore.created_at)              # +1 per day since creation, max 30
  + dependency_bonus(spore)                  # +50 if other spores are blocked on this one
  - rejection_penalty(spore)                 # -200 if rejected in last 2 hours
  - staleness_penalty(spore)                 # -100 if attempted and failed in last 24h

priority_weight:
  0 -> 500 (critical)
  1 -> 400 (high)
  2 -> 300 (medium)
  3 -> 200 (low)

dependency_bonus(spore):
  count = number of spores where spore.id is in their blocked_by
  return min(count * 25, 100)  # up to +100 for being a blocker

4.3 Dependency-Aware Scheduling

The taskmaster identifies "critical path" spores — those that unblock the most downstream work:

MCC-11.21 (system stable gate) ─── blocks ──► MCC-6.4 (Linear push sync)
                                                    │
                                                    └── blocks ──► MCC-6.5 (drift detection)

4.4 "Work in Advance" Suggestions

When the intake queue is empty or all items have been rejected:

  1. Spores in backlog state that could be promoted to todo if context has changed.
  2. Review-state spores that need PR review or merge.
  3. Stale in_progress spores where the worker may have crashed.
  4. GitHub issues not yet tracked as spores (via GitHub API scan).
  5. Code maintenance — test coverage gaps, stale branches, dependency updates.

4.5 Cooldown and Rejection Tracking

// data/taskmaster-state.json (rejection tracking)
{
  "rejected": {
    "MCC-11.9": {
      "rejected_at": "2026-11-18T14:30:00Z",
      "reason": "user: not now",
      "cooldown_hours": 2
    }
  },
  "last_suggestion_at": "2026-11-18T14:25:00Z",
  "suggestion_count_today": 7
}

Cooldown rules:

  • After rejection: 2-hour cooldown for that specific spore.
  • After any suggestion: 10-minute cooldown before next suggestion.
  • Daily cap: max 20 suggestions per day.
  • After 3 consecutive rejections: extend cooldown to 1 hour between any suggestions.

4.6 Suggestion Format

[TASKMASTER] Next: MCC-11.9 — Rebuild seed.html from seeds.json
Priority: 2 | Unblocks: nothing | Est: small
Accept? Or say "skip" / "later" / "not now"

Responses: accept (dispatch), skip (2-hour cooldown), later (re-queue), not now (1-hour global cooldown).

5. Recommended Architecture

5.1 Process Type: Go Shroom with claude --print

The taskmaster should be a Go shroom (service type) that periodically shells out to claude --print for reasoning steps. Not a persistent Claude session.

Rationale:

  • A persistent Claude session is expensive and unnecessary. The taskmaster needs periodic assessment (every 30-60 seconds), not continuous reasoning.
  • A Go service handles timers, file watching, chatbus integration, and GitHub API calls natively.
  • When LLM reasoning is needed ("is this spore still relevant?"), it shells out to claude --print with a focused prompt — the batch worker pattern proven by octocat.
  • Go services are cheap to run. A Claude session costs tokens per turn.

5.4 Communication Mechanism

Taskmaster → Supervisor:
  1. Append event to JSONL log
  2. Post chatbus message: agent=taskmaster, text="[suggestion details]"
  3. Supervisor receives via MCP chat-bridge

Supervisor → Taskmaster:
  1. Append event to JSONL log (accept/skip/reject)
  2. OR: supervisor writes to state file (simpler for v1)
  3. Taskmaster picks up on next poll cycle (30s)

5.5 Authority Model

Phase 1: Suggest-only. The taskmaster suggests work. All suggestions require explicit acceptance.

Phase 2: Auto-dispatch for low-risk. After trust is established, auto-dispatch spores that meet ALL of: priority ≥ 2, clear acceptance criteria, ≤ 3 files, passing tests, human idle >1 hour.

Phase 3: Full PM. The taskmaster manages the entire intake queue: triages, dispatches, monitors, updates spore state. Human involvement is limited to setting priorities and reviewing PRs.

6. Implementation Phases

Phase 1: Activity Monitor (1-2 days)

Go service that polls JSONL transcript, chatbus, teammate count every 30 seconds. Computes activity score. Writes data/taskmaster-state.json. No LLM calls, no suggestions — just observation.

Validates: Signal accuracy, polling overhead, state file format.

Phase 2: Intake Reader + Suggestion Engine (2-3 days)

Read active.json, apply intake filter, score and rank by priority + dependency bonus. When idle: post suggestion to chatbus. Cooldown tracking in state file.

Validates: Suggestion quality, timing accuracy, cooldown behavior.

Phase 3: Completion Tracking (1-2 days)

Observe supervisor activity: PR merges, commits, chatbus "done" messages. Match completed work to in-progress spores. Append completion events to JSONL log.

Validates: Work detection accuracy, spore lifecycle automation.

Phase 4: LLM-Assisted Triage (2-3 days)

When a spore's relevance is unclear, shell out to claude --print with the spore description + project context. Decisions: still relevant? ready to work? needs human input?

Validates: LLM triage quality, cost per triage cycle.

Phase 5: Auto-Dispatch (1-2 days)

Risk assessment function. Auto-dispatch qualifying spores: create branch, dispatch teammate, record in event log. Kill switch via state file flag.

Validates: Autonomous operation, trust model, error handling.

Phase 6: Dashboard Integration (1 day)

Surface taskmaster state in the supervisor dashboard. New tile showing: activity score, current suggestion, intake queue depth, recent completions.

Appendix A: Event Schema

type TaskmasterEvent = {
  ts: string;          // ISO 8601 timestamp
  from: "taskmaster" | "supervisor" | "human";
  type: EventType;
  spore?: string;      // spore ID (MCC-X)
  score?: number;      // suggestion score
  reason?: string;     // rejection reason, completion note
  pr?: string;         // PR number
  branch?: string;     // branch name
  meta?: Record<string, unknown>;
};

type EventType =
  | "suggest"          // taskmaster suggests a spore
  | "accept"           // supervisor accepts suggestion
  | "skip"             // supervisor skips (short cooldown)
  | "reject"           // supervisor rejects (long cooldown)
  | "later"            // supervisor defers (re-queue)
  | "dispatch"         // work dispatched to teammate
  | "completed"        // work completed
  | "triage"           // triage assessment recorded
  | "activity"         // activity score snapshot
  | "auto_dispatch"    // auto-dispatched (phase 5)
  | "config"           // configuration change
