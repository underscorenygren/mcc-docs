Message Flow: Seven Scenarios

How messages move through the system — from fast chat to voice round-trips, reconnection, barge-in, multi-agent routing, and work dispatch. Companion to Message Mechanics.

The state machine

Every message goes through these states. The sequence number is the anchor across all of them.

SENT → DELIVERED → PROCESSING → RESPONDED ↘ STALLED (no processing ack within threshold) ↓ escalation ladder kicks in
StateTriggerUI indicatorWhat the system knows
Sent Chatbus assigns seq N Single check Message is in the log, routed to agent
Delivered Channel acks seq N Double check Agent's channel server received it, queued for MCP
Processing Agent emits "processing N" Thinking indicator Claude has the message and is working on it
Responded Reply message referencing seq N Response displayed Done
Stalled Delivered but no processing ack within threshold "Agent busy" indicator Message is in the channel but agent hasn't picked it up

Key design point: every state transition is driven by an event with a sequence number, not a timer. Timers are only used for the escalation ladder (detecting stalls). The UI never guesses — it reflects actual system state.

Key: each agent has its own sequence space. Atlas is at seq 12 (long history), Porter starts at seq 1 (just woke up). The chatbus routes by agent name — each agent's stream is an independent log. The user's client subscribes to multiple streams simultaneously and merges them in display order.

The 2-second wake-up delay for Porter (5.0s to 7.0s) is visible in the ack flow: the chatbus accepts the message immediately (seq assigned), but the processing ack doesn't arrive until the agent is ready. With acks, the UI shows "Delivered, waking agent..." during this gap.

Same primitives, different use case. The auto-worker is just another consumer on the bus. The dispatch message gets a sequence number. The worker acks receipt, then sends periodic status updates back through the bus. The supervisor subscribes to the worker's outbound stream and sees progress in real time.

Today the supervisor dispatches via docker exec and polls logs to check if the worker received the job. With the stream library, dispatch is a publish to the worker's inbound stream, and receipt is an ack — same mechanism as chat delivery. The escalation ladder applies too: if no ack within 30s, the supervisor knows the worker is down.

Design insight: Work dispatch has stronger delivery requirements than chat. A lost chat message is annoying; a lost work order means a task silently doesn't happen. The stream library should support configurable delivery guarantees per stream — at-most-once for chat, at-least-once for work dispatch (retry until acked).

Summary: seven scenarios, one model

All seven scenarios use the same building blocks: sequence numbers, acks, typed messages, and per-agent streams. The differences are in configuration, not mechanism:

ScenarioStreamDeliveryKey insight
A: Fast response chat (agent) at-most-once Lag = 0, acks confirm immediately
B: Agent busy chat (agent) at-most-once Lag > 0 triggers escalation ladder
C: Voice chat + voice events at-most-once Voice signals (VAD, STT, TTS) on ephemeral event stream
D: Reconnect chat (agent) at-most-once + replay Sequence cursor makes replay gapless
E: Barge-in chat + voice events at-most-once Seq numbers track which message was interrupted
F: Multi-agent chat (per agent) at-most-once Independent sequence spaces per agent
G: Work dispatch work (worker) at-least-once Same ack model, stronger delivery guarantee

This is the core argument for the unified stream library: one set of primitives, configured per use case, replaces four ad-hoc connection types.
