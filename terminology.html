MCC Terminology

Project-specific language for Mushroom Cloud Computing. These terms have precise meanings that differ from their generic usage.

Why This Exists

We work across multiple systems (Linear, GitHub, chatbus, Claude Code) where words like "issue", "task", and "agent" mean different things depending on context. We also have voice as a primary interface, so terms need to be short, distinct, and unambiguous when spoken aloud. This glossary defines what each term means in our system specifically.

Work Items

Spore work
From mushroom biology — a spore carries everything needed to grow.

A spore is our canonical data object for a tracked piece of work between agent and human. It carries inline sources: GitHub URLs, Linear URLs, chatbus message IDs, commit hashes, and human-readable summaries of each. Sources are denormalized — copied at creation time, not looked up live.

A spore maps to a Linear issue for storage today, but the schema is ours and will evolve independently. Multiple source references per spore. Message IDs are preserved for future cross-referencing.

Maps to: Linear issue (current storage layer)
"Create a spore for the voice dropping bug."
"This spore has three sources: the GitHub issue, Erik's voice note, and the chatbus thread."
"Create a Linear issue" — use only when referring to the Linear service API specifically
"Create a task" — ambiguous (Claude Code tasks, mcc-tasks, Linear?)
"Spore this" verb

Synthesize the current conversation into a spore. The agent extracts the work item, attaches relevant sources (message IDs, links, quotes), and creates the spore with enough context to act on later. Like "commit" is to git — a single verb that packages current state into a durable record.

"Spore this — we decided to replace the chatbus HTTP layer."
"Spore this conversation about the stream library."

Agents & Workers

Shroom infra
Short for mushroom — grows in the background, part of the ecosystem.

A shroom is a background agent worker — a process that picks up work, executes it autonomously, and reports results. Shrooms are dispatched as teammates (via Claude Code's teammate/worktree system) and run without interactive supervision.

Previously, shrooms were self-hosted Docker containers subscribing to the chatbus. The teammate model replaced that: each shroom gets its own worktree, executes a focused prompt, and pushes results to a branch. The infra changed but the concept is the same — autonomous background work.

Implementation: Claude Code teammates (current), Docker containers (legacy)
"Dispatch a shroom to fix the auth bug on a branch."
"The four shrooms finished — three PRs ready for review."
"Background agent" — ambiguous
"Worker" — too generic, could mean anything
Supervisor role

The primary Claude Code session that the human interacts with directly. Receives messages via chat-bridge (voice, web, Slack), dispatches shrooms, manages state, reports status. There is one supervisor per session.

"The supervisor dispatched three shrooms and is waiting for results."
Agent role

A user-facing Claude agent with a named identity (Porter, Atlas, Runa). Has a portal page, wakes on demand, interacts conversationally with external users. Agents are not shrooms — they are interactive, not autonomous.

"Porter is an agent — users talk to him through his portal."
"The builder agent" — builder is a shroom, not an agent

Communication

Chatbus comm

The central message routing service. All chat messages (human, agent, shroom) flow through the chatbus. Messages have channels (supervisor, chat, agent-specific), directions (in/out), and are persisted to a JSONL ring buffer. The chatbus is the system of record for conversation history.

Service: cmd/chatbus/, port 9095
Sysbus comm

The system event bus. Carries lifecycle signals (session start, build status, deploy events, tool calls) — not chat messages. The UI activity feed reads from the sysbus. Fire-and-forget; never blocks work.

Service: cmd/sysbus/, port 9097
Chat-bridge comm

The MCP server that connects the supervisor to the web/voice UI. Messages from the human arrive here; the supervisor replies here. This is the canonical communication channel — every response must go through chat-bridge AND the terminal.

External Services

Linear service

The external issue tracking service at linear.app. We use it as a storage and sync layer for spores. When we say "push to Linear" or "sync to Linear", we mean the service. The data format (spore) is ours — Linear is one backend.

"Sync this spore to Linear."
"Check the Linear board for MCC priority."
"Create a Linear issue" when you mean "create a spore"
Seed service

The project inventory and task dashboard at tasks.mushroomcloudcomputing.com. Shows all projects, their status, and top-priority work. Built from mcc-tasks repo data.

Conventions

Naming Rules
  • Voice-first: terms must be short, distinct, and unambiguous when spoken. "Spore" vs "store" is borderline — context resolves it. "Shroom" is clear.
  • No overloading: if a word already means something in a system we use (GitHub, Linear, Claude Code), pick a different word.
  • Qualify external systems: say "GitHub issue", "Linear issue", "Claude Code task" when referring to those systems specifically. Our terms (spore, shroom) are unqualified.
  • Mushroom theme: preferred but not required. The name should fit naturally in conversation.
