Browser Testing Without a Browser

Testing browser-bound code server-side for a Rust-to-TypeScript stream/messaging library.

TL;DR: Make the state machine the contract. Test it exhaustively in Rust with proptest-state-machine. Transpile the state machine to TypeScript and run the same logical tests via vitest + happy-dom. The browser layer becomes a thin view that barely needs testing. WASM test runners and DOM emulation are useful for edge cases but not the primary strategy.

The Problem

A stream/messaging library needs to work across web browsers, React Native, and server-side runtimes. The core is written in Rust, transpiled to TypeScript. Testing the full matrix (Rust + TS + browser + mobile) with real browsers is expensive and fragile. Puppeteer/Playwright are heavy: 1-2 second cold starts per browser, 300-400MB Chromium downloads, and they test the wrong thing for a state machine library.

The question: what can you test without a browser, and where is the real boundary?

1. Server-Side DOM Emulation in Rust

Available Crates
Limited HTML parsing, not DOM simulation. Useful for testing markup output, not runtime behavior.

What exists

  • scraper (v0.27, May 2026) — CSS selectors over html5ever parse trees. Read-only queries, no event model.
  • kuchikikiki — tree manipulation (insert, remove, reorder nodes). Closest to a mutable DOM, but no events, no layout, no addEventListener.
  • html5ever — WHATWG-compliant HTML parser from Servo. Callback-driven, not tree-based. Foundation for scraper and kuchiki.

What they can do

  • Parse HTML strings into a tree structure
  • Query nodes with CSS selectors
  • Mutate the tree (kuchikikiki): insert, remove, replace nodes
  • Serialize back to HTML

What they cannot do

  • Events (addEventListener, dispatchEvent, bubbling/capture)
  • Any Web API: fetch, WebSocket, ReadableStream, MessageChannel
  • Layout, rendering, or CSS computation
  • Timer APIs (setTimeout, requestAnimationFrame)
Verdict: These crates test HTML structure, not runtime behavior. For a stream library that needs WebSocket, ReadableStream, and event dispatch, Rust DOM crates are the wrong tool. They would only help if you needed to test SSR output.

2. WASM Test Runners

wasm-bindgen-test + wasm-pack
Viable Real browser APIs, lightweight headless execution. Good for integration verification.

How it works

wasm-pack test --headless --chrome compiles your Rust to WASM, spins up a headless browser, loads the WASM module, and runs annotated test functions inside the browser context. The test harness is minimal — no Puppeteer, no Node.js test runner, just a small HTML page that loads your WASM and reports results. 

use wasm_bindgen_test::*;

wasm_bindgen_test_configure!(run_in_browser);

#[wasm_bindgen_test]
async fn stream_reconnect() {
    let ws = WebSocket::new("ws://localhost:9090").unwrap();
    // Test actual browser WebSocket behavior
    // Assert state machine transitions
}

Limitations

  • Still requires a browser binary (Chrome, Firefox) — not truly browserless
  • WASM stack traces are harder to debug than native Rust
  • Cannot test the transpiled TypeScript — tests the Rust-as-WASM, which is a different artifact
  • No React Native coverage
Verdict: Good for verifying that your Rust code works correctly when compiled to WASM and run in a real browser. Use it as an integration check, not the primary test strategy. It does not help test the transpiled TypeScript output.

3. Happy-DOM / jsdom for TypeScript

happy-dom with vitest
Recommended 2-4x faster than jsdom. Sufficient for testing transpiled TS stream logic.

What happy-dom provides

  • DOM manipulation: document.createElement, querySelector, tree mutations
  • Events: addEventListener, dispatchEvent, bubbling, CustomEvent
  • fetch API (mocked or real via undici)
  • setTimeout, setInterval, requestAnimationFrame
  • MutationObserver, IntersectionObserver (basic)
  • WebSocket (basic implementation)

What is missing or incomplete

  • ReadableStream / WritableStream — partial or missing (depends on version)
  • MessageChannel / MessagePort — may not be implemented
  • BroadcastChannel — missing in happy-dom, present in jsdom
  • CSS layout computation — no getBoundingClientRect, offsetWidth
  • HTMLOptionElement, Selection API — known gaps
  • Event sequencing edge cases — form submission, focus/blur order
  • Service Workers, Web Workers — not available

Strategy for stream library testing

For a stream/messaging library, the critical APIs are WebSocket, custom events, and possibly ReadableStream. happy-dom covers WebSocket and events. For streams, you have options:

  • Use Node.js built-in ReadableStream (available since Node 18) — vitest runs on Node
  • Mock the stream interface at the boundary
  • Fall back to jsdom for specific test files: // @vitest-environment jsdom
Verdict: happy-dom + vitest is the right environment for testing transpiled TypeScript. Set it as default, drop to jsdom per-file when you hit gaps. For a stream library, you will likely need to mock or polyfill ReadableStream — but that is a thin wrapper, not core logic.

4. State Machine as the Testing Boundary

proptest-state-machine
Recommended The highest-leverage approach. Test the core exhaustively, make the browser layer trivial.

The architecture

┌─────────────────────────────────────────────────────────┐ │ State Machine (Rust) │ │ │ │ States: Disconnected, Connecting, Connected, │ │ Reconnecting, Draining, Closed │ │ │ │ Transitions: open, message, error, close, timeout, │ │ ack, nack, heartbeat_miss, resume │ │ │ │ Properties tested: │ │ - No message sent in Disconnected state │ │ - Reconnect backoff increases monotonically │ │ - Buffer never exceeds capacity │ │ - Every sent message eventually acked or nacked │ │ - State is always reachable from any error state │ └──────────────────────┬──────────────────────────────────┘ │ transpile ▼ ┌─────────────────────────────────────────────────────────┐ │ State Machine (TypeScript) │ │ │ │ Same states, same transitions, same properties │ │ Tested via vitest with identical fixtures │ └──────────────────────┬──────────────────────────────────┘ │ ┌────────────┼────────────┐ ▼ ▼ ▼ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ Browser │ │ React │ │ Node.js │ │ thin │ │ Native │ │ server │ │ view │ │ thin │ │ thin │ │ layer │ │ view │ │ adapter │ └──────────┘ └──────────┘ └──────────┘

proptest-state-machine in practice

The proptest-state-machine crate (part of the proptest ecosystem) automates stateful property testing. You define a reference state machine with states and transitions, then the framework generates random sequences of transitions and checks that invariants hold after every step. 

use proptest_state_machine::*;
use proptest::prelude::*;

#[derive(Clone, Debug)]
enum StreamState { Disconnected, Connecting, Connected, Reconnecting }

#[derive(Clone, Debug)]
enum Transition { Open, Message(Vec<u8>), Error(u16), Close, Timeout }

impl ReferenceStateMachine for StreamSpec {
    type State = StreamState;
    type Transition = Transition;

    fn init_state() -> BoxedStrategy<Self::State> {
        Just(StreamState::Disconnected).boxed()
    }

    fn transitions(state: &Self::State) -> BoxedStrategy<Self::Transition> {
        match state {
            StreamState::Disconnected => Just(Transition::Open).boxed(),
            StreamState::Connected => prop_oneof![
                any::<Vec<u8>>().prop_map(Transition::Message),
                (400u16..600).prop_map(Transition::Error),
                Just(Transition::Close),
            ].boxed(),
            // ... other states
        }
    }

    fn apply(state: Self::State, transition: &Self::Transition) -> Self::State {
        // Pure state transition logic — no I/O, no DOM
    }
}

// Postconditions checked after every transition:
fn check_invariants(ref_state: &StreamState, sut: &RealStream) {
    assert_eq!(sut.can_send(), matches!(ref_state, StreamState::Connected));
    assert!(sut.buffer_len() <= MAX_BUFFER);
    // ... more invariants
}

What this buys you

  • Automatic shrinking — when a property fails, proptest finds the minimal transition sequence that reproduces it
  • Exhaustive edge cases — rapid disconnect/reconnect, message during reconnect, error during drain
  • Regression seeds — failing cases are persisted to .proptest-regressions and re-run on every cargo test
  • Speed — hundreds of random sequences per second, pure Rust, no I/O
  • Platform independence — the state machine has no browser dependency

The thin view layer

If the state machine is the contract, the browser layer reduces to:

  • Bind a real WebSocket to the state machine's open/message/error/close inputs
  • Read state machine output (send buffer, connection status) and apply to the transport
  • Wire up reconnect timers

This layer is 50-100 lines of glue code. It barely needs testing — and what testing it needs is a simple integration check, not exhaustive property testing.

Verdict: This is the right primary strategy for a stream/messaging library. The state machine captures all the hard logic (reconnect, backoff, buffering, ordering, delivery guarantees). Property-based testing finds edge cases that manual tests never would. The browser layer becomes trivially simple.

5. Cross-Platform Test Strategy

Shared fixtures, multiple runners
Recommended JSON fixtures as the lingua franca between Rust and TypeScript test suites.

Golden file / fixture testing

The ODIN Golden Tests project demonstrates this at scale: 159 JSON fixture files tested across TypeScript, Rust, .NET, Java, Python, and Ruby. The pattern: 

tests/
  fixtures/
    reconnect-backoff.json        # input sequence + expected states
    message-ordering.json
    buffer-overflow.json
    concurrent-close.json
  rust/
    src/lib.rs                    # reads fixtures, runs against Rust SM
  ts/

6. Existing Frameworks Survey

Deno
Limited No built-in DOM. Uses deno-dom (WASM or native backend). Similar coverage to happy-dom. Not a meaningful advantage over vitest + happy-dom for this use case.
Tauri
Limited Tests split into Rust unit tests (backend) and WebDriver E2E (frontend). Cross-platform webview testing is painful — three rendering engines (WebKit, WebView2, WebKitGTK). A tauri-plugin-playwright exists but requires browser binaries. Tauri's problem is different from ours: they must test native webview integration, we do not.
wasm-bindgen-test-runner
Viable Part of wasm-pack test. Supports headless Chrome/Firefox, dedicated/shared/service workers, and Deno as a target. Lightweight relative to Puppeteer — reuses an existing browser binary, no npm dependency tree. Good for WASM integration checks.
Vitest 4 Browser Mode
Viable Vitest 4 introduced a browser mode that runs tests in a real browser without Playwright's full overhead. Uses Vite's dev server to serve tests directly. Lower overhead than Playwright, higher fidelity than happy-dom. Worth evaluating if happy-dom gaps become blocking.
proptest-stateful (ReadySet)
Viable Alternative to proptest-state-machine, from the ReadySet team (database company). Similar API, different ergonomics. Both are built on proptest. Choose based on which API feels better.

Recommendation

The state machine approach is the right call for a stream/messaging library. Here is why, and how to structure it.

Why state machine first

A stream/messaging library's complexity is almost entirely in state management: reconnection logic, message buffering, delivery guarantees, ordering, backpressure, error recovery. These are pure functions of (current state + input) -> (next state + effects). None of this requires a DOM.

The browser/mobile layer is a thin adapter: bind platform-specific transport (WebSocket, React Native TCP) to the state machine inputs, and apply state machine outputs (send buffer, timers) to the platform. This adapter is simple enough to verify with a handful of integration tests.

Concrete test pyramid

╱╲ ╱ ╲ ╱ E2E╲ wasm-pack test --headless ╱ (few)╲ Smoke test: real browser, real WS ╱────────╲ ╱Integration╲ vitest + happy-dom ╱ (moderate) ╲ TS glue: WebSocket binding, timers ╱───────────────╲ ╱ State Machine ╲ cargo test + proptest-state-machine ╱ (exhaustive) ╲ + vitest with shared JSON fixtures ╱──────────────────────╲

Implementation order

  1. Define the state machine in Rust. States, transitions, invariants. Write property-based tests with proptest-state-machine. Target: hundreds of random transition sequences, checking invariants after every step.
  2. Export golden fixtures. Run the Rust state machine against hand-crafted scenarios, serialize the (input, state-trace) pairs to JSON. These become the cross-platform conformance suite.
  3. Transpile to TypeScript. Run the same JSON fixtures against the TS state machine in vitest. Any divergence is a transpilation bug.
  4. Write thin platform adapters. Browser adapter (WebSocket + DOM timers), React Native adapter, Node.js adapter. Each is small enough to test with a few integration tests in the appropriate environment (happy-dom, Jest, etc.).
  5. Optional: wasm-pack smoke tests. Compile to WASM, run a few end-to-end scenarios in headless Chrome to verify the WASM build works. Not the primary quality gate.

What you skip

  • Puppeteer/Playwright — too heavy, tests the wrong layer
  • Rust DOM crates — wrong tool (parsing, not runtime simulation)
  • Deno DOM — no advantage over happy-dom for this use case
  • Full browser E2E for every test — state machine catches the bugs, browser just confirms wiring

Risk to watch

The thin adapter assumption breaks if the platform layer becomes complex. Watch for:

  • Platform-specific WebSocket quirks (mobile network transitions, background/foreground)
  • Timer precision differences (React Native timers vs browser timers)
  • Backpressure behavior differences across transports

If the adapter grows beyond ~200 lines per platform, it is no longer "thin" and needs its own test strategy. At that point, consider Vitest 4 browser mode for web and platform-specific integration tests for mobile.
