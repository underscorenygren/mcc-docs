Redis Streams Migration

Chatbus replacement analysis — current architecture, Redis Streams mapping, migration path, and code examples.

Current Go Chatbus Architecture

What it does

The chatbus is an HTTP-based message bus that routes chat messages between agents, users, and the web UI. It provides:

  1. Publish/subscribe messaging via HTTP endpoints
  2. Message persistence to a JSONL file on disk
  3. In-memory ring buffer for fast queries (default 20,000 envelopes)
  4. Channel-based routing (messages carry channel, agent, direction fields)
  5. Agent proxying — forwards messages to agent HTTP endpoints, records request/response
  6. Long-poll subscriptions — clients block up to 30s waiting for new messages
  7. Deduplication — 5-minute TTL dedup cache keyed on agent+id or agent+from+text
  8. Bridge push — outbound messages are POSTed to the bridge for WebSocket delivery

Message storage details

On-disk: Append-only JSONL file at data/chatbus/bus-messages.jsonl. Currently 186K lines (~95MB). Each line is a full Envelope JSON object. On startup, the tail (up to BUS_RING_SIZE) lines are loaded into memory.

In-memory: Go slice acting as a ring buffer (default 20,000 entries). When capacity is exceeded, the oldest entries are dropped from memory (but remain on disk). A monotonic Seq counter is assigned on append — this is the primary cursor for subscription polling.

Compaction: Store.Compact() method exists to rewrite the file, archiving old entries. Intended for cron but not actively wired up.

Guarantees

PropertyCurrent behavior
OrderingSingle-writer append, monotonic Seq — total order within the process
PersistenceSynchronous file append on every publish (no fsync, but OS buffers)
ReplayRing buffer in memory (last 20K). On-disk file has full history but is only read at startup
DeliveryAt-most-once in-process dispatch. Long-poll clients may miss messages if they disconnect between polls
Dedup5-minute TTL cache, max 500 entries, keyed on content hash
AvailabilitySingle process, no replication. Container restart loses in-flight state

What Redis Streams Would Replace

Core concept mapping

Redis Streams is a log data structure. Each stream is an append-only sequence of entries with auto-generated IDs (timestamp-based, e.g. 1699012345678-0). Consumer groups provide exactly-once delivery semantics.

Current chatbus conceptRedis Streams equivalent
EnvelopeStream entry (field-value pairs)
Channel fieldSeparate Redis stream key per channel (e.g. bus:chat, bus:work) or single stream with field-based filtering
Seq (monotonic counter)Redis stream ID (auto-assigned, monotonic)
Ring buffer (20K entries)MAXLEN ~20000 on XADD — Redis trims automatically
JSONL file persistenceRedis AOF/RDB persistence — built-in
Store.Append()XADD stream_key * field1 val1 field2 val2
Store.Query()XRANGE stream_key start end COUNT limit
/subscribe long-pollXREAD BLOCK 30000 STREAMS stream_key $ (blocking read) or consumer groups
In-process Subscribers.Dispatch()Consumer groups: XREADGROUP GROUP name consumer BLOCK 30000 STREAMS key >
Dedup middlewareApplication-level: SET key NX EX 300

Migration Path

Phase 1: Add Redis container

# docker-compose.yml addition
redis:
  image: redis:7-alpine
  mem_limit: 128m
  volumes:
    - redis-data:/data
  command: redis-server --appendonly yes --maxmemory 100mb --maxmemory-policy noeviction
  expose:
    - "6379"
  restart: unless-stopped
  profiles:
    - prod

Add REDIS_URL=redis://redis:6379 to the chatbus environment. Self-hosting Redis 7 Alpine is ~30MB memory at idle.

Phase 2: Replace Store with Redis-backed implementation

Create pkg/provider/bus/redis_store.go implementing the same interface as Store:

// Sketch — not production code
type RedisStore struct {
    client *redis.Client
    prefix string  // "bus:" — stream key prefix
}

func (s *RedisStore) Append(env Envelope) {
    data, _ := json.Marshal(env)
    s.client.XAdd(ctx, &redis.XAddArgs{
        Stream: s.prefix + env.Channel,
        MaxLen: 20000,
        Approx: true,
        Values: map[string]interface{}{
            "data":      string(data),
            "agent":     env.Agent,
            "direction": env.Direction,
            "from":      env.From,
        },
    })
}

func (s *RedisStore) Query(opts QueryOpts) []Envelope {
    // XRANGE with filtering by agent/channel
}

Phase 3: Replace long-poll with XREAD BLOCK

The /subscribe handler currently uses Store.Wait() (a Go channel-based notification). Replace with:

// Blocking read — Redis handles the wait
results, _ := client.XRead(ctx, &redis.XReadArgs{
    Streams: []string{streamKey, lastID},
    Block:   30 * time.Second,
    Count:   50,
})

Simpler and more efficient than the current approach (which wakes all waiters on any message, then each waiter re-queries and filters).

Phase 4: Consumer groups for service subscribers

Services currently long-poll via busclient.Subscribe(). Replace with Redis consumer groups for guaranteed delivery:

XGROUP CREATE bus:work builder-group 0 MKSTREAM
XREADGROUP GROUP builder-group builder-1 BLOCK 30000 STREAMS bus:work >
XACK bus:work builder-group <id>

This gives exactly-once processing semantics — if a consumer crashes before ACKing, the message is re-delivered to another consumer in the group.

Phase 5: Dedup via Redis

// SET NX with TTL — atomic check-and-set
set, _ := client.SetNX(ctx, "dedup:"+key, "1", 5*time.Minute).Result()
if !set {
    // duplicate
}

What stays

  1. HTTP API (server.go handlers) — thin wrapper, calls Redis instead of Go store
  2. Agent routing (main.go agentSendHandler) — pure routing logic, storage-agnostic
  3. Envelope type (envelope.go) — application-level type, serialized to/from Redis
  4. Bridge push (OnPublished callback) — side effect, storage-agnostic
  5. pkg/busclient — HTTP client for services that prefer HTTP over direct Redis

What changes

  1. Store backend — JSONL file + Go slice replaced by Redis XADD/XRANGE
  2. Subscription mechanism — Go channels + long-poll replaced by XREAD BLOCK
  3. Dedup — In-memory map replaced by Redis SET NX
  4. Persistence — JSONL file replaced by Redis AOF. The data/chatbus/bus-messages.jsonl file is retired.
  5. Compaction — No longer needed. Redis MAXLEN handles stream trimming automatically.

TypeScript SDK quality

ioredis (the standard Node.js Redis client) has full Redis Streams support: xadd, xread, xrange, xreadgroup, xack — all available. Blocking reads work natively. TypeScript types included. Widely used in production (>13K GitHub stars).

The web UI's shared/core/chatbus/send.ts currently POSTs to the HTTP API. It can continue doing so. For future optimization, a direct Redis-backed WebSocket transport could replace the HTTP round-trip entirely.

Self-hosting complexity

  • Memory: ~30MB idle, ~100MB with 20K messages (configurable via maxmemory)
  • Disk: AOF persistence, auto-rewrite. Comparable to current JSONL but with built-in compaction
  • Monitoring: redis-cli INFO for stats, XLEN for stream sizes
  • Backup: Copy the AOF/RDB file, or BGSAVE
  • Failure mode: Single instance, same as current chatbus. If Redis dies, chatbus dies. No worse than today.

    env.Stamp()

        case ch <- struct{}{}:

        }

2. Querying messages

Before — Go (store.go:231-254) — O(N) linear scan 
func (s *Store) Query(opts QueryOpts) []Envelope {
    s.mu.RLock()
    defer s.mu.RUnlock()

    var result []Envelope
    for _, env := range s.envelopes {
        if opts.Agent != "" && env.Agent != opts.Agent {
            continue
        }
        if opts.Channel != "" && env.Channel != opts.Channel {
            continue
        }
        if opts.SinceSeq > 0 && env.Seq <= opts.SinceSeq {
            continue
        }
        result = append(result, env)
    }
    if opts.Limit > 0 && len(result) > opts.Limit {
        result = result[len(result)-opts.Limit:]
    }
    return result
}
After — Go with Redis — O(log N) range query 
func (s *RedisStore) Query(opts QueryOpts) ([]Envelope, error) {
    start := "-"
    if opts.SinceSeq > 0 {
        start = fmt.Sprintf("%d", opts.SinceSeq)
    }
    msgs, err := s.client.XRange(ctx, "bus:"+opts.Channel, start, "+").Result()
    if err != nil {
        return nil, err
    }
    var result []Envelope
    for _, msg := range msgs {
        var env Envelope
        json.Unmarshal([]byte(msg.Values["data"].(string)), &env)
        if opts.Agent != "" && env.Agent != opts.Agent {
            continue  // field filtering still needed
        }
        result = append(result, env)
    }
    if opts.Limit > 0 && len(result) > opts.Limit {
        result = result[len(result)-opts.Limit:]
    }
    return result, nil
}
After — TypeScript with ioredis 
async function query(channel: string, opts: { since?: string; limit?: number }): Promise<Envelope[]> {
    const start = opts.since ?? '-';
    const count = opts.limit ?? 100;
    const results = await redis.xrange(`bus:${channel}`, start, '+', 'COUNT', count);
    return results.map(([id, fields]) => ({
        ...JSON.parse(fields[1]),  // fields = ['data', '{json}']
        streamId: id,
    }));
}

3. Subscribing (blocking wait for new messages)

Before — Go (busclient/client.go:120-173) — HTTP long-poll loop 
func (c *Client) Subscribe(ctx context.Context, agent string, handler func(Message)) error {
    longClient := &http.Client{Timeout: 45 * time.Second}
    var cursor time.Time

    for {
        if ctx.Err() != nil {
            return ctx.Err()
        }
        q := url.Values{}
        q.Set("agent", agent)
        if !cursor.IsZero() {
            q.Set("since", cursor.Add(time.Nanosecond).UTC().Format(time.RFC3339Nano))
        }
        q.Set("timeout", "30s")

        req, _ := http.NewRequestWithContext(ctx, http.MethodGet,
            c.BaseURL+"/subscribe?"+q.Encode(), nil)
        resp, err := longClient.Do(req)
        if err != nil {
            time.Sleep(2 * time.Second)
            continue
        }
        var body listResponse
        json.NewDecoder(resp.Body).Decode(&body)
        resp.Body.Close()

        for _, msg := range body.Messages {
            handler(msg)
            if msg.Timestamp.After(cursor) {
                cursor = msg.Timestamp
            }
        }
    }
}
After — Go with Redis consumer groups (exactly-once delivery) 
func Subscribe(ctx context.Context, redis *redis.Client,
    group, consumer, stream string, handler func(Envelope)) error {
    // Create consumer group (idempotent)
    redis.XGroupCreateMkStream(ctx, stream, group, "0")

    for {
        if ctx.Err() != nil {
            return ctx.Err()
        }
        results, err := redis.XReadGroup(ctx, &redis.XReadGroupArgs{
            Group:    group,
            Consumer: consumer,
            Streams:  []string{stream, ">"},
            Block:    30 * time.Second,
            Count:    10,
        }).Result()
        if err != nil {
            continue  // timeout or transient error
        }
        for _, msg := range results[0].Messages {
            var env Envelope
            json.Unmarshal([]byte(msg.Values["data"].(string)), &env)
            handler(env)
            redis.XAck(ctx, stream, group, msg.ID)  // acknowledge
        }
    }
}

After — TypeScript with ioredis 
async function subscribe(
    group: string,
    consumer: string,
    stream: string,
    handler: (env: Envelope) => Promise<void>,
): Promise<void> {
    // Create group (ignore error if exists)
    await redis.xgroup('CREATE', stream, group, '0', 'MKSTREAM').catch(() => {});

    while (true) {
        const results = await redis.xreadgroup(
            'GROUP', group, consumer,
            'BLOCK', 30000,
            'COUNT', 10,
            'STREAMS', stream, '>',
        );
        if (!results) continue;  // timeout
        for (const [, messages] of results) {
            for (const [id, fields] of messages) {
                const env: Envelope = JSON.parse(fields[1]);
                await handler(env);
                await redis.xack(stream, group, id);
            }
        }
    }
}

Before — Go (store.go:264-287) — manual channel-based waiter 
func (s *Store) Wait(done <-chan struct{}) bool {
    ch := make(chan struct{}, 1)
    s.subMu.Lock()
    s.waiters = append(s.waiters, ch)
    s.subMu.Unlock()

    defer func() {
        s.subMu.Lock()
        for i, w := range s.waiters {
            if w == ch {
                s.waiters = append(s.waiters[:i], s.waiters[i+1:]...)
                break
            }
        }
        s.subMu.Unlock()
    }()

    select {
    case <-ch:
        return true
    case <-done:
        return false
    }
}

Tradeoffs

Gains from migration

  1. Exactly-once delivery via consumer groups (current system is at-most-once)
  2. No startup JSONL scan — Redis loads its own state, no 186K-line file parse
  3. Efficient blocking reads — XREAD BLOCK is cheaper than HTTP long-poll
  4. Built-in stream trimming — no manual compaction needed
  5. Query by ID range — O(log N) vs current O(N) linear scan
  6. ~500 lines of Go code deleted — store, subscribe, middleware, file I/O
  7. Multi-consumer parallelism — consumer groups allow scaling subscribers without code changes

Costs

  1. New dependency — Redis container in docker-compose (~30MB memory)
  2. Operational surface — Redis needs monitoring (memory, AOF size, connection count)
  3. Migration work — estimated 2-3 days to implement, test, and cut over
  4. Single point of failure — Redis replaces the JSONL file but is equally a SPOF
  5. Filtering limitations — Redis Streams doesn't filter by field values natively. Separate streams per channel is the natural fit.

Recommendation

The migration is justified if consumer group semantics (exactly-once delivery, pending message tracking) are needed — which they are for reliable work dispatch to builder, scheduler, and tester. The current at-most-once long-poll means a builder crash during a build command can silently drop the message.

For the current scale (~186K messages total, ~15 services), the operational cost of Redis is minimal and the code simplification is significant. The HTTP API stays as a backward-compatible wrapper, so no consumer code changes are required in Phase 1.
