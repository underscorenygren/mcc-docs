State: Fundamentals

Where state lives in our system, how it flows, and the vision for executable scenarios that double as documentation and tests.

Last updated: 2026-10-16

The question

Our system has state scattered across multiple boundaries: the mobile/web client, the bridge server, the chatbus, the sysbus, and each agent's Claude session. Messages flow between them, but there's no formal model for what state exists where, who owns it, or how we prove it's correct.

The goal: formalize state into something we can visualize, execute, and test — using the same language for all three.

Current state landscape

Where state lives today

Client
Orchestrator
Voice state (recording, processing, speaking), chat messages, connection status, current agent. Mutable object with emitState() broadcasts. ~20 boolean/string fields.
Client
Event Bus
Pub/sub with sticky values. Cross-component glue. No schema — any string event, any payload. ~40 distinct event types today.
Server
Bridge
WebSocket connection state, audio pipeline state (STT/TTS in-flight), session auth. Per-connection, in-memory, lost on restart.
Bus
Chatbus
Message history (JSONL per agent). Ring buffer in memory, append-only on disk. The closest thing to a "log" — but no sequence numbers yet.
Bus
Sysbus
Tool-call events, lifecycle signals. Fire-and-forget, no persistence. Consumed by UI for activity feed. Ephemeral.
Agent
Claude session
Conversation context, tool state, in-progress work. Opaque to us — we see inputs and outputs but not internal state.

How state flows

State changes propagate through messages, not shared memory. The client doesn't read server state directly — it receives WebSocket messages that it interprets into local state. The bridge doesn't read agent state — it receives bus messages. This is already message-passing, but it's implicit and untyped. 

User speaks → client PCM → bridge STT → transcription message → client state update
                                       → chatbus publish → agent receives
                                       → agent reply → chatbus → bridge → client TTS

Each arrow is a state transition, but we don't model it that way. We model it as "send a message and hope the other side does the right thing."

The problems

1. No single source of truth

The client thinks it's recording. The bridge thinks the connection is idle. The chatbus has a message the client hasn't seen yet. These states can diverge, and we have no mechanism to detect or reconcile the divergence.

2. State is mutable and implicit

The orchestrator is a bag of mutable variables (recording, vadSpeaking, ttsDeferred, micStarting). Transitions happen as side effects of message handlers. There's no state machine — just conditionals checking combinations of flags.

3. No replay / time-travel

When something goes wrong, we can't reconstruct what happened. The bus events are ephemeral (sysbus) or append-only without cursors (chatbus). The client state is gone when you refresh.

4. Can't test state transitions

We test behavior ("send audio, get transcription") but not state ("after two messages with a delayed ack, the client is in state X and the server is in state Y"). The state machine is invisible.

The vision: executable scenarios

North star

A scenario is a sequence of events with state assertions at each step. The same scenario definition serves three purposes:

  1. Documentation — renders as a visual timeline showing messages and state
  2. Test — runs against real client + server code, asserts state at each step
  3. Proof — if the test passes, the visual is guaranteed accurate

The scenario language is declarative: "send message A, wait 100ms, send message B, assert client state is X, assert server state is Y." The runtime executes it against our actual orchestrator and bus code.

What a scenario might look like:

scenario "reconnect with missed messages":
  # Setup
  client connects to bridge
  assert client.state == { connected: true, chatLoaded: false }

  # History replay
  bridge sends history_end
  assert client.state == { connected: true, chatLoaded: true }

  # Normal message
  user sends "hello"
  assert chatbus.messages.length == 1

  # Disconnect
  bridge drops connection
  assert client.state == { connected: false }

  # Reconnect with replay
  client reconnects with since: last_message_time
  bridge replays missed messages
  bridge sends history_end
  assert client.state == { connected: true, chatLoaded: true }
  assert client.messages == chatbus.messages  # no duplicates, no gaps

This scenario is simultaneously a spec, a diagram source, and a test. The visual rendering shows the timeline with state boxes at each assertion point. The test runner executes the real code and checks the assertions.

Informing models

We're not inventing this from scratch. Several established patterns inform how we might formalize state:

Event Sourcing
Greg Young, Martin Fowler
State is derived from an append-only log of events. You never mutate state directly — you append an event, and the current state is computed by replaying events from the beginning. Relevant: our chatbus is already an append-only log. If we treat bus messages as the source of truth, client state becomes a projection of the event stream.
The Log: What every software engineer should know
Jay Kreps (LinkedIn / Confluent), 2013
The log is the fundamental data structure for distributed systems. Every database, message queue, and replication system is built on ordered, append-only logs. Relevant: our stream library design (L0-L5 layers) is directly informed by this. The log IS the state — everything else is a materialized view.
Read the original
Elm Architecture / Redux
Evan Czaplicki / Dan Abramov
Unidirectional data flow: (state, action) → newState. State is immutable. Every transition is an explicit action. Time-travel debugging comes for free because you can replay actions. Relevant: our orchestrator could be modeled this way — each bus event is an action, the state is a pure function of the action history.
Rust ownership / borrow checker
Rust lang
State has exactly one owner at a time. Mutations require exclusive access. The compiler proves at build time that no data races exist. Relevant: the principle that state ownership should be explicit. Who owns the "recording" flag — the client, the bridge, or the bus? In our system, ownership is ambiguous. Making it explicit (like Rust forces you to) would eliminate entire categories of bugs.
CRDTs (Conflict-free Replicated Data Types)
Shapiro et al.
Data structures that can be replicated across nodes and merged without conflicts. Eventual consistency without coordination. Relevant: if client and server both maintain state, their states will diverge during network partitions. CRDTs give us a framework for thinking about how to merge them back — though we may not need full CRDTs if we pick the right ownership model.
TLA+ / Formal specification
Leslie Lamport
Specify the set of valid states and transitions. A model checker exhaustively explores all possible interleavings to find bugs. Relevant: our executable scenarios are a lightweight version of this. We're not doing full model checking, but we're specifying valid state transitions and checking them against real code.

Where this connects

This exploration feeds directly into several ongoing efforts:

  • Message Mechanics — the message flow patterns are the events that drive state transitions. Sequence numbers (decided there) give us the ordered log we need.
  • Stream Library — the L0-L5 layer model is the infrastructure for typed, ordered, replayable events. State becomes a materialized view of the stream.
  • Typed state events — the planned refactor from OrchestratorState into per-domain bus events (VoiceState, ChatState, AgentState) is the first step toward making state transitions explicit and observable.

Next steps

  • Scenarios doc — pick 3-4 concrete scenarios (reconnect, interruption, agent switch) and write them in the executable format
  • State ownership map — for each piece of state, declare who owns it and how it propagates
  • Prototype runner — a minimal JS harness that can execute a scenario against the real orchestrator + a mock bus, rendering the timeline
