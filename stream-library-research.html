Stream & Messaging Library Survey

Evaluating TypeScript stream and messaging libraries as alternatives to the custom chatbus. Context: low-volume multi-agent system, ~10 agents, self-hosted, Redis already in the stack plan.

Last updated: 2026-10-17 — Part of Message Mechanics series — GitHub #238, #239

TL;DR Recommendation

Use Redis Streams via ioredis. It delivers ordered, persistent, replayable messaging with consumer groups out of the box. Redis is already the planned infrastructure layer. ioredis has first-class TypeScript types, 11M+ weekly downloads, and active maintenance. The chatbus HTTP pub/sub can be replaced with direct XADD/XREADGROUP calls — fewer moving parts, built-in durability, trivial self-hosting.

Second choice: BullMQ (also Redis-backed) if we later need job scheduling, retries, or rate limiting on top of messaging. It builds on ioredis and adds a job-queue abstraction.

Skip: Kafka/Redpanda (operational overhead for low volume), NATS (another server to run with no persistence by default), RxJS (in-process only, no durability).

Evaluation Criteria

Each library is evaluated on seven dimensions relevant to this project:

Criterion Why it matters
Ordering Agents process messages sequentially. Out-of-order delivery breaks conversation flow.
Persistence Messages must survive restarts. The current chatbus loses everything on process death.
Consumer groups Multiple workers need to process different message types without duplication.
TS SDK quality First-class types, active maintenance, large user base reduce integration risk.
Self-hosting Everything runs on one machine. Complex clustering or JVM dependencies are disqualifying.
Message replay Agents need to catch up on missed messages after restart or crash.
Low-volume fit ~100 messages/minute peak. Solutions designed for millions/sec add unnecessary complexity.

1. Redis Streams (Top Candidate)

Redis Streams (XADD/XREAD/XREADGROUP) is a log-based data structure built into Redis since 5.0. It provides ordered, persistent, replayable message streams with consumer groups as a first-class primitive. This is the top candidate because Redis is already the planned infrastructure for this project.

ioredis

Top Pick ioredis
npm: ~13M weekly downloads • TypeScript: built-in types • License: MIT • Redis Streams docs

The dominant Redis client for Node.js. Full Redis Streams support via raw commands: xadd, xread, xreadgroup, xack, xlen, xrange, xinfo.

Types are comprehensive — command return types are correctly typed, pipeline and cluster modes work out of the box. The API mirrors Redis commands directly, so Redis documentation applies 1:1. 

import Redis from 'ioredis';
const redis = new Redis();

// Publish
await redis.xadd('chat:supervisor', '*', 'from', 'user', 'text', 'deploy bridge');

// Consumer group setup (once)
await redis.xgroup('CREATE', 'chat:supervisor', 'workers', '0', 'MKSTREAM');

// Consume
const messages = await redis.xreadgroup(
  'GROUP', 'workers', 'worker-1',
  'COUNT', 10, 'BLOCK', 5000,
  'STREAMS', 'chat:supervisor', '>'
);

// Acknowledge
await redis.xack('chat:supervisor', 'workers', messageId);

node-redis (official)

Good @redis/client (node-redis v4)
npm: ~5M weekly downloads • TypeScript: built-in • License: MIT • Maintained: Redis Inc.

The official Redis client, rewritten in v4 with TypeScript from the ground up. Streams API is available but uses a more abstracted interface than ioredis. Commands return parsed objects rather than raw arrays, which is convenient but occasionally surprising.

Downsides: smaller ecosystem than ioredis, some rough edges in the streams API typing. Auto-pipelining is a nice feature but irrelevant at our volume.

Migration path from chatbus: Each chatbus channel becomes a Redis Stream key (e.g., chat:supervisor, work:auto). The HTTP publish endpoint becomes an XADD call. The polling/subscribe loop becomes XREADGROUP ... BLOCK. The bus-follower and builder already use channel names that map directly to stream keys.

2. Message Queue Libraries

BullMQ

Good BullMQ
npm: ~700K weekly downloads • TypeScript: built-in • License: MIT • Docs

Redis-backed job queue with TypeScript-first design. Built on ioredis internally. Provides named queues, workers, job scheduling (cron, delay, repeat), rate limiting, retries with backoff, job priorities, and flow dependencies (parent/child jobs).

Stronger than raw Redis Streams when you need job semantics: retry policies, completion callbacks, progress tracking, job deduplication. Weaker when you need pub/sub fan-out — BullMQ is competing-consumer by default, not broadcast.

Fit for this project: The auto-worker dispatch pattern maps naturally to BullMQ. A Queue per work type, Worker instances per agent. But for chat routing (fan-out to UI + agents), raw Redis Streams or Redis pub/sub is simpler. 

import { Queue, Worker } from 'bullmq';

const workQueue = new Queue('auto-worker', { connection: { host: 'localhost' } });

// Dispatch
await workQueue.add('fix', {
  repo: 'underscorenygren/claude-by-voice',
  branch: 'auto/fix-login',
  prompt: 'Fix login refresh...'
});

// Process
const worker = new Worker('auto-worker', async (job) => {
  // job.data has the payload
  await runClaude(job.data.prompt);
}, { connection: { host: 'localhost' } });
CriterionRatingNotes
OrderingGoodFIFO within a queue. Priorities available but add complexity.
PersistenceStrongRedis-backed. Jobs survive restarts. Configurable retention.
Consumer groupsStrongBuilt-in competing consumers. Concurrency controls per worker.
TS SDKStrongTypeScript-first. Excellent types. Well-documented API.
Self-hostingTrivialJust needs Redis (same as above).
Message replayLimitedCompleted jobs can be queried, but no stream-style replay. Job data is cleaned up by default.
Low-volume fitGoodMinimal overhead. Slightly heavier than raw Streams due to Lua scripts and metadata.

Bee-Queue

Skip Bee-Queue
npm: ~100K weekly downloads • TypeScript: @types/bee-queue • License: MIT • Maintained: minimal

Simpler Redis-backed queue. Lighter than BullMQ but with fewer features (no repeatable jobs, no flows, no rate limiting). TypeScript support is via DefinitelyTyped, not built-in. Maintenance has slowed significantly. No reason to choose this over BullMQ.

3. Event Streaming Platforms

NATS (nats.js)

Situational nats.js / NATS JetStream
npm: ~250K weekly downloads • TypeScript: built-in • License: Apache 2.0 • JetStream docs

NATS is a lightweight messaging server. Core NATS is fire-and-forget pub/sub with no persistence. JetStream adds persistence, consumer groups, replay, and exactly-once delivery — but it is a separate subsystem that must be enabled and configured.

The TypeScript SDK (nats.js) is well-typed and actively maintained by the NATS team. The API is clean. Subject-based routing (chat.supervisor.>) maps well to our channel model.

Downside: Running a NATS server is another process to manage. JetStream persistence requires storage configuration. At our scale, Redis already covers everything NATS JetStream provides, without the additional server.

CriterionRatingNotes
OrderingStrong (JetStream)Per-stream ordering guaranteed. Core NATS: no ordering guarantees.
PersistenceStrong (JetStream)File-backed or memory-backed streams. Core NATS: none.
Consumer groupsStrong (JetStream)Durable consumers with ack/nack, redelivery policies.
TS SDKStrongOfficial SDK, good types, Deno-compatible.
Self-hostingEasySingle Go binary, ~20MB. But it is another server process beyond Redis.
Message replayStrong (JetStream)Replay by sequence, time, or from last acked.
Low-volume fitOverkillDesigned for high-throughput microservice mesh. Full capabilities unused at our scale.

Apache Kafka (kafkajs)

Skip kafkajs
npm: ~1.5M weekly downloads • TypeScript: built-in • License: MIT • Docs

KafkaJS is the standard Node.js client for Apache Kafka. The TypeScript types are solid and the API covers all Kafka operations (produce, consume, admin, transactions).

Disqualifying factor: Kafka requires a JVM-based broker (or at minimum ZooKeeper/KRaft). Even with KRaft mode eliminating ZooKeeper, running a Kafka broker for ~100 messages/minute is extreme over-engineering. Memory footprint alone (1-2 GB minimum) is unreasonable for a single-machine deployment.

Redpanda

Skip Redpanda (Kafka-compatible)
Kafka wire-compatible • Uses kafkajs client • License: BSL • Docs

Redpanda is a C++ Kafka-compatible broker that eliminates the JVM dependency. Single binary, lower resource usage than Kafka. Uses the same kafkajs client library.

Better than Kafka for self-hosting, but still a dedicated streaming platform designed for high-throughput workloads. Partitioned log model, tiered storage, rack awareness — none of which we need. Redis Streams covers the same use cases at our scale with zero additional infrastructure.

4. Pub/Sub Libraries

Redis Pub/Sub

Complementary Redis Pub/Sub
Built into Redis • Available via ioredis or node-redis • No additional dependencies

Redis has a built-in pub/sub system (PUBLISH/SUBSCRIBE) that is separate from Redis Streams. It is fire-and-forget: messages are delivered to all currently connected subscribers and then discarded. No persistence, no replay, no consumer groups.

Useful as a complement to Streams for real-time notifications. Pattern: write durable messages to a Stream (XADD), then PUBLISH a notification on a channel so listeners wake up immediately instead of polling. This is how the bustail/UI activity feed could work — the UI subscribes to a pub/sub channel for instant push, but the canonical data lives in the Stream.

CriterionRatingNotes
OrderingPer-publisherMessages from one publisher arrive in order. No global ordering.
PersistenceNoneFire-and-forget. Missed messages are gone.
Consumer groupsNoneAll subscribers get all messages (fan-out only).
TS SDKStrongSame ioredis/node-redis clients.
Self-hostingTrivialAlready running Redis.

Low-volume fitIdealZero overhead, instant delivery.

MQTT (mqtt.js)

Skip mqtt.js
npm: ~1.8M weekly downloads • TypeScript: built-in (v5+) • License: MIT • Docs

MQTT is a lightweight pub/sub protocol designed for IoT. mqtt.js is the standard Node.js client. Supports QoS levels (0=fire-and-forget, 1=at-least-once, 2=exactly-once), retained messages, will messages, and topic wildcards.

Requires a broker (Mosquitto, EMQX, Aedes for Node.js). The protocol is elegant for device-to-cloud messaging but does not provide consumer groups, message replay, or stream semantics. Persistence depends entirely on the broker implementation. Adding another broker process is not justified when Redis Streams covers all these needs natively.

5. In-Process Alternatives

RxJS

Wrong layer RxJS
npm: ~30M weekly downloads • TypeScript: built-in • License: Apache 2.0 • Docs

RxJS is the reactive extensions library for JavaScript. Excellent for in-process event stream composition: operators for filtering, mapping, debouncing, merging, error handling. TypeScript types are first-class.

Not a messaging solution. RxJS Observables live in a single process. No persistence, no cross-process communication, no replay after restart. Could be useful within an agent for composing event handlers (e.g., debouncing bus messages), but it does not replace the chatbus.

Highland.js

Skip Highland.js
npm: ~50K weekly downloads • TypeScript: @types/highland • License: Apache 2.0 • Docs

Utility library for managing Node.js Streams with a higher-level API. Wraps Node streams into a lazy, composable pipeline. Types are community-maintained (DefinitelyTyped), not built-in. Development has slowed. Same limitation as RxJS: in-process only, no durability.

most.js

Skip most.js
npm: ~100K weekly downloads • TypeScript: built-in • License: MIT • Docs

High-performance reactive programming library. Faster than RxJS in synthetic benchmarks. Clean TypeScript types. Same limitation: in-process only, no cross-process messaging or persistence. Performance advantage is meaningless at our message volume.

Recommended Architecture

The chatbus replacement uses three Redis primitives, all accessed via ioredis:

Producer (agent/supervisor) Consumer (agent/worker) | | | XADD chat:supervisor * ... | |-----> [Redis Stream: chat:supervisor] ------>| XREADGROUP GROUP workers agent-1 BLOCK ... | | | PUBLISH notify:supervisor "new" | (wakes up immediately) |-----> [Redis Pub/Sub] ---------------------->| SUBSCRIBE notify:supervisor | | | XACK chat:supervisor workers <id>
  • Redis Streams for durable, ordered message storage with consumer group semantics.
  • Redis Pub/Sub for instant wake-up notifications (optional optimization; XREADGROUP BLOCK already polls efficiently).
  • BullMQ (later, if needed) for scheduled/retryable jobs like the auto-worker dispatch.

Stream key naming

chat:{agent}         # Chat messages routed to an agent
work:{agent}         # Work dispatch (structured JSON payloads)
events:{source}      # System events (tool calls, lifecycle signals)
build:requests       # Builder work queue

Consumer group per service

# Each service type gets its own consumer group:
XGROUP CREATE chat:supervisor  ui-readers    0 MKSTREAM   # UI reads all messages
XGROUP CREATE chat:supervisor  agent-workers 0 MKSTREAM   # Agents process messages
XGROUP CREATE work:auto        auto-workers  0 MKSTREAM   # Auto-worker processes jobs

# Fan-out: multiple groups on the same stream each get all messages
# Competing consumers: multiple consumers in one group split the load

Migration from chatbus

The current chatbus HTTP API maps directly to Redis Streams operations:

Current chatbusRedis Streams equivalent
POST /publishXADD stream * field value ...
GET /subscribe?channel=XXREADGROUP GROUP g consumer BLOCK 5000 STREAMS X >
GET /messages?channel=XXRANGE X - +
GET /messages?channel=X&since=IDXRANGE X ID +
Bus store file persistenceRedis RDB/AOF (automatic)

What we lose: The chatbus HTTP interface is convenient for docker exec wget dispatches. A thin HTTP wrapper around Redis Streams (a few Express routes) preserves this for cron jobs and shell scripts that cannot use a Redis client directly.

Open Questions

  • Stream trimming policy. XADD ... MAXLEN ~ 10000 caps each stream at ~10K messages. Acceptable for chat; may need higher for events. Or use MINID to trim by age.
  • Serialization format. Redis Stream entries are flat key-value pairs. Nested JSON payloads (like work requests) would be stored as a single data field containing JSON. Alternatively, flatten top-level fields for queryability.
  • HTTP bridge. Keep a lightweight HTTP adapter for shell/cron callers, or require all producers to use the ioredis client directly?
  • BullMQ for auto-worker. The auto-worker dispatch has job-queue semantics (retry, timeout, progress reporting). Worth using BullMQ for that specific queue even if chat uses raw Streams?

MCP Implications

What we have now

The current message flow for agents uses MCP (Model Context Protocol) over stdio as the last-mile transport. The path is:

User message → HTTP POST to chatbus → Chatbus persists + routes to channel server → Channel server sends MCP notification via stdin → Claude agent processes, calls reply() tool → Channel server receives MCP tool call → Publishes response back to chatbus → Chatbus broadcasts to WebSocket clients

MCP is a fire-and-forget transport. There are no delivery receipts, no backpressure, no way to know if Claude consumed a notification. This is the source of the "supervisor goes silent" bug — messages get queued behind tool calls and the user sees nothing.

What changes with Redis Streams

The MCP layer does not change. Redis Streams replaces the chatbus (the routing and persistence layer), not the channel server or MCP transport. The channel server still bridges between the bus and MCP stdio.

Before: Chatbus (Go HTTP) → Channel server → MCP → Agent After: Redis Streams → Channel server → MCP → Agent

What improves:

  • Acknowledgment at the bus layer. The channel server can XACK a message after receiving it from the stream, and separately track whether Claude actually processed it. Today the chatbus has no ack mechanism — once the HTTP POST returns, the message is "delivered" even if the channel server dropped it.
  • Replay without custom code. Reconnection replay is currently hand-built in the chatbus. With Redis Streams, XRANGE from the last-seen ID gives you replay for free.
  • Consumer groups for competing workers. Multiple instances of a service can share a stream without duplicating work. Today each chatbus subscriber gets all messages.
  • Pending entry list (PEL). Redis tracks unacknowledged messages per consumer. A monitor can detect stuck consumers — "the channel server consumed this 60s ago but hasn't acked it" — and escalate. This is the missing piece for the MCP reliability problem.

What stays the same:

  • MCP stdio transport — still fire-and-forget between channel server and Claude. Agent-level acks still need explicit tool calls (ack(seq, status)).
  • Channel server role — still the bridge between bus and MCP. It subscribes to the Redis Stream instead of HTTP long-polling the chatbus.
  • WebSocket to browser — the bridge still fans out to connected clients via WebSocket. The stream library doesn't replace this — the bridge reads from Redis Streams and writes to WebSocket.

Key insight: Redis Streams solves the bus reliability problem (ordering, persistence, replay, ack tracking). It does not solve the MCP reliability problem (Claude ignoring notifications mid-tool-call). Those are different layers. But having ack tracking at the bus layer makes the MCP problem visible — you can see where a message stalled, which today is invisible.
