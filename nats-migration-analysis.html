NATS Migration Analysis

Full replacement mapping for chatbus, sysbus, and voice signaling. What NATS replaces, what stays, what gets deleted, and a phased migration path. Builds on the HTTP vs WebSocket Pub/Sub analysis which deferred the NATS decision.

TL;DR

NATS can replace both the chatbus and sysbus as a single dependency, eliminating two custom Go services (~2,500 lines of Go, their Dockerfiles, Docker Compose entries, and the pkg/busclient client library), while also collapsing three browser WebSocket connections into one nats.ws connection. JetStream replaces our JSONL file persistence and ring buffer with built-in disk-backed streams, consumer groups, and replay. PCM audio streaming should not move to NATS — the binary frames are too large and latency-sensitive for a message bus — but voice signaling (session start/end, transcription results, TTS notifications) fits cleanly into NATS subjects. The migration is three independent phases: chatbus first (highest code savings, lowest risk), sysbus second, voice signaling third. Each phase is independently deployable and reversible.

What gets added

A NATS client wrapper (~60 lines Go) that all services import instead of pkg/busclient. Each consuming service replaces its busclient.Subscribe() call with a NATS subscription — typically a 5-line change per service.

Before: busclient Subscribe (53 lines)

// pkg/busclient/client.go — long-poll loop
func (c *Client) Subscribe(ctx context.Context,
    agent string, handler func(Message)) error {
  longClient := &http.Client{Timeout: 45 * time.Second}
  var cursor time.Time
  for {
    if ctx.Err() != nil { return ctx.Err() }
    q := url.Values{}
    q.Set("agent", agent)
    if !cursor.IsZero() {
      q.Set("since", cursor.Add(time.Nanosecond).
        UTC().Format(time.RFC3339Nano))
    }
    q.Set("timeout", "30s")
    endpoint := c.BaseURL + "/subscribe?" + q.Encode()
    req, _ := http.NewRequestWithContext(
      ctx, http.MethodGet, endpoint, nil)
    resp, err := longClient.Do(req)
    if err != nil {
      time.Sleep(2 * time.Second)
      continue
    }
    var body listResponse
    json.NewDecoder(resp.Body).Decode(&body)
    resp.Body.Close()
    for _, msg := range body.Messages {
      handler(msg)
      if msg.Timestamp.After(cursor) {
        cursor = msg.Timestamp
      }
    }
  }
}

After: NATS Subscribe (12 lines)

// pkg/natsbus/client.go — NATS subscription
func Subscribe(nc *nats.Conn, agent string,
    handler func(Message)) error {
  subject := fmt.Sprintf("chat.%s.in", agent)
  _, err := nc.Subscribe(subject,
    func(msg *nats.Msg) {
      var m Message
      if json.Unmarshal(msg.Data, &m) == nil {
        handler(m)
      }
    })
  return err
}

// With JetStream (durable, replay on reconnect):
func SubscribeDurable(js jetstream.JetStream,
    agent string, handler func(Message)) error {
  stream, _ := js.Stream(ctx, "CHAT")
  cons, _ := stream.CreateOrUpdateConsumer(ctx,
    jetstream.ConsumerConfig{
      Durable:       agent + "-consumer",
      FilterSubject: "chat." + agent + ".in",
      AckPolicy:     jetstream.AckExplicitPolicy,
    })
  _, err := cons.Consume(func(msg jetstream.Msg) {
    var m Message
    if json.Unmarshal(msg.Data(), &m) == nil {
      handler(m)
    }
    msg.Ack()
  })
  return err
}

The key difference: no cursor management, no HTTP retry loop, no long-poll timeout tuning. NATS handles connection management, message delivery, and reconnection internally. The durable consumer version also handles replay after disconnection — the consumer picks up where it left off.

Agent routing

The chatbus currently resolves agent URLs and POSTs messages to http://mcc-agent-{name}:9091/message. With NATS, agents subscribe to their own subject (chat.{name}.in) and publish replies to chat.{name}.out. No HTTP proxy, no URL resolution, no timeout management. The agent routing code in cmd/chatbus/main.go (lines 104–120, 225–383) is entirely eliminated.

Dedup

The chatbus dedup logic (lines 56–100, ~45 lines) is replaced by JetStream's built-in deduplication. Publishers set a Nats-Msg-Id header; JetStream deduplicates within a configurable window (default 2 minutes, configurable up to any duration). Zero application code for dedup.

3. Voice Bridge Analysis

The bridge (cmd/bridge/, 3,643 lines) handles two fundamentally different types of traffic over one WebSocket connection:

Traffic typeFormatSizeLatency requirementNATS fit
Voice signaling JSON 0.1–2 KB <50ms acceptable Yes
PCM audio streaming Binary (PCM16, 24kHz mono) ~48 KB/sec continuous <20ms required No

Voice signaling — moves to NATS

Session management, transcription results, TTS notifications, and state changes are small JSON messages that fit within NATS's default 1 MB max payload by orders of magnitude. These can publish to voice.signal.* subjects:

// Bridge publishes transcription result
nc.Publish("voice.signal.transcript", json.Marshal(map[string]any{
    "session_id": sessionID,
    "text":       "Hello, how are you?",
    "confidence": 0.95,
    "timestamp":  time.Now().UTC(),
}))

// Browser subscribes to voice signals
nc.Subscribe("voice.signal.>", func(msg *nats.Msg) {
    // Update UI state: listening bubble, transcription display, etc.
})

PCM audio streaming — stays on dedicated WebSocket

PCM audio cannot move to NATS for three reasons:

1. Frame size and throughput

At 24kHz sample rate, 16-bit mono PCM, the bridge handles ~48,000 bytes/sec of continuous audio. Frames are typically sent every 20ms (960 bytes/frame) or accumulated into larger chunks. While each frame is well under NATS's 1 MB max message size, the continuous stream of messages at 50 Hz adds per-message overhead (headers, subject routing, subscription matching) that a raw WebSocket binary frame does not have.

2. Latency

Voice audio requires consistent sub-20ms delivery. NATS core pub/sub typically adds 0.1–1ms of routing latency per message — acceptable in isolation. But NATS is designed for request-reply and event patterns, not sustained binary streaming. Under load, message coalescing and slow consumer detection can introduce jitter that is imperceptible for chat but audible in audio.

3. Binary handling

NATS messages are byte arrays, so binary PCM can be transmitted. However, the nats.ws browser client serializes everything as text over the WebSocket (the NATS protocol is text-based with payload length headers). Binary audio would need base64 encoding for browser transport, adding ~33% overhead on a latency-sensitive stream. A native WebSocket sends raw binary frames with zero encoding overhead.

Recommendation

  1. Move voice signaling to NATS subjects (voice.signal.*). Session start/end, transcription results, TTS start/end, state changes. These are JSON messages identical in nature to chat and sysbus events.
  2. Keep PCM audio on a dedicated WebSocket. The bridge remains the audio endpoint. It connects to NATS for signaling but maintains its own WebSocket for the binary audio stream.
  3. The bridge shrinks but does not disappear. It loses chat relay code (the /internal/broadcast handler, bridge-to-browser chat push) and the system state WebSocket. It keeps audio streaming, Realtime API proxy, and STT/TTS provider integration.

4. JetStream for Persistence

JetStream replaces two persistence mechanisms: the chatbus JSONL file (bus-messages.jsonl, unbounded, currently managed by a compaction cron) and the sysbus in-memory ring buffer (50 events, lost on restart).

Stream configuration

// Two JetStream streams: one for chat, one for system events

// CHAT stream — replaces bus-messages.jsonl + ring buffer
js.CreateStream(ctx, jetstream.StreamConfig{
    Name:      "CHAT",
    Subjects:  []string{"chat.>"},                 // All chat subjects
    Storage:   jetstream.FileStorage,               // Disk-backed (replaces JSONL)
    Retention: jetstream.LimitsPolicy,
    MaxAge:    30 * 24 * time.Hour,                 // 30-day retention
    MaxMsgs:   100_000,                             // Cap at 100K messages
    MaxBytes:  500 * 1024 * 1024,                   // 500 MB max
    Replicas:  1,                                    // Single node (bump for HA)
    Discard:   jetstream.DiscardOld,                // Drop oldest when full
    Duplicates: 5 * time.Minute,                    // Dedup window (replaces custom dedup)
})

// SYS stream — replaces sysbus ring buffer
js.CreateStream(ctx, jetstream.StreamConfig{
    Name:      "SYS",
    Subjects:  []string{"sys.>"},
    Storage:   jetstream.MemoryStorage,             // In-memory (events are ephemeral)
    Retention: jetstream.LimitsPolicy,
    MaxMsgs:   500,                                  // Ring buffer equivalent
    MaxAge:    24 * time.Hour,                       // 1-day retention
    Discard:   jetstream.DiscardOld,
})

Consumer groups for bus-follower

The bus-follower (cmd/bus-follower/) currently uses busclient.Subscribe(ctx, "", handler) to receive all messages for classification. With JetStream, it becomes a durable consumer on the CHAT stream:

// bus-follower as a JetStream consumer
stream, _ := js.Stream(ctx, "CHAT")
cons, _ := stream.CreateOrUpdateConsumer(ctx, jetstream.ConsumerConfig{
    Durable:       "bus-follower",
    FilterSubject: "chat.>",           // All chat messages
    AckPolicy:     jetstream.AckExplicitPolicy,
    DeliverPolicy: jetstream.DeliverNewPolicy,
})

// Process messages — automatically tracks position,
// survives restarts, replays unacknowledged messages
cc, _ := cons.Consume(func(msg jetstream.Msg) {
    var m Message
    json.Unmarshal(msg.Data(), &m)
    classify(m)
    msg.Ack()
})

If bus-follower crashes and restarts, it resumes from the last acknowledged message. No cursor file, no timestamp tracking, no "did I already see this?" logic.

Replay capability

The browser can request history on connect by creating an ephemeral consumer with a DeliverByStartTime policy:

// Browser requests last 24h of chat on connect (via nats.ws JetStream API)
const js = nc.jetstream();
const consumer = await js.consumers.get("CHAT", {
    deliver_policy: "by_start_time",
    opt_start_time: new Date(Date.now() - 86400000).toISOString(),
    filter_subject: "chat.supervisor.>",
});
for await (const msg of consumer) {
    displayMessage(JSON.parse(msg.data));
    msg.ack();
}

Auth: JWT per-user with subject permissions

The auth server (or the bridge, acting as token issuer) generates a NATS JWT for each browser session. The JWT embeds subject permissions:

// JWT claims for a browser client
{
  "sub": "user-session-abc123",
  "nats": {
    "pub": {
      "allow": ["chat.supervisor.in", "chat.*.in"]   // Can send to any agent
    },
    "sub": {
      "allow": ["chat.supervisor.>", "sys.>", "voice.signal.>"]  // Can read
    },
    "resp": {
      "max": 1,
      "ttl": "5s"     // Can receive request-reply responses
    }
  }
}

The NATS server enforces these permissions without any application code. A browser client cannot subscribe to subjects it is not permitted to access. This replaces the current setup where the bridge manually filters which messages to relay to the browser.

9. Migration Path

Three phases, each independently deployable and reversible. Each phase can run in parallel with the system it replaces during transition.

Phase 1: NATS replaces chatbus

Risk: Low — chatbus is the simplest service, most subscribers are internal Go services.

Code savings: ~1,762 lines deleted.

Steps:

  1. Add NATS container to Docker Compose with JetStream enabled.
  2. Create pkg/natsbus/ with Connect, Publish, Subscribe helpers.
  3. Create CHAT JetStream stream on startup.
  4. Migrate Go services one at a time: replace busclient.Subscribe() with NATS subscription. Each service change is ~5 lines.
  5. Migrate the bridge: subscribe to chat.*.out via NATS instead of receiving POST /internal/broadcast. Delete the broadcast handler.
  6. Migrate browser chat publishing: send to NATS via bridge (bridge publishes to NATS on behalf of browser), or directly via nats.ws if Phase 3 is co-deployed.
  7. Delete cmd/chatbus/, pkg/busclient/, pkg/provider/bus/, chatbus Docker Compose entry.

Parallel running: During migration, both chatbus and NATS can run. A bridge adapter publishes to both, subscribers can be migrated one at a time. Remove chatbus once all consumers are on NATS.

Phase 2: NATS replaces sysbus

Risk: Low — sysbus has fewer consumers (browser only) and simpler data (no persistence needed).

Code savings: ~553 lines deleted.

Steps:

  1. Create SYS JetStream stream (memory-backed, 500 message limit).
  2. Migrate event publishers: bash curl commands switch to nats pub, or keep a thin HTTP adapter that publishes to NATS internally.
  3. Migrate browser: subscribe to sys.> via NATS instead of connecting to /sysbus/ws/events.
  4. Delete cmd/sysbus/, pkg/provider/ws/, web/src/eventbus-client.ts, sysbus Docker Compose entry.

Backward compatibility: Keep the HTTP adapter (POST /events → NATS publish) for bash scripts that use curl. This is ~15 lines in the bridge or a standalone adapter, and can be removed once all publishers switch to the nats CLI.

Phase 3: Voice signaling moves to NATS

Risk: Medium — requires splitting the bridge WebSocket protocol into audio (stays) and signaling (moves).

Code savings: ~80 lines deleted from bridge, plus simplification of the voice WebSocket protocol.

Steps:

  1. Define voice.signal.* subject hierarchy.
  2. Bridge publishes signaling events (session, transcript, TTS status) to NATS instead of sending them over the voice WebSocket.
  3. Browser subscribes to voice.signal.> via its existing NATS connection.
  4. The voice WebSocket becomes audio-only: binary PCM frames in both directions, no JSON signaling interleaved.

Audio stays on WebSocket. The bridge remains as the audio endpoint. It is simpler now: just PCM frames, no JSON protocol multiplexing.

Migration timeline estimate

PhaseEffortDependencies
Phase 1 (chatbus) 1–2 days None. Can start immediately.
Phase 2 (sysbus) 0.5–1 day Phase 1 (NATS container must be running).
Phase 3 (voice signaling) 1–2 days Phase 1 + 2. Also requires browser NATS client to be working.

10. Risk Assessment

RiskSeverityMitigation
NATS server crash loses in-flight messages Medium JetStream with file storage persists to disk. Messages survive server restart. For core NATS (non-JetStream) subjects, at-most-once is the same guarantee we have today.
Browser nats.ws library compatibility Medium The nats.ws package was deprecated and merged into @nats-io/nats-core (May 2026). Use the new package. The API is nearly identical. Verify W3C WebSocket compatibility in target browsers before committing.
JetStream storage grows unbounded Low Stream configuration has MaxAge, MaxMsgs, and MaxBytes limits. JetStream auto-compacts. No cron needed.
Auth complexity (JWT token issuance) Medium Start with simple token auth (one shared token, same as current setup). Migrate to per-user JWTs later when multi-user access matters. Token auth is ~3 lines of config.
NATS becomes a single point of failure Medium Currently chatbus and sysbus are each single points of failure too. NATS replaces two SPOFs with one. Built-in clustering is available if HA is needed later.
Loss of curl-friendly HTTP API Low Keep a thin HTTP adapter for bash scripts, or use the nats CLI tool. NATS monitoring endpoints (/varz, /connz) are curl-able.
NATS subject hierarchy design mistakes Medium Subject hierarchy is hard to change after consumers depend on it. Design carefully in Phase 1. Use wildcard subscriptions to keep flexibility. Subjects proposed in this doc are based on existing channel/agent/direction semantics.
Service migration causes message loss during cutover Low Run chatbus and NATS in parallel during migration. Dual-publish to both systems. Migrate consumers one at a time. Remove chatbus only after all consumers are on NATS.
Debugging becomes harder without HTTP request/response logs Medium nats sub ">" shows all traffic in real-time. nats stream view CHAT shows stored messages. Different from HTTP logs but equally inspectable. JetStream also provides per-consumer metrics (pending, acked, redelivered).

11. NATS vs Redis Streams

The Redis Streams migration analysis proposed Redis as the persistence backend. Here is why NATS is a stronger fit for this system:

PropertyRedis StreamsNATS JetStream
Browser connection No — needs WebSocket gateway Native — browser connects directly via nats.ws
Services eliminated 0 — chatbus becomes thinner but stays as gateway 2 — chatbus and sysbus both deleted entirely
Pub/sub Separate system (SUBSCRIBE) from streams (XREADGROUP) Unified — core pub/sub + JetStream are one system
Consumer groups Yes Yes — plus push and pull modes
Deduplication Manual (application-level) Built-in (Nats-Msg-Id header, configurable window)
Clustering Redis Cluster (complex, slot-based sharding) Built-in Raft (simple routes config)
Memory model All data in memory (AOF/RDB for durability) File-backed streams (memory optional per stream)
Docker image ~30 MB (redis:alpine) ~6 MB (nats:alpine)
Auth for browsers Not suitable JWT + subject permissions
Request-reply Manual (Lua scripts or application-level) Built-in (nc.Request())

Redis Streams is the right choice if you already run Redis for caching or other data structures and want to add messaging as an incremental feature. NATS is the right choice when messaging is the primary concern and you want browser clients, subject-based auth, and built-in clustering without running a separate gateway service.

For this system, NATS eliminates more code, more services, and more browser connections than Redis Streams would. The previous analysis recommended Redis because it deferred the "should we adopt NATS" question. This analysis answers it: yes, NATS is the better fit.
