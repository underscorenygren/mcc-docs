HTTP vs WebSocket Pub/Sub

Can we replace HTTP-based pub/sub with WebSocket-native messaging? What does Supabase do? Can browsers connect directly to Redis or NATS? Tradeoffs, patterns, and a recommendation.

TL;DR

  1. WebSocket pub/sub eliminates polling overhead and gives instant push delivery. For our chatbus, switching the browser-facing transport from HTTP long-poll to WebSocket is a clear win. The backend-to-backend transport (Go services subscribing) is a separate question with different tradeoffs.
  2. Browsers cannot connect directly to Redis. Redis speaks a custom TCP protocol, has no authentication model suitable for untrusted clients, and browsers lack raw TCP socket APIs. You always need a proxy/gateway. NATS is the exception — it has first-class WebSocket support and a browser client, but it is a new dependency with its own operational surface.
  3. Supabase Realtime is instructive but not transferable. It is a globally-distributed Elixir cluster that reads Postgres WAL and fans out via Phoenix Channels. The pattern (database change → server-side fanout → WebSocket) is the same pattern everyone uses. The implementation is Supabase-specific and assumes Postgres as source of truth.
  4. The universal pattern is: backend bus + WebSocket gateway. Every production system (Supabase, Socket.IO + Redis adapter, Ably, Pusher, NATS) puts a server-side process between the message bus and the browser. Direct federation does not work for untrusted clients.
  5. For our system: add a WebSocket subscription endpoint to the chatbus (or the bridge, which already has one). Redis Streams migration (separate analysis) handles backend durability. The browser gets push via WebSocket; services keep using HTTP or Redis consumer groups. Two transports, one bus.

Current State: How Our Chatbus Works

The chatbus is an HTTP-based message bus. All message flow — publishing, subscribing, querying history — happens over HTTP. The relevant code lives in cmd/chatbus/main.go (383 lines), pkg/provider/bus/ (server, store, envelope, subscribe, middleware), and pkg/busclient/client.go (194 lines).

What this means

The browser already receives messages via WebSocket (through the bridge). The HTTP pub/sub question is really about two things:

  1. Publishing from the browser — currently HTTP POST, could be WebSocket
  2. Service-to-service subscriptions — currently HTTP long-poll, could be WebSocket or Redis consumer groups

The bridge is already a WebSocket gateway. The question is whether to eliminate the HTTP hop between chatbus and bridge, and whether services should subscribe via WebSocket instead of long-poll.

Analysis: WebSocket Pub/Sub — What Changes

What gets easier

  1. Instant delivery. No 30-second long-poll ceiling. Messages arrive within milliseconds of being published. The long-poll approach has a latency floor of one HTTP round-trip per batch, and a worst case of 30 seconds if the poll just started when the message arrives.
  2. No wasted requests. Long-poll burns one HTTP connection per subscriber, continuously. Even when no messages arrive, the connection is held open for up to 30 seconds, then immediately reopened. WebSocket holds one connection and is idle until data flows.
  3. Bidirectional on one connection. A service that both publishes and subscribes currently needs two code paths (POST for publish, GET for subscribe). Over WebSocket, both directions share one connection.
  4. Simpler client code. The busclient.Subscribe() function is 53 lines of retry-loop, cursor management, and HTTP request construction. A WebSocket subscriber is: connect, receive messages, handle reconnect. The cursor management is pushed to the server.
  5. Bridge integration simplifies. Currently the chatbus POSTs to the bridge's /internal/broadcast endpoint to push outbound messages. If the bridge subscribes to the chatbus via WebSocket, this push-from-chatbus pattern is replaced by pull-from-bridge. One fewer HTTP integration point.

What gets harder

  1. Connection lifecycle management. HTTP is stateless — each request is independent. WebSocket connections are stateful. The server must track connected clients, handle disconnects, manage reconnection, and decide what to do about messages missed during disconnection (replay from cursor? drop?).
  2. Load balancing. HTTP requests can be load-balanced per-request. WebSocket connections are pinned to a specific server instance for their lifetime. If you scale to multiple chatbus instances, you need sticky sessions or a shared pub/sub backplane (Redis, NATS) to route messages to the right instance.
  3. Backpressure. HTTP long-poll has natural backpressure — the client processes a batch, then asks for more. WebSocket push has no built-in flow control. A slow consumer can accumulate unbounded messages in the server's send buffer.
  4. Debugging. HTTP requests show up in logs, curl, browser devtools network tab with clear request/response pairs. WebSocket frames are harder to inspect and replay.
  5. Auth and middleware. HTTP has mature middleware chains (auth, rate limiting, CORS, logging). WebSocket auth typically happens once at handshake time, then the connection is trusted for its lifetime. Mid-connection auth changes (token expiry) require application-level handling.

Deep Dive: Supabase Realtime Architecture

Supabase Realtime is worth studying because it solves a problem close to ours: take changes from a data store and push them to browsers in real time. It is not something to adopt (it is Postgres-specific and Elixir-native), but the pattern is instructive.

Architecture overview

Supabase Realtime data flow: Postgres ── WAL (logical replication) ──> Realtime Server ── WebSocket ──> Browser │ (Elixir/Phoenix) (Phoenix Channels) │ │ │ ┌─────────┴──────────┐ │ │ │ │ subscription subscription │ matching matching │ (append IDs (append IDs │ to WAL records) to WAL records) │ │ │ │ Client A Client B │ Replication slot is polled by the Realtime server. Each WAL record gets subscription IDs appended based on which clients are listening to that table/filter combo.

How it works internally

  1. Postgres WAL as source of truth. Supabase uses PostgreSQL's logical replication protocol. When a row changes, the change is written to the Write-Ahead Log. The Realtime server acquires a replication slot and polls it for new entries.
  2. Elixir/Erlang process model. The server is a globally-distributed Elixir cluster. Each WebSocket connection is an Erlang lightweight process. Phoenix Channels (built on Phoenix.PubSub with the PG2 adapter) handle subscription matching and fan-out. Erlang's process model means millions of concurrent connections are feasible without OS thread overhead.
  3. Subscription matching. When a WAL record arrives, the server appends globally-unique subscription IDs (one per listening Erlang process/socket) to the record. Erlang's process routing then delivers the record to the right clients.
  4. Three features on one transport:
    • Postgres Changes — subscribe to INSERT/UPDATE/DELETE on specific tables with column filters. Authorization respects Row-Level Security policies.
    • Broadcast — arbitrary pub/sub messaging between clients. Uses a realtime.messages table with daily partitions (3-day retention). Changes to this table flow through the same WAL pipeline.
    • Presence — distributed key-value store backed by a CRDT, synced across cluster nodes. Tracks who is online, cursor positions, etc.
  5. Authorization. Broadcast and Postgres Changes use database-level access controls. The client authenticates with a JWT; the server enforces RLS policies before delivering changes.

What to take from this

  1. The pattern is universal: data store → server-side process → subscription matching → WebSocket push. Supabase just happens to use Postgres WAL as the data store and Elixir processes as the routing layer.
  2. The browser never touches the database. All access goes through the Realtime server, which authenticates, filters, and fans out. This is the same gateway pattern every system uses.
  3. Presence and broadcast are extras layered on the same WebSocket connection. Once you have a persistent connection for data changes, adding ephemeral messaging (broadcast) and shared state (presence) is cheap — same transport, different channel semantics.
  4. When to use Supabase Realtime: when your source of truth is Postgres and you want reactive UIs without building a change-data-capture pipeline. When to replace it: when your source of truth is not Postgres, when you need sub-5ms latency (WAL polling adds latency), or when you need message ordering guarantees across multiple tables.

Deep Dive: Direct Backend Federation to Browsers

The question: can a browser connect directly to Redis, NATS, or another backend bus, skipping the application server entirely?

Redis: No

ConcernStatus
Browser TCP accessBlocked — browsers have no raw TCP socket API. Cannot speak the Redis protocol (RESP).
Redis over WebSocketNot supported — Redis server has no WebSocket listener. Third-party proxies (webdis, redis-websocket-proxy) exist but are thin wrappers — you are back to running a gateway.
AuthenticationUnsuitable — Redis auth is a single password or ACL username/password. Not per-user, not token-based, not revocable per session. Designed for trusted internal services, not untrusted browser clients.
AuthorizationCoarse — Redis ACLs can restrict commands and key patterns, but cannot express "this user can only read messages where agent=X". Application-level filtering is required.
Exposure riskCritical — 39,000+ unauthenticated Redis instances found on the public internet; ~50% show signs of compromise. Redis explicitly documents it is not designed for untrusted network exposure.

Redis is a backend data store. Exposing it to browsers — even through a WebSocket proxy — means every connected browser has a Redis client with whatever permissions the proxy grants. There is no safe way to do per-user, per-channel authorization at the Redis level. You always need application-level gating.

NATS: Yes, with caveats

ConcernStatus
Browser WebSocket accessNative — NATS server has built-in WebSocket listener. Official nats.ws client library for browsers.
Pub/sub from browserFull — subscribe, publish, request-reply, JetStream (persistent streams with replay) all work from the browser.
AuthenticationToken/JWT — NATS supports token auth, NKey auth, and JWT-based decentralized auth. Per-user credentials are possible.
AuthorizationSubject-based — NATS can restrict which subjects (topics) a user can publish/subscribe to. But filtering within a subject (e.g., only messages where agent=X) requires application logic.
Operational costNew dependency — NATS is a separate server process. Lightweight (~20MB binary, ~10MB memory), but it is a new thing to run, monitor, and understand.
JetStream (persistence)Built-in — JetStream provides persistent streams with replay, consumer groups, exactly-once delivery. Comparable to Redis Streams but with native WebSocket access.

NATS is the closest thing to "direct browser federation" that actually works. The browser connects via WebSocket to the NATS server and speaks the NATS protocol natively. No application-layer proxy needed for basic pub/sub. However:

  • Subject-level authorization means you need to design your topic hierarchy carefully. chat.supervisor.in vs chat.builder.out — the subject structure becomes your access control model.
  • Any filtering finer than subject matching (e.g., "only messages from user X") still requires application logic, either server-side or client-side.
  • Browser clients can publish to any subject they have permissions for. If your authorization model is "browsers can only read," you need to configure that explicitly per credential.

NATS deep dive: what it is and how it works

NATS is a message bus built by Synadia (originally by Derek Collison, who also built the messaging system inside Cloud Foundry and Apcera). It is written in Go, single-binary, and designed for cloud-native infrastructure. The name stands for nothing — it is just "NATS."

Core concepts

NATS has three layers, each building on the previous:

1. Core NATS — fire-and-forget pub/sub

The simplest layer. Publishers send messages to subjects (string-based topic names like chat.supervisor.in). Subscribers listen to subjects, optionally with wildcards. Messages are delivered at most once — if no subscriber is listening when a message is published, it is gone.

  • Subjects are dot-separated hierarchies: chat.atlas.out, system.scheduler.idle
  • * matches one token: chat.*.out matches chat.atlas.out and chat.builder.out
  • > matches one or more tokens: chat.> matches everything under chat.
  • Request-reply: a publisher sends a message with a reply subject. The subscriber responds to that subject. NATS routes the response back. This is how synchronous RPC works over an async bus.
  • Queue groups: multiple subscribers can join a named group. NATS delivers each message to exactly one member of the group (load balancing). Similar to Redis consumer groups but without persistence.

Core NATS has no persistence, no replay, no delivery guarantees beyond "if someone is listening right now, they get it." It is fast (~15 million msgs/sec on a single server) because it does almost nothing besides routing.

2. JetStream — persistent streams with replay

JetStream adds durability on top of core NATS. It is NATS's answer to Kafka, Redis Streams, and Pulsar. JetStream stores messages in streams and delivers them to consumers.

  • Streams capture messages published to one or more subjects. They persist to disk (or memory) with configurable retention (by time, count, or size). A stream is like a Redis Stream or a Kafka topic.
  • Consumers read from a stream with a cursor. They can be durable (survive restarts, track position) or ephemeral (disappear when the client disconnects). Durable consumers are like Redis consumer groups.
  • Delivery policies: start from the beginning, start from a specific sequence, start from a timestamp, or "new messages only." This is how replay works — a reconnecting client can resume from where it left off.
  • Acknowledgment: consumers ACK messages. Unacknowledged messages are redelivered after a timeout. This gives at-least-once delivery (or exactly-once with dedup).
  • Deduplication: publishers can set a Nats-Msg-Id header. JetStream deduplicates within a configurable window, giving effectively exactly-once publishing.

3. Key-Value and Object Store — state on the bus

Built on top of JetStream, NATS also provides:

  • Key-Value store: a distributed, replicated KV with watch (subscribe to changes on a key). Like etcd but lighter. Could replace our agent state tracking.
  • Object store: for large blobs (chunked into JetStream messages). Less relevant for us.

WebSocket support

NATS server has a built-in WebSocket listener (configurable port, TLS, compression). The nats.ws npm package is the official browser client. From the browser's perspective, connecting to NATS looks like this:

import { connect } from 'nats.ws';

const nc = await connect({
  servers: 'wss://nats.example.com:9222',
  user: 'browser-client',
  token: 'jwt-token-here',
});

// Subscribe to messages for a specific agent
const sub = nc.subscribe('chat.atlas.out');
for await (const msg of sub) {
  const data = JSON.parse(new TextDecoder().decode(msg.data));
  console.log('Message:', data.text);
}

// Publish a message
nc.publish('chat.atlas.in', JSON.stringify({ text: 'hello' }));

// Request-reply (synchronous RPC over async bus)
const reply = await nc.request('agent.atlas.status', '', { timeout: 5000 });
console.log('Agent status:', new TextDecoder().decode(reply.data));

The browser speaks the full NATS protocol — not a subset, not a translation layer. Every feature available to Go/Rust/Python clients is available to the browser, including JetStream consumers with replay.

Authentication and authorization

NATS has three auth models, each progressively more sophisticated:

ModelHow it worksSuitable for browsers
Token auth Single token per connection. Server validates against config. Basic — works but all browsers share one identity
NKey auth Ed25519 key pairs. Client signs a nonce; server verifies. No secret transmitted. Possible — requires key management in the browser
JWT + NKey (decentralized) Operator issues account JWTs. Accounts issue user JWTs. Permissions are embedded in the JWT. Server validates the chain without contacting an auth server. Best fit — your auth server issues a NATS JWT with scoped permissions per user session

With JWT auth, you can issue a browser-specific JWT that says: "this user can subscribe to chat.supervisor.* and system.status.>, can publish to chat.supervisor.in, and nothing else." The NATS server enforces this without any application code. Permissions are embedded in the signed JWT — the NATS server never calls back to your auth server.

Operational profile

  • Binary size: ~20MB single binary. No runtime dependencies.
  • Memory: ~10MB base. JetStream streams use memory or disk (configurable per stream).
  • Docker image: nats:alpine is ~10MB. Add to docker-compose.yml as one service.
  • Configuration: single nats.conf file. WebSocket listener, JetStream storage dir, auth config.
  • Monitoring: built-in HTTP monitoring endpoint (/varz, /connz, /subsz). Prometheus endpoint available. CLI tool nats for inspection.
  • Clustering: built-in. Add routes to config and NATS servers form a mesh. JetStream uses Raft for leader election and replication. Not needed for single-node, but trivial to add later.
  • Client libraries: Go (nats.go), TypeScript/Node (nats.js), browser (nats.ws), Rust, Python, C, .NET, Java, Ruby, Elixir, Zig. All officially maintained by Synadia.

The key difference from Redis: NATS is purpose-built for messaging. Redis is a general-purpose data structure server that added Streams as one of many features. NATS does one thing — message routing — and does it with less operational surface than Redis (no AOF, no RDB snapshots, no memory fragmentation concerns, no Lua scripting, no 20+ data types to reason about).

The universal pattern

Every production real-time system: Browser <── WebSocket ── Gateway / Proxy <── Backend Bus <── Services │ ┌─────┴──────┐ │ │ Auth/Authz Filtering (JWT, RLS) (per-user, per-channel) Supabase: Browser <── WS ── Realtime (Elixir) <── Postgres WAL Socket.IO: Browser <── WS ── Node.js server <── Redis Pub/Sub adapter Ably: Browser <── WS ── Ably edge ── Ably core <── publisher Our bridge: Browser <── WS ── bridge (Go) <── chatbus HTTP POST NATS: Browser <── WS ── NATS server (native) <── services // NATS is the only one where the gateway IS the bus

NATS collapses the gateway and bus into one process. Everything else separates them. The reason: the gateway handles concerns the bus should not — per-user auth, fine-grained filtering, rate limiting, protocol translation. NATS handles some of these (subject-level auth, token-based credentials) but not all (field-level filtering, rate limiting per user).

Recommendation

What we should do

  1. Add WebSocket subscriptions to the bridge for browser clients. The bridge already has a WebSocket connection to every browser. Extend it to deliver chatbus messages in real time instead of relying on the chatbus-to-bridge HTTP POST callback. The bridge becomes the WebSocket gateway. This is the highest-value, lowest-risk change.
  2. Keep HTTP POST for browser publishing. The browser sends messages infrequently (user-initiated). HTTP POST is simpler to auth, log, and rate-limit than a WebSocket message. No reason to change this.
  3. Migrate service subscriptions to Redis Streams consumer groups (per the Redis Streams migration analysis). This gives exactly-once delivery, pending message tracking, and eliminates the long-poll overhead for Go services. This is a backend change, invisible to browsers.
  4. Do not adopt NATS at this time. NATS is technically superior for the "browser connects directly to bus" use case, but it is a new operational dependency that replaces both Redis and our custom chatbus. The current system does not need that level of change. If we ever need multi-region distribution or cross-cluster messaging, NATS becomes the right answer.
  5. Do not expose Redis to browsers. Not now, not ever. Redis is a backend store. The gateway pattern exists for good reasons: per-user auth, field-level filtering, rate limiting, and protocol translation.

When to reconsider NATS

NATS becomes the right choice if any of these become true:

  • We need multi-region deployment with message routing across clusters
  • We want browsers to subscribe to arbitrary topics without a custom gateway
  • We need request-reply patterns from the browser (not just pub/sub)
  • We want to replace both Redis and the chatbus with a single system
  • We need JetStream's stream processing capabilities (dedup, flow control, consumer push/pull modes)

For current scale (~15 services, ~1 browser client, single-node deployment), Redis Streams + the existing bridge is sufficient. NATS is the right answer at a larger scale or for a greenfield project without an existing WebSocket gateway.

Advising Others: When to Use What

If someone asks "should I use Supabase Realtime / Redis pub/sub / NATS / custom WebSocket?", here is the decision framework:

If your situation is...UseWhy
Postgres is your source of truth, you want reactive UIs Supabase Realtime Zero custom code. WAL → WebSocket is built-in. RLS for auth. Works until you need non-Postgres events or sub-5ms latency.
You already have Redis, services need reliable message passing Redis Streams + WebSocket gateway Consumer groups for exactly-once delivery. No new dependency. Browser access via your existing server.
You need browser-native pub/sub without a custom gateway NATS Only system with first-class WebSocket support and browser client. JetStream for persistence. Built-in clustering.
You need global scale, edge delivery, SLA guarantees Managed service (Ably, Pusher, etc.) Connection management, presence, history, auth, edge nodes — all handled. Cost scales with connections.
Simple app, few clients, just need real-time updates Server-Sent Events (SSE) One-way push, works over HTTP/2, no WebSocket complexity. Add POST endpoint for client → server messages.
You have a custom WebSocket server already Add pub/sub to it No new dependency. Use Redis/NATS as backplane only if you need multi-instance fan-out.
