Agent Architecture: Dispatch Board Task Orchestration

Task Orchestration Research

Autonomous task management for a multi-agent system: survey, three alternatives, and a phased recommendation.

November 2026 — Agent Architecture series

TL;DR

Start with a reactive tail that watches the chatbus, maintains a live task state model, and answers "what are we doing?" queries. Layer on an LLM planner in phase two. Defer full autonomy until the state model proves reliable. Linear integration comes free in phase one via polling; deeper integration follows naturally.

1. Survey of Approaches

The agent orchestration space has converged on a few dominant patterns. Each makes different tradeoffs on autonomy, reliability, and developer control.

CrewAI — Role-Based Crews

CrewAI assigns agents fixed roles (researcher, writer, reviewer) and runs them through a sequential or hierarchical task pipeline. A "crew" is a static DAG of agents with defined handoff points. Tasks carry context objects that accumulate outputs from prior steps.

  • Pattern: Static role assignment, sequential or hierarchical execution
  • Strengths: Simple mental model, declarative task definitions, built-in delegation
  • Weaknesses: Rigid pipelines — poor at dynamic re-planning. No durable state; a crash mid-pipeline loses all progress. No native concept of long-running tasks or follow-ups.
  • Relevance: The role-based pattern maps loosely to our agent registry (builder, octocat, porter), but our agents are persistent services, not ephemeral pipeline stages.

AutoGen / AG2 — Conversation-Based Routing

Microsoft's AutoGen frames multi-agent work as conversations. Agents are participants in a group chat; a "speaker selection" policy determines who talks next. Tasks emerge from conversation flow rather than being declared upfront.

  • Pattern: Multi-agent conversation with turn-taking policies
  • Strengths: Flexible — agents can dynamically decide to delegate, ask for help, or escalate. Natural for open-ended exploration tasks.
  • Weaknesses: Hard to reason about termination. Conversation can loop or drift. No built-in persistence — state lives only in the conversation context window. Speaker selection is fragile at scale.
  • Relevance: Our chatbus already implements a conversation-like pattern. The "who should respond?" question is exactly what we need to solve for proactive orchestration.

LangGraph — State Machines for Agents

LangGraph models agent workflows as directed graphs with typed state. Nodes are processing steps (LLM calls, tool invocations, human-in-the-loop gates). Edges are conditional transitions. State is checkpointed, making workflows resumable.

  • Pattern: Explicit state machine with checkpointed transitions
  • Strengths: Predictable execution — you can trace exactly which node fired and why. Built-in persistence and resume. Human-in-the-loop is a first-class concept (interrupt nodes).
  • Weaknesses: Graphs must be defined upfront — dynamic re-planning requires meta-graphs. Verbose for simple workflows. Tightly coupled to the LangChain ecosystem.
  • Relevance: The state machine pattern is directly applicable. Our orchestrator already uses XState-like state machines on the client. The checkpointing model is what we need for crash recovery.

Temporal.io — Durable Execution

Temporal provides durable execution for long-running workflows. Activities (units of work) are retried automatically on failure. Workflow state survives process crashes — the runtime replays the event history to reconstruct state. Originally designed for microservice orchestration, now adopted for agent workflows.

  • Pattern: Durable workflow engine with automatic retry, replay, and compensation
  • Strengths: Bulletproof reliability — workflows survive any failure mode. Excellent visibility into running workflows. Timers and cron schedules are native.
  • Weaknesses: Heavy infrastructure — requires a Temporal server cluster. Determinism constraints on workflow code (no random, no system time, no I/O in workflow functions). Significant learning curve.
  • Relevance: Overkill for our current scale, but the concepts (event sourcing, replay, durable timers) are worth stealing. Our bus message history already provides a crude event log.

Anthropic Multi-Agent Patterns

Anthropic's recommended patterns (from the multi-agent cookbook and tool_use documentation):

  • Orchestrator-worker: A central LLM reads the task, decides which sub-agent to invoke (via tool_use), collects results, synthesizes. This is what our supervisor already does manually.
  • Routing: A lightweight classifier determines which specialized agent handles a request. Our auto-routing concept matches this.
  • Parallel fan-out: Dispatch the same task to multiple agents, aggregate results. Useful for search, analysis, or consensus tasks.
  • Tool chains: Sequential tool_use calls where each output feeds the next. Simple, predictable, but synchronous and blocking.

The key insight from Anthropic's patterns: keep the orchestrator thin. The orchestrator decides what to do; workers decide how. Mixing both in one agent leads to context window bloat and unpredictable behavior.

2. Three Alternatives

A. Reactive Tail
Watch the bus, maintain state, answer queries. No autonomous action.
B. Planner-Executor
LLM reads state, proposes actions, dispatches to workers. Human approves.
C. Full Autonomous Loop
Continuous agent: world model, proactive assignment, follow-up, escalation.

A. Reactive Tail

Architecture

A single Go service (task-tailer) subscribes to the chatbus and sysbus. It maintains an in-memory task state model — a map of task IDs to their current status, assigned agent, last update time, and a short history of state transitions. Periodically polls Linear for external task state.

Exposes a simple HTTP API: GET /state returns the full model as JSON. GET /summary returns a human-readable summary. The supervisor queries this when the user asks "what are we doing?"

Octocat has PR #247 open. Two Linear issues unassigned."

Strengths

  • Minimal implementation — one Go service, ~500 lines, uses existing busclient
  • No LLM calls — deterministic, fast, cheap
  • Answers "what are we doing?" immediately from in-memory state
  • Linear integration is a simple polling loop (5-minute interval)
  • Zero risk of runaway autonomous actions

Weaknesses

  • No proactive follow-up — only responds to queries
  • State model requires manual tuning of what bus messages mean what
  • Cannot suggest next actions or prioritize
  • Summary quality depends on structured message conventions (bus messages must be parseable)

Implementation Cost

~2-3 days. New Go service in cmd/task-tailer/. Subscribe to chatbus + sysbus. Parse known message patterns (dispatch/confirmed, build/done, etc.). Add Linear API polling. Expose HTTP endpoints. Register in agents/registry.yaml as a service.

B. Planner-Executor

Architecture

Builds on top of Alternative A. The task-tailer provides the state model. A separate planner service periodically reads the state, sends it to an LLM (via claude --print), and receives a list of suggested next actions. These suggestions are posted to the chatbus for the supervisor to review and approve.

The planner does not execute — it only suggests. The supervisor (or user) approves, and the supervisor dispatches via the normal teammate/worker path. This keeps a human in the loop while adding proactive capability.

Strengths

  • Proactive — surfaces stale tasks, failed builds, unassigned work without being asked
  • Human-in-the-loop — suggestions require approval, limiting blast radius
  • LLM understands context — can reason about priority, dependencies, urgency
  • Batch worker pattern — follows existing octocat/worker architecture exactly
  • Linear integration richer — LLM can reason about issue labels, assignees, sprint context

Weaknesses

  • LLM calls cost money and add latency (~5-15s per planning cycle)
  • Suggestion quality depends on prompt engineering and state model completeness
  • Approval step adds friction — if user is away, suggestions queue up without action
  • Planner may suggest actions the system cannot actually execute (hallucinated capabilities)

Implementation Cost

~1 week, assuming Alternative A exists. New batch worker in cmd/planner/. Cron trigger every 15 minutes. Prompt template that accepts JSON state and returns structured suggestions. Suggestion rendering in the UI activity feed. Approval mechanism (chatbus command or UI button).

C. Full Autonomous Loop

Architecture

A persistent Claude agent (orchestrator) with its own MCP session. Maintains a world model by continuously tailing the chatbus and sysbus. Has tool access to: dispatch work to agents, create/update Linear issues, query GitHub, send notifications. Operates on a continuous loop: observe → plan → act → observe.

Guardrails: budget limits (max N dispatches per hour), escalation thresholds (if confidence is low, ask the user instead of acting), and an explicit "autonomous mode on/off" toggle.

Strengths

  • Truly autonomous — handles overnight work, follows up without user involvement
  • Rich reasoning — can correlate events across time (build failed + same branch + recent PR)
  • Natural language interface — user says "handle things while I'm out" and it does
  • Can manage multi-step workflows (create issue → assign → monitor → review → merge)
  • Integrates with everything via tool_use — Linear, GitHub, chatbus, notifications

Weaknesses

  • Most complex to implement — persistent agent session, world model, guardrails
  • Expensive — continuous Claude session with large context window
  • Hardest to debug — autonomous decisions may be surprising or wrong
  • Risk of runaway loops — agent dispatches work, observes result, dispatches more work
  • Context window management — world model grows unboundedly without summarization
  • Requires robust guardrails: rate limits, budget caps, confidence thresholds, kill switch

Implementation Cost

~3-4 weeks. New MCP agent in agents/ with channel server routing. Tool definitions for dispatch, Linear, GitHub, notification. World model schema and summarization logic. Guardrail system (budget tracking, escalation rules). UI for monitoring autonomous decisions. Cron or continuous-run mode. Testing framework for autonomous behavior (scenario-based with expected decisions).

4. Recommendation

Start with A, layer B on top, defer C until the state model proves reliable.

The state model is the foundation everything else depends on. If the reactive tail cannot accurately answer "what are we doing?", no amount of LLM reasoning on top will produce good results. Building A first validates the data pipeline (bus messages → structured state) before adding intelligence.

Phased Roadmap

Phase 1: Reactive Tail (weeks 1-2)

Build: cmd/task-tailer/ Go service. Subscribe to chatbus + sysbus. Parse dispatch/build/deploy/merge events into a task state map. Poll Linear every 5 minutes. Expose GET /state and GET /summary.

Wire: Supervisor queries /summary when user asks "what are we doing?" Add a "Status" tile to the UI that renders the live state.

Validate: Run for a week. Check: does the state model match reality? Are there bus messages we're missing? Is the summary useful?

Linear integration: Read-only. Fetch open issues, map to internal task IDs where possible. Show in summary as "External: 3 Linear issues (2 assigned, 1 unassigned)."

Exit criteria: State model accuracy >90% when spot-checked against GitHub + Linear.

Phase 2: Planner Layer (weeks 3-4)

Build: cmd/planner/ batch worker. Cron-triggered every 15 minutes. Reads /state from task-tailer, sends to claude --print with a structured prompt, publishes suggestions to chatbus channel suggestions.

Prompt design: Include the state snapshot, the agent registry (who can do what), recent history (last 10 state transitions), and explicit constraints ("never dispatch more than 2 tasks at once", "always escalate if build has failed 3+ times").

Approval flow: Suggestions appear in the UI activity feed. Supervisor can approve via chat command (!approve 1) or the user can approve via voice. Unapproved suggestions expire after 1 hour.

Linear integration: Planner can suggest creating issues, changing assignments, updating status. Execution still goes through supervisor.

Exit criteria: >70% of suggestions are useful (not rejected or expired). User reports it surfaces things they would have missed.

Phase 3: Selective Autonomy (weeks 5-8)

Not full autonomy. Instead, define a whitelist of actions the planner can execute without approval: retry failed builds, assign unassigned Linear issues to the default worker, post status summaries to chat. Everything else still requires approval.

Guardrails: Max 5 autonomous actions per hour. Mandatory cool-down after any failure. All autonomous actions logged to a decision audit trail (append-only JSONL file). Kill switch via chatbus command (!autonomous off).

Evaluate: After running for 2 weeks, review the decision audit trail. Expand the whitelist if the autonomous actions were consistently correct. Contract if not.

Full C (persistent agent) is deferred until the whitelist approach shows clear limitations that only a continuous reasoning loop can solve. The batch planner with selective autonomy covers 80% of the value at 20% of the complexity.

Key Design Decisions

  • Go service for the tailer, not a Claude agent. The state model must be deterministic and fast. An LLM adds no value to event parsing. Keep it mechanical.
  • Batch worker for the planner, not a persistent agent. Planning every 15 minutes is sufficient. A persistent agent is expensive and adds context management complexity for no gain at this stage.
  • Suggestions channel on chatbus. Keeps suggestions visible to all consumers (UI, supervisor, future agents) without special routing.
  • Linear polling, not webhooks. Webhooks require a public endpoint and SSL termination. Polling every 5 minutes is adequate and simpler to implement. Switch to webhooks only if latency matters.
  • State model as the single source of truth. Both the UI and the planner read from the same /state endpoint. No divergent views of reality.

What This Does Not Solve

This design assumes the supervisor is running. When the supervisor is offline (overnight, weekends), suggestions queue up but nothing acts on them. Phase 3's selective autonomy partially addresses this, but a fully autonomous overnight worker is a separate problem that requires the persistent agent model (Alternative C) or a dedicated cron-triggered batch pipeline.

For overnight scenarios, the better near-term solution is a cron job that runs claude --print with the state snapshot and a narrow mandate ("retry any failed builds, post a morning summary"). This is cheaper and more predictable than a persistent agent.
