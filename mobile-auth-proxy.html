Mobile Auth & Proxy Architecture

How mobile auth differs from web, and why we proxy everything through /mobile/*.

2026-11-25

Two Auth Paths

Web and mobile use completely different authentication mechanisms. This is the root cause of most "works on web, broken on mobile" issues.

Web OAuth2 Cookie Flow
Browser → Cloudflare → oauth2-proxy → nginx → upstream

The browser has an _oauth2_proxy cookie set by the Google OAuth flow. Every request passes through oauth2-proxy which validates the cookie and sets X-Auth-Email. All routes — including subdomains like activity.* and tasks.* — work because the cookie is scoped to the domain.

Mobile Session Token Flow
Expo app → Google Sign-In → POST /mobile/session → Bridge validates → Returns session token

The native app uses @react-native-google-signin to get an ID token, posts it to /mobile/session, and receives a mobile_session token. This token is passed as a ?session= query parameter on every subsequent request. There are no cookies.

Why Subdomains Don't Work on Mobile

On web, services are exposed via subdomains:

  • activity.mushroomcloudcomputing.com → mcc-activity (port 9101)
  • tasks.mushroomcloudcomputing.com → mcc-taskmaster (port 9102)

These subdomains go through Cloudflare's proxy, which requires the oauth2-proxy cookie. The mobile app doesn't have this cookie — it has a mobile_session token that only the main domain's nginx understands. So mobile requests to subdomains get a 403 from Cloudflare/oauth2-proxy.

Additionally, Cloudflare's proxy layer blocks WebSocket upgrades on some subdomain configurations, which is why even the web dashboard proxies /spores-ws through the main domain rather than connecting directly to tasks.*.

The /mobile/* Mirror Pattern

Every authenticated endpoint the mobile app needs is mirrored under /mobile/* in nginx. These routes:

  1. Validate the session token via auth_request to /_check_mobile_auth
  2. Strip the /mobile prefix
  3. Proxy to the upstream service
# Auth subrequest — validates ?session= param
location = /_check_mobile_auth {
    internal;
    proxy_pass http://bridge:8080/mobile/auth-check?session=$arg_session;
}

# Example: mobile chat WebSocket
location /mobile/ws/chat {
    auth_request /_check_mobile_auth;
    rewrite ^/mobile/(.*)$ /$1 break;
    proxy_pass http://bridge:8080;
    # ... WebSocket headers ...
}

No-auth routes

Three routes skip authentication: sysbus, spores-ws, and activity-ws. These are read-only event streams with no sensitive data. Skipping auth avoids complexity with WebSocket token validation on host-based services that run outside Docker.

WebSocket Auth: Query Params, Not Cookies

iOS's native WebSocket implementation cannot set cookies on the handshake request. React Native's WebSocket similarly has no cookie jar. The solution: pass the session token as a query parameter.

// Mobile WebSocket factory
function createMobileWebSocket(session: string) {
  return (url: string) => {
    const mirrored = url.replace("/ws/", "/mobile/ws/");
    const sep = url.includes("?") ? "&" : "?";
    return new WebSocket(mirrored + sep + "session=" + encodeURIComponent(session));
  };
}

Nginx's _check_mobile_auth reads $arg_session from the query string, so this works for both HTTP and WebSocket requests.

How Mobile Components Get Data

Before (broken)
  • Spores: HTTP fetch to raw.githubusercontent.com/*/spores.json → 404 (private repo)
  • Activity: WebSocket to activity.mushroomcloudcomputing.com/ws → 403 (OAuth blocks)
  • Tasks: HTTP fetch to /tasks.md → 403 (behind oauth2-proxy)
After (fixed)
  • Spores: WebSocket to /mobile/spores-ws → nginx proxies to mcc-taskmaster on host:9102
  • Activity: WebSocket to /mobile/activity-ws → nginx proxies to mcc-activity on host:9101
  • Tasks: HTTP fetch to /mobile/admin/api/tasks?session=... → nginx proxies to admin-api:3001
