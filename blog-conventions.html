Blog & Doc Conventions

Internal guide for generating docs and blog-style pages. These rules ensure consistency, navigability, and a good reading experience.

File structure

Must
All docs live at the repo root. Related docs are grouped into topic folders (e.g., message/, stream/, game/). Standalone docs live at the root until they get a sibling on the same topic.
Must
All files in a topic folder are assumed related by proximity. When a second doc on the same topic appears, create a folder and move both in.
Must
HTML for rich content (styled pages, interactive demos, pixel art). Markdown for simple references and conventions. Prefer HTML for anything a reader will browse.
Must
Every new doc must be added to index.html (the landing page) so it's discoverable.

Navigation

Breadcrumbs

Must
Every page gets a breadcrumb at the top. Immediately after <body>, before the <h1>. This lets the reader always navigate back to the index and see where they are.

For root-level pages:

<nav style="margin-bottom: 1.5rem; font-size: 0.85rem;">
  <a href="index.html" style="color: #5dade2; text-decoration: none;">MCC Docs</a>
</nav>

For pages in a topic folder:

<nav style="margin-bottom: 1.5rem; font-size: 0.85rem;">
  <a href="../index.html" style="color: #5dade2; text-decoration: none;">MCC Docs</a>
  / <span style="color: #94a3b8;">Topic Name</span>
</nav>

The breadcrumb uses inline styles matching the page's link and muted colors. index.html is the root and does not need a breadcrumb.

Series nav

Must
Sibling nav after the title. Every doc in a folder with peers gets a nav block after the title/subtitle. Lists all siblings in the same folder, highlights the current page, and links to the others. This is how readers move between related pages — like a blog series. 
<nav style="padding: 0.8rem 1.25rem; background: var(--surface); ...">
  <div style="...">Series / Topic name</div>
  <div><a href="intro.html">Introduction</a> — short description</div>
  <div><strong>Current Page</strong> (this page)</div>
</nav>
Must
Nav goes at the top, not the bottom. Readers need orientation before they start reading. A nav at the bottom means they have to scroll past the entire page to find related content.
Should
When linking to a new doc in chat, link to an existing page the user can refresh (like the intro or index), not directly to the new page. The user navigates from the parent — this confirms the nav works and the page is reachable.

Styling

Must
All pages link to the shared style.css. Pages in subdirectories use ../style.css. No inline <style> blocks for base styling — only for page-specific additions (custom palettes, demos).
Should
Dark theme consistent with the project aesthetic. Use the standard palette: #0f172a bg, #1e293b surface, #e2e8f0 text, #94a3b8 muted, #5dade2 links. Topic-specific pages (like the game docs) can define their own palette.
Should
Max width 700-860px, centered. Comfortable reading width. Wider for pages with visual demos or code-heavy content.

Content patterns

Title block

Every page starts with: breadcrumb nav, h1 title, .subtitle one-liner, optional .meta with date/status. Then the series nav (if applicable). Then the content.

Series progression

When a topic has multiple docs, follow a natural progression:

  1. Fundamentals — what exists, how it works today
  2. Scenarios — concrete examples, walkthroughs, edge cases
  3. Decisions — what to keep, change, explore
  4. Design — the resulting spec or architecture

Not every series needs all four. A topic can start as one page and grow.

Interactive / visual demos

CSS-only where possible for visual elements (pixel art grids, animated scenes, diagrams). This keeps pages self-contained and fast.

For runnable code examples, use the established "Run" button pattern (see Stream Library Code Guide for a working example). The pattern:

<pre><code id="ex-NAME-code">
// Your example code here
// Use log() instead of console.log()
const result = doSomething();
log('Result:', result);
</code></pre>

<button class="run-btn" onclick="runExample('ex-NAME')">Run</button>
<div class="output" id="ex-NAME-output"></div>

The runExample() function captures the code block's text content, wraps it in an async function with library imports in scope, and prints output to the output div. Examples should use log() for output (not console.log). Library-specific imports are loaded via a bundled ES module at the top of the page's <script type="module"> block.

Should
Every code example that demonstrates behavior should be runnable. Static code blocks (type signatures, configuration) don't need Run buttons.

Hosting

Must
Docs are hosted via GitHub Pages. Push to main and the site deploys automatically. No build step, no server configuration — static HTML served directly from the repo root.
Must
Verify URLs before sharing. After creating or moving a doc, check the GitHub Pages URL to confirm it's live before posting the link. 404s erode trust.

When to use the series convention

The series pattern (shared nav, progression, cross-references) is optional. Use it when:

  • A topic has 2+ documents and is growing
  • You want to drive toward decisions with artifacts left behind
  • Multiple angles (text, diagrams, interactive) would help understanding

Don't use it for standalone references, one-off research, or simple docs that won't be revisited. When in doubt, ask.
