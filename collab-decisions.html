Collaboration Design Decisions

Every non-trivial choice for the collaboration system — what was chosen, what was rejected, and when to revisit.

D1: Context as the primary collaboration primitive (not agent)

Chosen: A Context is the top-level object. Members, messages, tasks, and assets belong to a context. An agent is an optional binding on a context.

Alternatives:

  • (A) Keep agent = collaboration. Each collaboration gets a full MCP agent.
  • (B) Introduce "rooms" within a single agent.

Why this: Option A is the status quo and requires a Docker container + Claude session per collaboration, costing ~$0.50/day idle and not scaling past 5–10 collaborations. Option B keeps the agent-centric model but adds complexity inside agents that don't need it. A context is lighter — tier-0 contexts have zero AI cost. The agent becomes a pluggable layer, not the foundation.

Revisit if: Every collaboration genuinely needs a persistent AI agent (unlikely given the party-planning use case, which is mostly human-to-human with occasional AI assist).

D2: Three-tier agent binding

Chosen: Three tiers: none (relay), batch (claude --print), full (MCP agent).

Alternatives:

  • (A) Two tiers: none and full.
  • (B) Continuous spectrum (configurable per-request).

Why this: Two tiers forces every AI-enabled context to bear the full cost of a persistent agent. The batch tier is the sweet spot for most collaborations: inject context state into a prompt, get a one-shot response, no persistent session. Option B is overengineered for the current use cases.

Revisit if: Batch latency (cold-start claude --print is ~3s) is unacceptable for a use case, or if a use case needs tools but not persistence (could add a tier 1.5: batch with tools).

D3: Go for the context service

Chosen: cmd/context-service/main.go, same pattern as chatbus, scheduler, builder.

Alternatives:

  • (A) TypeScript/Bun service.
  • (B) Add context endpoints to the existing chatbus.

Why this: All backend services are Go. Adding a TS service introduces a new runtime dependency in production. Option B overloads the chatbus, which has a clear single responsibility (message routing). A separate service follows the existing pattern and can be developed/deployed independently.

Revisit if: The team shifts to TypeScript for all services, or if the context service is so thin that a separate container is unjustified (fold into chatbus).

D4: File-based storage (YAML config + JSONL messages)

Chosen: Each context gets a directory under data/contexts/{id}/. Config is context.yaml, messages are messages.jsonl, tasks are tasks.md.

Alternatives:

  • (A) SQLite per context.
  • (B) Postgres/Redis.
  • (C) Single global JSONL (like current bus-messages.jsonl).

Why this: YAML and JSONL are human-readable, inspectable with standard tools, and trivially backupable. The current chatbus already uses JSONL successfully. SQLite adds a dependency and makes data inspection harder. Postgres/Redis is massive overkill for <100 contexts. Option C loses isolation — context data must never leak across contexts.

Revisit if: Message volume per context exceeds ~100K messages (JSONL scan becomes slow), or if complex queries are needed (search across messages, aggregations). At that point, SQLite per context is the right step up.

D5: WebSocket hub in context-service (not chatbus)

Chosen: Context-service manages its own WebSocket connections per context. Messages flow: client WS → context-service → persist + broadcast. Agent messages flow: chatbus → context-service → broadcast to WS clients.

Alternatives:

  • (A) Clients connect to chatbus directly, chatbus gains context routing.
  • (B) Clients connect to bridge, bridge routes to context-service.

Why this: Option A violates chatbus's single responsibility (inter-service message routing, not client-facing WebSocket management). Option B adds a hop and couples the bridge to context semantics. Context-service owns the context lifecycle, so it should own the client connections for that context.

Revisit if: Context-service WebSocket management becomes a bottleneck (unlikely at <100 concurrent connections), or if all client WebSockets should unify through a single gateway.

D6: Per-context access via email allowlist

Chosen: Each context has a members array with email addresses and roles. Context-service checks X-Auth-Email (from oauth2-proxy) against the member list.

Alternatives:

  • (A) Role-based access control (RBAC) with permission matrices.
  • (B) Token-based access (share a secret link).
  • (C) Reuse deploy/routes.json access lists.

Why this: Email allowlists are dead simple and match the existing auth model (routes.json already uses email lists). RBAC is overkill for two roles. Token-based access bypasses the OAuth flow. Option C couples contexts to the deploy config, which should be for system routing, not collaboration membership.

Revisit if: More than two roles are needed (e.g., read-only, admin, moderator), or anonymous/guest access is required.

D7: Owner and collaborator roles only

Chosen: Two roles: owner (full control: settings, membership, deletion) and collaborator (read/write: messages, tasks, notes, assets).

Alternatives:

  • (A) Three roles: owner, editor, viewer.
  • (B) Fine-grained permissions per layer (can_chat, can_edit_tasks, can_upload).

Why this: The first use case is two people (owner + Lisa). A viewer role would be needed for larger groups, but not now. Fine-grained permissions add UI complexity for settings that nobody will configure. Start with two roles; add viewer when someone asks for it.

Revisit if: A context has >5 members and the owner wants some to be read-only.

D8: Context switcher replaces agent selector

Chosen: The UI's top-level selector switches between contexts, not agents. Each context renders the tiles appropriate to its enabled layers.

Alternatives:

  • (A) Keep agent selector, add context selector as a second dropdown.
  • (B) Tabs or sidebar for contexts.

Why this: Two selectors create confusion about which one controls what. The agent selector's current purpose (pick Marcel, Vanya, etc.) maps directly to "pick a context" since each agent becomes a context. A sidebar (option B) is planned for the full UI but the switcher dropdown is simpler to implement first and matches the existing UI pattern.

Revisit if: The number of contexts exceeds what fits comfortably in a dropdown (~10), at which point a sidebar with search is better.

D9: Messages as JSONL, not in chatbus

Chosen: Context messages are stored in per-context messages.jsonl files, separate from the global bus-messages.jsonl.

Alternatives:

  • (A) Store in chatbus global JSONL with a context field for filtering.
  • (B) Store in chatbus and per-context (dual write).

Why this: The chatbus JSONL is a system bus log — it contains all inter-service traffic, not just user-facing messages. Context messages are user content with different retention, privacy, and access requirements. Mixing them makes it hard to delete a context's data or enforce context isolation. Dual-write adds consistency risk.

Revisit if: Cross-context message search is needed (which would require an index anyway, at which point the storage backend changes).

D10: No database, no ORM

Chosen: Direct file I/O. YAML parsed with gopkg.in/yaml.v3, JSONL with encoding/json line-by-line.

Alternatives:

  • (A) SQLite with an ORM.
  • (B) Embedded key-value store (bbolt, badger).

Why this: The data model is simple: one YAML file per context, one JSONL file per context's messages. File I/O is the simplest correct solution. Adding a database adds schema migrations, connection management, and a dependency.

Revisit if: Transactions are needed (e.g., atomic membership + access control updates), or query performance degrades.

D11: Presence via WebSocket heartbeat, not a separate system

Chosen: Presence (who is online in a context) is tracked by context-service based on active WebSocket connections. A member is "online" if they have at least one open WS connection to that context.

Alternatives:

  • (A) Separate presence service with Redis pub/sub.
  • (B) Polling endpoint.

Why this: The WebSocket connection already exists per context. Tracking connection state is trivial and doesn't require another service. Redis adds operational complexity for a feature that serves <20 concurrent users. Polling wastes bandwidth.

Revisit if: Cross-service presence is needed (e.g., "is Lisa online anywhere in the system"), or if WS connections are distributed across multiple server instances.

D12: Message envelope includes sender identity

Chosen: Every message carries from_email, from_name, and role. The server stamps these from the authenticated session, not from client-provided data.

Alternatives:

  • (A) Client sends display name, server trusts it.
  • (B) Only email, display name resolved client-side.

Why this: Trusting client-provided identity is a security hole. Server-stamped identity ensures messages are attributed correctly. Including both email and name avoids a client-side lookup step.

Revisit if: Identity providers beyond oauth2-proxy are added where email isn't the canonical identifier.

D13: Batch agent uses context state injection, not conversation history

Chosen: When a tier-1 (batch) agent processes a request, it receives: the last N messages, current tasks, and pinned notes — formatted as a system prompt prefix to claude --print.

Alternatives:

  • (A) Full conversation history replay.
  • (B) RAG over message history.
  • (C) Summary of conversation.

Why this: Full history is expensive and hits context limits quickly. RAG requires an embedding pipeline that doesn't exist. A summary loses detail. Injecting recent messages + structured state (tasks, notes) gives the model enough context for one-shot assistance without infrastructure overhead.

Revisit if: Users complain the batch agent "doesn't remember" — at that point, add a conversation summary that's updated periodically and injected alongside recent messages.

D14: Mobile support via responsive web, not native components

Chosen: The collaborative UI works on mobile through responsive CSS. The same SPA serves both desktop and mobile browsers. No native mobile components for contexts.

Alternatives:

  • (A) Native React Native components in the Expo app.
  • (B) Separate mobile-optimized web view.

Why this: The Expo app is still early stage. Building context UI twice (web + native) doubles the work. Responsive web gives mobile support immediately. The collaboration features (chat, tasks, notes) are standard UI patterns that work well in mobile browsers.

Revisit if: The Expo app becomes the primary mobile interface and web views feel second-class.

D15: Invitation by email, not by link

Chosen: The owner invites collaborators by entering their email. The system sends an invite email via Resend. The invitee must log in with that email via OAuth.

Alternatives:

  • (A) Shareable invite link (anyone with the link can join).
  • (B) Invite code (enter a short code to join).

Why this: Email-based invitation ties directly to the auth model (oauth2-proxy checks email). A shareable link bypasses access control. An invite code adds a step without adding security over email-based auth.

Revisit if: Users without Google accounts (the current OAuth provider) need to be supported, or public/semi-public contexts are desired.

D16: No cross-context data sharing

Chosen: Contexts are fully isolated. No mechanism to reference data from one context in another.

Alternatives:

  • (A) Opt-in cross-context references (link a note from context A into context B).
  • (B) Global shared library of artifacts.

Why this: Isolation is the safe default. Cross-context references create permission complexity (if Lisa can see context A but not context B, and context A references context B data, what happens?). Build isolation first; add controlled sharing later if needed.

Revisit if: The owner has related contexts (e.g., "Lisa party" and "Lisa birthday") and wants to share assets between them.

D17: Context IDs are slugs, not UUIDs

Chosen: Context IDs are human-readable slugs (e.g., party-planning, reyes-project). Generated from the context name, with conflict resolution by appending a counter.

Alternatives:

  • (A) UUIDs.
  • (B) Numeric auto-increment.

Why this: Slugs are readable in URLs, file paths, and logs. UUIDs are opaque and make debugging harder. The slug appears in data/contexts/{id}/, in WebSocket paths /ws/context/{id}/chat, and in API routes /api/contexts/{id}. Human-readable identifiers make all of these easier to work with. Conflicts are rare (owner creates contexts, not automated systems).

Revisit if: Context renaming without breaking references is needed, or if slugs collide frequently.
