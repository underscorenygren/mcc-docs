Taskmaster

Procedural task reconciliation — snapshot + delta → new snapshot.

TL;DR

A Claude oneshot that reads evidence (git, PRs, chat), applies deterministic rules, then uses an LLM for ambiguous cases. Outputs a compressed project snapshot and a structured decision log. Runs on a schedule, independent of any Claude session.

Repo: mcc-taskmaster
Task store: mcc-tasks

Problem

Task tracking depends on the supervisor agent being active. If the supervisor isn't running, tasks go stale. The session review only runs at midnight when the supervisor is up. This is best-effort, not procedural.

Model

previous snapshot + delta (git, PRs, issues, chat)
  → deterministic rules (PR merged → done, inactivity → forgotten)
  → LLM oneshot (ambiguous: chat intent, new tasks, cross-project)
  → new snapshot + decision log + unknowns queue + run metadata

Snapshot: projects with three buckets

Projects are the organizing unit. Each project has three buckets:

now What's actively being worked on. Recent commits, open PRs, recent chat.
forgotten Half-done work nobody's watching. Stale branches, abandoned PRs, idle tasks. The most valuable bucket.
done Completed work. Merged PRs, closed issues, user confirmation.

The snapshot is compressed knowledge. An agent loads it and gets the full picture without reading hundreds of commits. Evidence refs point back to raw data for drill-down.

Decisions: structured audit trail

Every state change is a structured entry with action, evidence, reason, and confidence level. Two confidence levels:

  • deterministic — rule matched, no LLM (PR merged → done)
  • llm_judged — LLM interpreted evidence (chat message → task done)

Goal: maximize deterministic, minimize LLM. Rules handle the obvious cases before the LLM sees anything.

Chat as command interface

User messages are the primary reason things happen. Raw messages cluster into logical segments:

Messages (many, small):          Segment (one, compressed):
────────────────────             ───────────────────────────
"lets make a new repo"           project: taskmaster
"mcc-taskmaster"                 type: command
"add deploy docs"                outcome: "Created mcc-taskmaster repo"
"write a test post"              duration: 6 min

Segment types: command (do X), brainstorm (think about X), status check, feedback, noise.

Learning

Human triage decisions become rules in learned-rules.yaml:

  • Dismiss unknown → ignore rule ("FEMA alerts are noise")
  • Link to project → topic map ("convex talk maps to ablog project")
  • Correct decision → override rule

The system starts dumb and gets smarter. First runs produce many unknowns. After a few triage cycles, most routine evidence is handled automatically.

Architecture

[scripts — parallel, no LLM]
┌─ git-collector    → delta.git.json
├─ github-collector → delta.github.json
└─ chat-collector   → delta.chat.json

[deterministic rules — no LLM]
── rule-engine      → pre-decisions + remaining evidence

[LLM oneshot — sees full context]
── synthesizer      → new snapshot + decisions + unknowns + run_meta

If context grows past ~50k tokens, split into per-project oneshots. Run metadata tracks token cost per run to make this data-driven.

Implementation: seed → collect → rules → LLM

1. Seed

One-time bootstrap from mcc-tasks/tasks.md. Parse existing markdown into snapshot.json. Deterministic — no LLM. Map tasks to projects by repo context.

What we seed from: tasks.md (6 active, 30+ done), projects/ (2 folders), history.tsv, GitHub issues/PRs.

2. Collectors

Shell scripts. git log per repo, GitHub REST API for PRs/issues, read mcc-messages archive. All output JSON to delta/.

3. Rule engine

Deterministic. PR merged → done. Inactivity → forgotten. Learned patterns → ignore/classify. Outputs what it handled and what's left.

4. LLM oneshot

Single claude --print call. Sees previous snapshot + pre-decisions + remaining evidence + learned rules. Outputs strict JSON: updated snapshot, new decisions, unknowns.

5. Write + publish

Merge decisions, write snapshot, generate tasks.md, commit + push to mcc-tasks. Rendered at tasks.mushroomcloudcomputing.com.

Evaluating success

Run 1 Does the seed snapshot match reality? Compare to tasks.md by hand. Are the project mappings right?
Run 2-5 Unknown rate should decrease. Deterministic decisions should increase. Snapshot should stay accurate (spot-check against git).
Ongoing Token cost stable or decreasing. Forgotten bucket surfaces real missed work. New sessions orient faster from snapshot.
Failure modes Snapshot drift (says X, reality is Y). Over-classification (too aggressive). Context blowup (tokens growing unbounded).

Quick iteration path

  1. Seed — parse tasks.md → snapshot.json. Review by hand.
  2. Collectors only — run collectors, inspect delta JSON. Is the data there?
  3. Rules only — collectors + rules. Are obvious cases handled?
  4. Full run — add LLM. Inspect snapshot + decisions. Triage unknowns.
  5. Schedule — daily trigger. Monitor run_meta for cost and accuracy.

Each phase is independently testable. Don't move to the next until the current one looks right.
