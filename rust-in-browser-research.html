Rust in the Browser

Options for sharing a Rust stream/messaging library between server and browser client. October 2026.

Context: a Rust codebase implementing a stream and messaging library (framing, sequencing, delivery guarantees). The goal is to run the same logic in both a server process (native Rust or Node/Bun via NAPI) and a browser client. A TypeScript transpile of the Rust code already exists.

Option 1: Rust to WebAssembly

Recommended Compile Rust to WASM, run in browser
The Rust toolchain has first-class WASM support. wasm-pack compiles Rust to WASM and generates JS/TS bindings via wasm-bindgen. The result is an npm-installable package that exposes Rust types and functions to JavaScript.

Toolchain

# Install
rustup target add wasm32-unknown-unknown
cargo install wasm-pack

# Build — produces pkg/ with .wasm + .js + .d.ts
wasm-pack build --target web     # ES module, no bundler needed
wasm-pack build --target bundler # for webpack/vite/esbuild
wasm-pack build --target nodejs  # for Node.js (not browser)

wasm-bindgen handles the JS-Rust boundary: converts types, manages memory, generates TypeScript declarations. In 2026 it handles String, Vec<u8>, structs (via #[wasm_bindgen]), enums, Result, and Option.

Async support

Rust async functions annotated with #[wasm_bindgen] compile to JS Promise-returning functions. The wasm-bindgen-futures crate bridges Rust futures to JS promises. This works well for request/response patterns. For streaming (continuous frame processing), the typical pattern is to call synchronous Rust functions from JS in a loop or on each incoming message, avoiding the need for Rust-side async runtimes in WASM.

What WASM cannot do

  • No direct DOM access (must call back into JS)
  • No direct network I/O (no sockets, no fetch from inside WASM)
  • No threads by default (SharedArrayBuffer + Web Workers possible but complex)
  • No direct file system access

For a stream library, this is fine: JS handles the WebSocket connection and passes raw frames into WASM for processing. WASM handles framing, sequencing, buffering, reassembly. JS handles I/O.

Bundle size

A typical Rust WASM module compiles to 50-200 KB gzipped for a medium library. Using wasm-opt (included in wasm-pack) and lto = true in Cargo.toml brings this down. A pure data-processing library without large dependencies (no serde_json, no regex) can be under 50 KB. This is comparable to a minified JS library of equivalent complexity.

Performance

WASM runs at near-native speed for compute-bound work. For a stream library, the main cost is crossing the JS-WASM boundary — each call involves copying data across the boundary (no shared memory by default). For message framing, this is negligible: copying a few KB per frame is fast. For bulk data (audio streams, large buffers), Uint8Array views into WASM linear memory avoid copies.

Option 2: Rust to TypeScript Transpilation

Caution Transpile or manually port Rust to TypeScript
Maintain a TypeScript version of the Rust code. This can be a manual port (already done), an LLM-assisted translation, or tooling like ts-rs (type generation only, not logic).

Current state of tooling

No production-grade Rust-to-TypeScript transpiler exists in 2026. The tools that do exist:

  • ts-rs — generates TypeScript type definitions from Rust structs. Does not transpile logic. Useful for keeping types in sync.
  • LLM-assisted translation — works for initial port, but ongoing sync is manual.
  • Manual port — what you already have. Requires keeping two codebases in sync.

The sync problem

The fundamental issue: two codebases that must stay semantically identical. Every change to the Rust library requires a corresponding change to the TypeScript version. This is manageable for stable code but painful for actively evolving libraries. Behavioral drift is inevitable without cross-language test suites that exercise both implementations against the same fixtures.

When this makes sense

If the TypeScript port already exists, is well-tested, and the Rust code is stable (not changing weekly), this is a pragmatic choice. The TS version runs everywhere JS runs with zero build complexity. It is also the easiest to debug — standard browser DevTools, standard stack traces.

Evaluation

CriterionRating
TestabilitySeparate test suites; shared fixtures possible but require discipline
Developer experienceStandard TS tooling, full debuggability
Bundle sizeStandard JS — tree-shakeable, no WASM overhead
Browser compatibilityUniversal — it is just JavaScript
Tooling maturityNo automated transpiler; manual sync is the reality

Option 3: Server-Only Rust + Thin Client

Viable Keep all logic server-side, browser is a WebSocket relay
The browser sends raw bytes to the server over WebSocket. The server handles all framing, sequencing, and protocol logic in Rust. The browser is a thin pipe: capture audio, send bytes, receive bytes, play audio.

Architecture

Browser                    Server (Rust)
  |                           |
  |-- raw audio bytes ------->|  stream library processes
  |                           |  framing, sequencing, etc.
  |<-- processed frames ------|
  |                           |
  (no stream logic here)      (all logic here)

Tradeoffs

  • Simplicity — one codebase, one language, one test suite.
  • Latency — every frame round-trips to the server. For real-time audio this adds the connection RTT to every operation. On a fast connection (sub-50ms), acceptable. On mobile or high-latency links, noticeable.
  • Offline — nothing works without the server. No buffering, no local processing.
  • Scalability — server does all the work. Each connected client adds CPU load for stream processing that could run on the client instead.

When this makes sense

When the browser client is truly thin — just capturing and playing audio, with no need for client-side buffering, reordering, or protocol awareness. This is the current architecture for many voice applications. It becomes limiting when you want client-side features like optimistic UI updates, local echo cancellation, or offline message queuing.

Evaluation

CriterionRating
TestabilitySingle codebase — standard Rust testing
Developer experienceNo cross-language concerns
Bundle sizeMinimal — browser ships almost no code
Browser compatibilityJust WebSocket — universal
Tooling maturityN/A — no special tooling needed

Option 4: Hybrid — WASM Core + JS I/O

Recommended WASM for pure logic, JavaScript for I/O and DOM
The production pattern used by Figma, 1Password, Notion, and others. Compile deterministic core logic to WASM. Keep all I/O (WebSocket, DOM, user interaction) in JavaScript. The boundary is clean: JS feeds data in, WASM processes it, JS acts on the output.

The boundary pattern

JavaScript layer          WASM layer (Rust)
  |                           |
  | WebSocket.onmessage       |
  |--- raw bytes ------------>| decode_frame()
  |                           | reorder()
  |                           | reassemble()
  |<-- processed message -----|
  | update DOM                |
  |                           |
  | user sends message        |
  |--- payload -------------->| encode_frame()
  |                           | add_sequence()
  |<-- framed bytes ----------|
  | WebSocket.send()          |
  |                           |

Production examples

  • Figma — C++ compiled to WASM for the rendering engine. JS handles UI chrome, file I/O, collaboration protocol. The canvas is a WASM-rendered bitmap.
  • 1Password — Rust core (crypto, vault logic) compiled to WASM for the browser extension. JS handles browser extension APIs, DOM, network.
  • Notion — selective WASM use for performance-critical data operations.
  • Cloudflare Workers — Rust compiled to WASM runs on the edge. The runtime provides I/O bindings.

For a stream library specifically

This is the natural fit. The stream library is pure data processing:

  • Frame encoding/decoding (bytes in, structured data out)
  • Sequence number management
  • Reordering buffers
  • Delivery acknowledgment state machines
  • Backpressure logic

None of these touch the DOM or network. They take bytes, return bytes or structured events. This is exactly what WASM excels at.

Recommendation

For a stream/messaging library: Hybrid WASM (Option 4)

The stream library is pure data processing — framing, sequencing, buffering, state machines. This maps directly to the hybrid pattern. Compile the Rust core to WASM via wasm-pack. Keep WebSocket I/O and DOM interaction in JavaScript/TypeScript.

Concrete plan

  1. Define the WASM boundary. The Rust library exposes: encode_frame(payload) -> bytes, decode_frame(bytes) -> Frame, SequenceTracker (manages ordering), DeliveryTracker (manages acks). No I/O types cross the boundary.
  2. Add #[wasm_bindgen] annotations to the public API. Use wasm-pack build --target web to produce an ES module. The output includes .d.ts files — the browser gets type-safe Rust functions.
  3. Write a thin JS wrapper (~50 lines) that connects WebSocket events to WASM functions: ws.onmessage = (e) => { const frame = wasm.decode_frame(new Uint8Array(e.data)); ... }.
  4. Run wasm-pack test --headless --chrome in CI. This runs the same Rust unit tests inside a real browser. Combined with native cargo test, you get full coverage on both targets from one test suite.
  5. Retire the TS transpile once the WASM path is validated. The TS port becomes unnecessary — it was a bridge to this point.

What about the existing TS transpile?

Keep it running until the WASM path is proven. The migration sequence:

  1. Build WASM package, integration-test against the same fixtures as the TS version
  2. Run both in parallel (A/B) in the browser for a release cycle
  3. Once parity is confirmed, drop the TS version

The TS transpile is a maintenance liability — every Rust change requires a corresponding TS change. The WASM path eliminates this entirely. One source of truth, two compilation targets.

What about Node/Bun server-side?

On the server you have three options, in order of preference:

  • Native Rust — if the server is already Rust, just use the library directly.
  • NAPI binding (napi-rs) — compiles Rust to a native Node addon. Full native speed, no WASM overhead. Works with Bun.
  • WASM in Node/Bun — both runtimes support WASM natively. Slightly slower than NAPI but uses the exact same .wasm file as the browser. Simplest path to "same binary everywhere."

For maximum code sharing with minimum build targets: use the same WASM binary on both server and browser. For maximum performance on the server: use NAPI. Both approaches use the same Rust source.
